# Worker State Between Requests

In [worker mode](worker-mode.md) one PHP worker serves many requests, so its state either belongs to a request and is reset when that request ends, or belongs to the worker and persists. This page lists both, and where the reset stops.

## What Gets Reset Between Requests

OxPHP performs a soft reset between requests. The following state is cleaned automatically:

- **Superglobals** — `$_GET`, `$_POST`, `$_SERVER`, `$_COOKIE`, `$_FILES`, `$_REQUEST`, and `php://input` are repopulated with the new request data
- **Output buffers** — all output buffers are flushed and cleaned
- **Response headers** — HTTP status code and headers are reset to defaults
- **What PHP keeps per thread for a request** — the headers `http_get_last_response_headers()` returns after a fetch through the `http://` wrapper, the string `strtok()` goes on splitting, the `ob_implicit_flush()` setting, whether the request's output has gone out, after which PHP refuses a change to `zlib.output_compression` — the change `header('Content-Length: …')` makes too — and where that output started, which `headers_sent($file, $line)` reports. Each request starts without them, and a request paused at a [suspension point](fiber-multiplexing.md#suspension-points) takes its own with it and finds them again when it resumes. `ob_implicit_flush()` starts off in every request even with `implicit_flush` on in `php.ini`: PHP applies that directive as a request starts up, which a worker does once, when it boots. Call `ob_implicit_flush()` in the request that wants it
- **Error state** — last error information (message, file, line, type) and connection status are cleared. User-registered error handlers (`set_error_handler()`) and exception handlers (`set_exception_handler()`) persist across requests
- **Objects after a fatal error** — a fatal error releases the objects whose last reference was in the failed request's own variables without running their destructors, as PHP does after a fatal. It takes nothing else's: objects the worker keeps across requests, and those of the other requests in flight on the same worker — or, on a thread of the [async pool](async-promises.md), of the other tasks on it — have their destructors run when they are let go of, after the fatal as before it. So does an object of the failed request that outlives the worker's recovery from the fatal, where PHP-FPM skips it. For example: one still held by one of that request's shutdown functions or output handlers, or in its `$_SESSION`, when that reference goes; on PHP 8.5, one passed to a call in the fatal's backtrace — the one `error_get_last()` returns — when the request ends, with `fatal_error_backtraces` on (the default) and `zend.exception_ignore_args` off; one in a reference cycle, when the cycle collector frees it (with `zend.enable_gc` on, the default), which can be while another request is running, as for any request's cyclic garbage on a worker; and one the worker could not give back, when the worker stops
- **Session state** — the session a request opened is closed as that request ends, after its shutdown functions and before its ini changes are put back — the order PHP's own request shutdown uses, so the write runs under that request's settings: the data is handed to the save handler, the session id is released, and `$_SESSION` leaves the symbol table. The next request therefore starts a session under its own cookie, reads `''` from `session_id()` until it does, and finds `$_SESSION` undefined until then. Two boundaries here as well: a session travels with its request, and a worker has one open at a time; a closed session stays with its request. Both are described under [Sessions](#sessions) below.
- **ini directives changed by the request** — anything a request altered with `ini_set()`, `ignore_user_abort()` or `error_reporting()` belongs to that request, as it would under PHP-FPM: it is put back when the request ends. Most directives are also the request's own while it is paused — on an await, a sleep or a socket wait: they are taken off the worker, so the requests the worker runs in the meantime see the baseline rather than the paused request's values, and the paused request resumes with its own. `ini_set('default_socket_timeout', 5)` around one HTTP call and `ini_set('display_errors', '1')` in a debugging branch apply to the request that made them and not to the next one. What your **bootstrap** set is the baseline they are restored to, not the value in `php.ini` — an `ini_set()` in the outer scope is application configuration and survives every request, and every request starts with it. That includes `ignore_user_abort(true)`: called in the bootstrap, it applies to every request the worker serves, streams included (see [Server-Sent Events](sse.md)). See [What Persists](#what-persists). Seven boundaries are worth knowing:
    - **`memory_limit` and the `session.*` settings stay with the worker while it has other requests in flight.** The heap belongs to the worker thread, not to a request, and so does the session module the `session.*` settings configure (see [Sessions](#sessions)) — including the save handler `session_set_save_handler()` installs. So these are not taken off the worker when a request pauses, and they are put back only when the worker takes its next request with nothing else running on it. While a worker has work in flight — the case whenever a request is paused, and also while a fire-and-forget promise is still being reclaimed — a value one request set here applies to the requests the worker takes in that window. A session already open is the exception: it keeps the save handler and serializer it was opened with until it is closed, whatever another request installs meanwhile. A request waiting in `session_start()` for another request's session to close is not: it opens its session with the save handler and `session.*` settings in force when its turn comes, which a request run while it waited may have changed. Configure sessions the same way in every request, or once in the bootstrap.
    - **`set_time_limit()` sets the limit of the request that calls it, but `ini_get('max_execution_time')` reports the worker's.** Each request has a time limit of its own (see [Request Deadlines](worker-mode.md#request-deadlines)), and `set_time_limit()` — or `ini_set()` or `ini_restore()` on `max_execution_time` — changes that one and no other. The directive itself stays with the worker, as `memory_limit` does: `ini_get('max_execution_time')` answers with the last value any request set since the worker last had nothing in flight — or the bootstrap's, if none did — which on a worker carrying several requests need not be the caller's own limit, and it is put back when the worker takes its next request with nothing else running on it.
    - **A directive whose handler does more than store its value stays on the worker while its request is paused.** Moving a directive runs its handler, and some handlers act as they store: `default_charset` and the encoding settings reset mbstring's encodings, `zlib.output_compression` starts an output handler, `open_basedir` resolves a relative path against the current directory, and the deprecated `assert.*` settings raise a deprecation each time. Run on every pause and resume, they would undo what the request did in between, so these directives are not taken off the worker: the requests it runs while one is paused see the paused request's value, and are put back when the last request in flight ends. The directives that travel are the ones stored by one of PHP's standard setters — `ignore_user_abort`, `precision`, `display_errors`, `error_reporting`, `default_socket_timeout`, `user_agent` and most others. A few with a handler of their own stay on the worker too although they only validate the value: `include_path` while OPcache is enabled (OPcache installs its own handler for it, so `set_include_path()` included; with OPcache off it travels), `error_log`, `date.timezone` and `default_mimetype`. What a request sets through a function rather than an ini directive — `mb_internal_encoding()`, `date_default_timezone_set()`, `setlocale()` — is not an ini change at all: it is the worker's, and outlives the request unless the request puts it back — except the environment that `putenv()` writes, which the worker puts back itself (see below).
    - **A directive whose handler refuses to be put back stays as the request left it.** Putting a directive back runs its handler, and a handler can refuse. Such a directive keeps the request's value until the worker next takes a request with nothing else running on it, and a paused request whose change is refused when it resumes continues without that change.
    - **A request ended while one of its directives is being moved recycles the worker.** A handler can run application code: putting `assert.callback` back drops the callback, and with it whatever the callback held, whose destructors run there. Anything that ends the request from inside one of them — a fatal error, or output written by a stream whose client has already left — leaves the handler part-way through: the callback still set, and pointing at a closure already half torn down. Nothing short of a fresh worker puts that right, so the worker exits under `oxphp_worker_recycles_by_reason_total{reason="scheduled"}`, and the requests still in flight on it are ended as they are on any other recycle. The request itself is filed as its ending says: a fatal is answered `500` and counts toward the error breaker, a client that left is a cancellation and does not. An exception such a destructor throws is reported as the request's uncaught exception instead, and costs nothing more.
    - **`memory_limit` is restored as a value before it is restored as a limit.** PHP refuses to lower the allocator's ceiling while more than the new limit is still held, so a worker left holding what the request allocated reports the restored `memory_limit` from `ini_get()` while the allocator is still enforcing the raised one. The ceiling follows as soon as the worker's own footprint leaves room for it.
    - **`opcache.enable` is not restored at all.** Turning OPcache off is the only thing a request can do to it — PHP refuses to switch it back on mid-request — and what raises it again is OPcache's own per-request startup, which a worker runs once, when it boots. So a worker whose request turned OPcache off compiles every file from source for the rest of its life, and the directive is left reading `0` to say so. Restoring it would make `ini_get('opcache.enable')` and `opcache_get_status()` report an enabled cache that is not running, which is the worse of the two: an application that asks in order to decide something would be told the opposite of what is happening.
- **Environment variables set with `putenv()`** — `putenv()` writes the environment of the whole server process, the one `getenv()` reads and that a child process started by `exec()`, `shell_exec()`, `system()` or `proc_open()` without an `$env` array inherits. What a request sets there is put back when the request ends, as PHP's own request shutdown puts it back in traditional mode: a variable the request added is removed, and one it overwrote gets back the value it had before. What your **bootstrap** set before `oxphp_worker()` is the baseline: a request that overwrites such a variable ends it back to the bootstrap's value, so the next request starts with it again unless something else has set it since, as the boundaries below describe. Laravel's `Env`, which by default writes `.env` values with `putenv()` as well, keeps them for every request. Four boundaries:
    - **Until the request ends, the value is the process's.** There is one environment per process, and it is not taken off the worker when a request pauses, so other requests read what a request set while that request is still running: requests on other workers, and requests the same worker runs while the request that set it is paused at a [suspension point](fiber-multiplexing.md#suspension-points). Traditional mode has the same window for requests running at the same time on other workers, since every worker is a thread of one process — under PHP-FPM each is a process of its own. A value that belongs to one request, such as one client's credentials, belongs in a variable, or in the `$env` array of the `proc_open()` call that needs it, not in the environment.
    - **The last request to set a name owns it.** A request that sets a name another request on the same worker set and has not finished yet replaces that request's value, and the name is put back when the later request ends — to the value it had before either of them, so the earlier request does not get its own back.
    - **Every `putenv()` made while a request runs is that request's.** A bootstrap that runs lazily, inside the first request rather than before `oxphp_worker()`, has its `putenv()` calls undone when that request ends; call `putenv()` before `oxphp_worker()` for values every request is to see. A `putenv()` made outside every request — by a destructor or a callback the worker runs between requests — is put back when the next request on that worker ends.
    - **Not in `oxphp_async()` tasks.** A task runs on an async worker thread, not in the request that started it, and what it sets with `putenv()` stays for the life of that thread.

### Sessions

#### A session travels with its request

A worker takes new requests, and resumes the ones it has paused, whenever the request it is running suspends:

- in `oxphp_async_await()`, `oxphp_sleep()` or `oxphp_usleep()`;
- in a `sleep()`, `usleep()`, `stream_select()` or socket wait taken over by `RUNTIME_HOOKS` (for a socket, a read; with the `net` category also a connect — `new PDO('mysql:…')` and `new mysqli(...)` included — a TLS handshake, or a write that has to wait for room);
- in a streaming response's flush that waits for its client to make room (see [Server-Sent Events](sse.md#how-it-works)).

With `RUNTIME_HOOKS` on, the worker holds new requests back for a bounded time behind its [first request](runtime-hooks-shared-state.md#hooked-waits-and-shared-application-state).

PHP's session module, though, keeps one session per thread, and `session_start()` on a thread where a session is open answers `true` without looking at the caller's cookie. So a request's session is taken off the worker when the request suspends and put back when it resumes, as its superglobals are: its id and `$_SESSION`, open or closed, and while it is open the save handler and serializer it was opened with. A request run in the meantime that registers a handler of its own or changes `session.serialize_handler` therefore does not change how the paused session is written.

With the id carried in URLs (`session.use_trans_sid` on, `session.use_only_cookies` off — both deprecated since PHP 8.4), the id PHP's URL rewriter appends to the request's links and forms, and the `SID` constant, travel with it too, as do variables added with `output_add_rewrite_var()`, and all of them are given back when the request ends.

A request run in that window finds no session — `session_id()` reads `''`, `$_SESSION` is undefined — and its own `session_start()` reads its own cookie.

#### A worker has one session open at a time

A request does not open a session while another is open on the worker: the save handler can hold a lock for the open one — the default `files` handler locks the session file with a blocking call. A second open on the same thread that waited for that lock would hold the very thread the first needs to let it go, while nothing says in advance which session a `session_start()` will open.

So from `session_start()` until `session_write_close()`, `session_abort()`, `session_destroy()` or the end of the request — and after a `session_regenerate_id()` that fails part way, which can leave the save handler open without a session, at the latest until the end of the request — two things hold while that request is paused:

- the worker takes no new request — those wait in the queue for another worker, or for this one, as they do when every worker is busy;
- `session_start()` in any other request it is running waits until the session is closed, and until every request that called it earlier has had its turn, before it opens one.

Everything else on the worker goes on running meanwhile. A request waiting in `session_start()` is paused the way a sleep is, a quarter of a second at a time, and a drain or a cancellation ends it there as it ends a sleep; so does its time limit, within that quarter of a second, without opening the session. The window includes a wait inside `session_start()` itself, such as a save handler reading its store over a connection `RUNTIME_HOOKS` suspends.

Three consequences follow:

1. Sessions on one worker are open one after another, even for different clients, so a request that keeps its session open across a suspension point holds up the sessions of every other request on its worker, and every request the worker has not taken yet, for that long.
2. A request that, with its session open, waits for something only a request the worker has not taken yet, or one waiting in `session_start()`, could provide does not get it until the session is closed: with `PHP_WORKERS=1`, an HTTP call back to the server is not served until then, and fails once the caller's timeout or the server's queue wait runs out, and a wait with no timeout of its own does not end.
3. `session_start()` cannot wait inside a fiber a userland scheduler such as Revolt or AMPHP started, whose context OxPHP cannot resume, or in the cleanup a worker runs after a request has come apart (see [Where the `sleep` hooks do not suspend](runtime-hooks.md#where-the-sleep-hooks-do-not-suspend) for both), because what it would wait for runs on the same thread: there, while another request on the worker has a session open, it raises a warning and returns `false`.

#### The save handler's lock

The save handler also keeps whatever it locked until the session is closed. In the default `files` handler that is an exclusive lock on the session file, taken with a blocking call — so a request for the same session id on another worker, or in another process, waits inside the save handler, and because that wait is a blocking system call on that worker's thread, it stalls every request that worker is carrying.

Call `session_write_close()` as soon as the session data is final, and before any suspension point: both the write and the unlock then happen where your application put them, and the worker's other sessions and its queue are no longer held up.

#### A closed session stays with its request

After `session_write_close()`, the request that closed the session can still read its id from `session_id()` and its data from `$_SESSION`, as under PHP-FPM, and both go on travelling with it as described under [A session travels with its request](#a-session-travels-with-its-request), so it resumes with its own id and data while a request the worker took in between starts its session from its own cookie.

## What Persists

The following state survives across requests within the same worker:

- **Variables in outer scope** — anything defined before `oxphp_worker()` and captured via `use`
- **Static properties** — class static properties retain their values
- **Database connections** — PDO, MySQLi, and other persistent connections remain open
- **Autoloaders** — registered autoloaders (Composer, custom) remain active
- **Loaded classes and functions** — all previously loaded classes, interfaces, traits, and functions
- **ini directives set during bootstrap** — an `ini_set()` in the outer scope holds for the life of the worker and is what per-request changes are rolled back to
- **Environment variables set during bootstrap** — a `putenv()` in the outer scope is what a request's `putenv()` of the same name is put back to, for as long as the worker runs. The environment is the whole process's, though: with several workers, a name every worker's bootstrap sets goes back to what it was before the server started — or is removed — for every worker when the worker that set it first exits, until another worker's bootstrap sets it again (see [Superglobals](../php/superglobals.md#_env))
- **`$_ENV`** — deliberately not reset, with PHP's default `auto_globals_jit=1`. It describes the worker rather than the request, which is what keeps a `.env` loader's values alive past the boot that wrote them — and it keeps a write made from inside a request handler just as long, for every later request on that worker and for any request multiplexed alongside it. See [Superglobals](../php/superglobals.md#_env)
