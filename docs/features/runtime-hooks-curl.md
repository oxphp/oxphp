# cURL Under Runtime Hooks

The `curl` category of [`RUNTIME_HOOKS`](runtime-hooks.md) makes the waits of a cURL transfer suspend the current fiber, which covers every HTTP client built on ext/curl, Guzzle with its default handler among them. It is included in `1`, `true` and `all`.

## cURL transfers

With `curl` listed, a transfer suspends the fiber for everything `curl_exec()` waits on — connecting, the TLS handshake, sending the request and waiting for the answer — and `curl_multi_select()` suspends it for its wait. Resolving the host name is part of that wherever libcurl resolves in the background, as the official images' libcurl does with c-ares; a libcurl built to resolve on the calling thread holds the thread for it. `curl_multi_exec()` is not where a transfer waits: it moves every transfer as far as it can go without blocking and returns, so a loop of `curl_multi_exec()` and `curl_multi_select()`, the usual way to run transfers side by side, suspends in the second call. A wait libcurl makes outside the calls listed below, such as while a handle is destroyed, keeps the thread.

Cancelling an async task suspended in a transfer throws `OxPHP\Async\AsyncException` from the cURL call it is in. libcurl is told its wait failed, so the transfer ends and the handle can run the next one: an HTTP transfer in `curl_exec()` leaves `curl_errno()` reporting `CURLE_BAD_FUNCTION_ARGUMENT` (43), a `curl_multi_select()` leaves `curl_multi_errno()` reporting `CURLM_UNRECOVERABLE_POLL` (12), and a protocol that waits inside its own command exchange, such as FTP, can report an error of its own. A cancellation that reaches the task while a callback of a `curl_exec()` transfer waits, in a hooked `usleep()` say, is thrown there, and the transfer ends with the same error the next time it waits. In a callback `curl_multi_exec()` runs it is thrown there too, but it does not end the transfer: that stays in the multi handle, and the loop's next `curl_multi_select()` waits on the thread. A transfer the task makes after that, in a `finally` block say, waits on the thread, as it would without the hook.

**A handle another fiber is in the middle of a call on waits for it.** In worker mode a handle kept for the life of the worker, in a service or a static property, can be reached by every request on the worker, and with the hook a request can be suspended in the middle of a call on it. Another call on that handle meanwhile would be refused by libcurl (`CURLE_RECURSIVE_API_CALL`, `CURLM_RECURSIVE_API_CALL`), or would do worse: `curl_exec()` and `curl_multi_add_handle()` empty the handle's `CURLOPT_RETURNTRANSFER` buffer before they start, and `curl_setopt()` frees the value it replaces, such as a request body set with `CURLOPT_POSTFIELDS`, which the transfer may still be sending. So these calls claim the handles they are given until they return, and the same calls from another fiber wait for them: `curl_exec()`, `curl_setopt()`, `curl_setopt_array()`, `curl_reset()`, `curl_pause()`, `curl_upkeep()`, `curl_multi_exec()`, `curl_multi_select()`, `curl_multi_setopt()`, `curl_multi_close()`, and `curl_multi_add_handle()` and `curl_multi_remove_handle()`, which claim the easy handle and the multi handle together. `curl_multi_exec()` is the exception: it returns at once instead of waiting (below). A call from one of the transfer's own callbacks, on a handle that transfer holds, goes ahead. Calls that read a handle without changing a transfer, such as `curl_getinfo()`, `curl_errno()`, `curl_error()`, `curl_multi_getcontent()` and `curl_multi_info_read()`, never wait; `curl_multi_info_read()` hands each message to the first request that reads it, whichever transfer it is about. `curl_multi_getcontent()` returns a copy of what has arrived so far while the transfer may still write to it, which the rest of the transfer then leaves as it was: ext/curl's own return value shares the buffer the transfer goes on writing to, and a string read mid-way would grow, or be left on freed memory. That is while a fiber is in the middle of a call on the handle, `curl_exec()` say, or while the handle is in a multi handle it was added to with `curl_multi_add_handle()` and neither has `curl_multi_exec()` set `$still_running` to 0 nor has `curl_multi_info_read()` returned the transfer's `CURLMSG_DONE` message. The buffer stays beside the copy until the handle is freed or run again, `curl_reset()` keeping it, so an answer read mid-way takes twice its size until then; read after its end, it is the buffer itself, as without the hook. A transfer a server pushed (`CURLMOPT_PUSHFUNCTION`) gets no copy either, as no `curl_multi_add_handle()` put it in the handle.

A call made outside any fiber cannot wait. In worker mode that is chiefly a call from a destructor the worker runs between two requests: one PHP's cycle collector calls, or that of a session save handler a finished request lets go of. On a handle another fiber is in the middle of a call on, or on an easy handle in a multi handle one is, it throws `OxPHP\Async\AsyncException` instead and changes nothing, `curl_multi_exec()` included. Returned from at once there, as it is inside a fiber, `curl_multi_exec()` would keep a loop that runs until no transfer is left going for good: the other request cannot go on before that code returns. At any other moment it goes ahead, also on an easy handle another request has added to a multi handle and not yet taken out, where a `curl_setopt()` changes that request's transfer under way: keep such code off handles the worker's requests share.

The wait is bounded as the wait for a [shared database connection](runtime-hooks-shared-state.md) is: by the smaller of `max_execution_time` and `default_socket_timeout`, 30 seconds with neither set. A call whose handle is not given up within that bound, or one made where the fiber cannot be suspended (inside a fiber a userland scheduler started, or anywhere the `sleep` hooks would not suspend either), is not made at all. It throws `OxPHP\Async\AsyncException` with a message naming the reason, and the server log records it, at most once a second per worker thread. It throws rather than returning `false` because an HTTP client reads `false` as a failed transfer and may retry it, on the same handle.

A handle one fiber uses on its own, which is the ordinary case for an easy handle (one created for the transfer, or taken from a pool and put back afterwards), is never held up by this. Where a handle is shared, its calls run one after another, as they do without the hook, and the claim stops another fiber's call from landing inside one of them; the one thing a waiting call does to the call it waits for is end a `curl_multi_select()` early (below). Two things follow from that:

- A multi handle is free only between calls on it, and a loop of `curl_multi_exec()` and `curl_multi_select()` suspends inside `curl_multi_select()`, while it holds the handle. So a call from another request waiting for the handle is let in between two of the loop's calls: the loop's next `curl_multi_select()` waits for it. What the waiting call does meanwhile depends on the call:

  - A waiting call other than `curl_multi_select()`, `curl_multi_add_handle()` say, does not wait out the `curl_multi_select()` the loop is in: once that `curl_multi_select()` is all that keeps it waiting, it ends it, and that `curl_multi_select()` returns 0, as it does when its timeout runs out, only sooner. libcurl also returns 0 early when a signal interrupts the wait, so a loop that counts its zero returns as elapsed time, rather than reading the clock, was already wrong; Guzzle and Symfony HttpClient do not.
  - Another request's `curl_multi_select()` does wait for it, until its timeout or until a transfer has data: that `curl_multi_select()` returns on data for any transfer in the handle, the other request's included, and the next `curl_multi_exec()`, whichever request makes it, moves them all.

  Waiting calls on the same handle go in the order they started to wait, but one that is also waiting for a handle held elsewhere is passed by those that can go, the loop's own calls included. A call that has not had to wait goes ahead of them while the handles are free, unless it is a `curl_multi_select()` or a `curl_exec()`: a loop is suspended inside those, so that is where it lets a waiting call in, and a call suspended anywhere else would be suspended in the middle of the code that made it, as described next.

  `curl_multi_exec()` on a multi handle another request is in a call on does not wait at all. It returns `CURLM_OK` at once without moving any transfer, and sets `$still_running` to the number of easy handles added to it with `curl_multi_add_handle()` and not yet taken out, finished or not, so a loop goes on to its `curl_multi_select()` rather than ending; whichever request's `curl_multi_exec()` runs next moves every transfer in the handle. `curl_multi_errno()` is left with the code ext/curl last stored for the handle, which may be another request's: it stores the code of each `curl_multi_exec()` that goes into libcurl, but that of a `curl_multi_select()` only when it fails. The request learns what that did to its own transfer only from its next call after that `curl_multi_select()`, which still waits: first for its turn, behind the `curl_multi_select()` of each request that came before it, then for data on a transfer in the handle or its own timeout, 1 s in Guzzle and Symfony HttpClient. Each of those selects can last up to its timeout when the transfers left in the handle are idle, so a transfer finished meanwhile can be seen several timeouts later than it ended, about one for each request on the handle: with four requests on one multi handle, three of whose transfers ended together while the fourth's was idle, one of them saw its own 3 s late. An HTTP client may keep a flag over the code around its `curl_multi_exec()` that fails any request coming in while it is raised, as Symfony HttpClient's `CurlHttpClient` does ("Userland callback cannot use the client nor the response while processing"), so a request suspended inside that code would fail every other request using the client. A transfer callback that waits, an `on_progress` callback that sleeps under the `sleep` hooks say, still suspends its request there, as libcurl runs it from inside `curl_multi_exec()`. A loop that calls `curl_multi_exec()` again and again with no `curl_multi_select()` or other wait in between, which spins the CPU without the hook too, never lets the holder go on while it runs: it holds the thread it runs on until its request's `max_execution_time` ends it, and for good in an async task, which that bound does not reach.

  HTTP clients commonly keep one multi handle for the life of the client object: Guzzle for its asynchronous requests (`requestAsync()`, `Pool`), and Symfony HttpClient on ext/curl (`CurlHttpClient`) for all of them. Both pass `curl_multi_select()` a timeout of at most a second (Guzzle unless its `select_timeout` option, or the deprecated `GUZZLE_CURL_SELECT_TIMEOUT` environment variable it still reads when the option is absent, is set higher). In worker mode, where such a client is usually a service every request shares, each request adds its transfers while the others' are under way and the requests take turns calling on the handle, so their transfers run side by side.

  The turns run both ways, though: a loop's `curl_multi_select()` also waits for the call another request is in, so a loop that passes `curl_multi_select()` a timeout longer than the bound can make another request's `curl_multi_select()` throw. And a loop that makes its calls inside a fiber a userland scheduler started cannot stop to let a call in; it goes on, and the waiting call waits for the loop to end.
- `curl_pause()` cannot release a transfer another fiber is running with `curl_exec()`: it waits for `curl_exec()` to return, which a paused transfer never does, until the bound runs out. Unpause from the transfer's own callbacks, or run the transfer in a multi handle, where `curl_pause()` waits only for a call the loop driving it is in.

**An easy handle in a multi handle is held for longer: until it is taken out.** Its transfer is under way between the calls on the multi handle as well as inside them, and the loop driving it may be another request's, suspended between two calls while it runs other code, as an HTTP client is while it runs its promise callbacks. So the handle stays with the request or async task that added it with `curl_multi_add_handle()` until it is out again: taken out with `curl_multi_remove_handle()`, by any request, or out because the multi handle was closed or freed, or because the request or task that added it has ended. A call on the handle from anywhere else waits for that, within the same bound, since `curl_setopt()` would free a body that may still be being sent, and `curl_exec()` would empty the buffer the answer is being written to. `curl_multi_remove_handle()` does not wait for it, and neither do three calls made on a transfer under way, which Symfony HttpClient makes on the transfers of other requests sharing its multi handle: `curl_pause()`, and `curl_setopt()` of `CURLOPT_PRIVATE` or of `CURLOPT_VERBOSE`. Every call on the handle, these included, still waits for a call in progress on its multi handle. The transfer's callbacks run in whichever request drives the multi handle, or in the request whose `curl_pause()` lets go of data libcurl held back for a paused transfer, which it hands to the write callback before `curl_pause()` returns; their calls on the transfer's handle go ahead. A handle a server push adds (`CURLMOPT_PUSHFUNCTION`) is not held: it reaches the multi handle without a `curl_multi_add_handle()`, so a call on it waits only for a call in progress on that handle itself.

A share handle (`curl_share_init()`, and `curl_share_init_persistent()` on PHP 8.5) is not claimed. Transfers on handles that share one take turns on the worker thread, which is how libcurl expects a share handle to be used when no lock callbacks are set, and ext/curl sets none.
