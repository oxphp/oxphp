# 架构概览

OxPHP 是一个单二进制 HTTP 服务器，用于替代传统的 nginx + PHP-FPM 技术栈。它在单一进程中处理 HTTP 解析、TLS 终止、路由、PHP 执行、压缩和可观测性，运行时无需任何外部依赖。

## OxPHP 的工作原理

OxPHP 在单一进程中融合了两个运行时层：

1. **异步 HTTP 层** — 事件驱动的网络层，负责接受 TCP 连接、执行 TLS 握手、解析 HTTP 请求和发送响应。它使用非阻塞 I/O 处理数千个并发连接，一个慢速客户端永远不会阻塞其他客户端。
2. **PHP 工作进程池** — 一组专用的 PHP 工作进程执行您的 PHP 脚本。在标准模式下，每个工作进程一次处理一个请求。在启用了[纤程多路复用](../features/fiber-multiplexing.md)的[工作进程模式](../features/worker-mode.md)中，单个工作进程可以服务多个并发请求——当脚本调用 `oxphp_sleep()` 或 `oxphp_async_await()` 时，纤程让出线程，工作进程切换到下一个请求。
3. **异步池**（可选）— 用于处理通过 `oxphp_async()` 提交的任务的独立 OS 线程。通过设置 `ASYNC_WORKERS > 0` 启用。该池与工作进程池隔离，确保繁重的后台计算不会阻塞 HTTP 请求处理。

两层通过有界队列进行通信。当需要执行 PHP 的 HTTP 请求到达时，异步层将其放入队列。可用的 PHP 工作进程取出请求、执行脚本，并将响应返回给异步层以发送给客户端。

这种分离意味着网络 I/O——接受连接、读取头部、压缩响应、服务静态文件——永远不会与 PHP 执行竞争资源。每一层都可以独立扩展。

## 工作进程池

PHP 工作进程池决定了可以并发执行的 PHP 脚本数量。OxPHP 支持两种进程池模式。

### 静态进程池

在服务器启动时创建固定数量的工作进程，并在服务器整个生命周期内保持运行。这是默认模式。

```bash
PHP_WORKERS=8    # 恰好 8 个工作进程
PHP_WORKERS=0    # 自动检测（默认）：可用 CPU 核心数的一半，最少 1 个
```

### 动态进程池

工作进程根据需求自动扩缩容。用冒号分隔最小值和最大值：

```bash
PHP_WORKERS=2:16    # 从 2 个开始，负载高时扩展到 16 个
```

当所有当前工作进程均处于繁忙状态时，OxPHP 会创建新的工作进程直至上限。当工作进程空闲时间超过 `PHP_WORKERS_IDLE_SECONDS`（默认 30 秒）时，该工作进程会退出，向最小值收敛。

### 队列与背压

在异步 HTTP 层和工作进程池之间有一个有界队列。其容量默认为初始工作进程数乘以 128，可通过 `QUEUE_CAPACITY` 覆盖。对于静态进程池，初始数量是配置的工作进程数；对于动态进程池（`MIN:MAX`），初始数量是最小值。

到达时队列已满的请求不会被直接拒绝——它最多等待 `QUEUE_WAIT_TIMEOUT_MS`（默认 1000 毫秒）以获取空闲槽位，一旦工作进程取走排在它前面的请求便会入队。等待中的请求按到达顺序被接纳。该预算是请求到达时打上的单一截止时间，并随请求一同进入队列：工作进程取到它时若截止时间已过，则在取出时拒绝而不执行。这样预算限制的便是整段等待，而非其入队的那一半——这一点很重要，因为队列足够深，在慢速进程池上排到队尾所需的时间远超运维人员会设置的任何预算。因此负载是按实际等待时间而非请求到达瞬间的队列深度来削减的：微秒级即可排空的突发流量会被完整服务，而确实无法承载的进程池仍会削减负载。

该预算限制的是请求**进入**队列的等待时长，而非其全部等待时间。已被接纳的请求仍需在队列中等待工作进程处理，因此负载下的响应时间等于接纳等待 + 队列等待 + 执行时间——预算并不为后两项设置上限。

`QUEUE_MAX_WAITING` 限制同时等待的请求数（默认为初始工作进程数 × 128，上限为 `MAX_CONNECTIONS` 的一半）；超出后接纳将恢复为立即拒绝。等待并非零成本——等待中的请求在被接纳或预算耗尽之前，一直占用其连接以及已完整缓冲的请求体——因此若等待集合不设上限，持续过载会耗尽全部连接许可、阻塞 accept 循环，服务器将丢弃新连接而不是响应它们。默认值近似于进程池在预算内实际能够接纳的数量：超出该数量的等待只是推迟拒绝，同时继续占用这些资源。`MAX_CONNECTIONS` / 2 的上限正是让服务器仍能接受连接并给出拒绝的余量。请注意：两个取值都以连接数为单位，而消耗预算的是请求——HTTP/2 下一个连接可承载多个请求，因此以 h2 为主的部署只需一小部分连接预算即可触达上限，应显式设置 `QUEUE_MAX_WAITING`。

只有在等待预算耗尽后，OxPHP 才返回带 `Retry-After` 头部的 `529 Site is Overloaded` 响应。状态码 529（非标准，被 Cloudflare 等使用）将过载与应用错误（500）和维护（503）明确区分，便于配置告警和负载均衡器。设置 `QUEUE_WAIT_TIMEOUT_MS=0` 可禁用等待，队列满时立即拒绝。

由于等待中的请求占用的是连接而非队列槽位，过载时的并发上限由 `MAX_CONNECTIONS` 而非 `QUEUE_CAPACITY` 决定；在 HTTP/2 下则是 `MAX_CONNECTIONS` 与 `H2_MAX_CONCURRENT_STREAMS` 的乘积，因为每个流承载各自的请求。设置等待预算时应考虑这一点：请求进入队列时请求体已被读入内存，因此预算越大，真正过载的服务器在响应之前驻留在内存中的请求（连同其请求体）就越多。

## 请求流程

每个请求都经过相同的处理管道，无论是服务静态文件还是执行 PHP：

```text
客户端
  │
  ▼
TLS 终止（如已配置）
  │
  ▼
HTTP 解析 + 请求 ID 分配
  │
  ▼
受信任代理解析（TrustedProxyHandler -80）
  │
  ▼
限流检查
  │
  ▼
路由解析
  │
  ├── 静态文件 ──► 文件缓存 / 磁盘读取
  │                         │
  │                         ▼
  │                    压缩 + 响应头
  │                         │
  │                         ▼
  │                    响应返回客户端
  │
  └── PHP 请求 ──► 有界队列（满时返回 529）
                         │
                         ▼
                    PHP 工作进程执行脚本
                         │
                    ┌────┼─────────────────┐
                    ▼    ▼                 ▼
                 普通     SSE 流式传输    提前响应
                 响应     (chunked)      (finish_request)
                    │       │                │
                    ▼       ▼                ▼
                 压缩     分块 ──► 客户端  响应返回客户端
                    │                      + 后台工作
                    ▼
                 响应返回客户端
```

1. **TLS 终止** — 如果配置了 `TLS_CERT` 和 `TLS_KEY`，OxPHP 直接处理 TLS。无需单独的反向代理。
2. **HTTP 解析与请求 ID** — 解析请求并生成唯一请求 ID（或保留传入的 `X-Request-ID` 头部）。
3. **受信任代理解析** — 如果设置了 `TRUSTED_PROXIES`，OxPHP 检查连接 IP 是否受信任，并从 `Forwarded`（RFC 7239）或 `X-Forwarded-*` 头中提取真实客户端 IP、协议和主机名。使用 rightmost-non-trusted 算法防止 IP 欺骗。未设置时跳过此步骤。
4. **限流** — 如果设置了 `RATE_LIMIT`，将根据每 IP 请求计数器检查客户端 IP。超出限制的请求立即收到 `429 Too Many Requests` 响应。
5. **路由解析** — URL 与配置的路由模式（传统模式、框架模式或 SPA 模式）进行匹配。结果为静态文件、PHP 脚本或 404。工作进程模式（如已启用）改变 PHP 执行已解析脚本的方式，但本身不改变路由解析。
6. **静态文件** — 直接从内存缓存（高频访问文件）提供或从磁盘流式传输。OxPHP 自动添加 `ETag`、`Last-Modified` 和 `Cache-Control` 头部。
7. **PHP 执行** — 请求放入有界队列，由可用的工作进程取出。如果队列已满，客户端立即收到 529。
8. **压缩** — 当客户端发送 `Accept-Encoding: br` 时，基于文本的响应在发送前使用 Brotli 压缩（通过 `COMPRESSION_LEVEL` 配置）。
9. **SSE 流式传输** — 如果脚本设置了 `Content-Type: text/event-stream` 或调用了 `oxphp_stream_flush()`，OxPHP 切换到流式模式：每次 `flush()` 调用都会立即将分块发送给客户端，而不是缓冲整个响应。在工作进程模式下，SSE 与[纤程多路复用](../features/fiber-multiplexing.md)协作运行。
10. **提前响应** — 调用 `oxphp_finish_request()` 会立即将 HTTP 响应发送给客户端。脚本继续在后台执行——用于写入日志、更新缓存、发送通知——而不占用连接。
11. **响应发送** — 完成的响应通过连接发送回客户端，如果启用了[访问日志](../features/access-logging.md)，则触发日志记录。

## 工作进程模式与标准模式

OxPHP 支持两种 PHP 执行模型：

**标准模式**（默认）为每个请求创建全新的 PHP 环境。自动加载器、配置和数据库连接在每个请求时初始化，请求结束后销毁。此模式与所有 PHP 应用开箱即用兼容。

**工作进程模式**使 PHP 进程跨请求保持存活。您的应用只需引导一次——加载自动加载器、配置并建立数据库连接——然后进入请求循环。在请求之间，OxPHP 自动重置超全局变量、输出缓冲区和响应头，同时保留已引导的状态。

工作进程模式消除了每次请求的启动开销，对于引导成本较高的基于框架的应用（Laravel、Symfony 等）可以显著减少响应时间。

要启用工作进程模式，设置 `WORKER_MODE_ENABLED=true` 并将 `ENTRY_FILE` 指向一个调用 `oxphp_worker()` 的 PHP 脚本：

```php
<?php
require __DIR__ . '/../vendor/autoload.php';
$app = new MyApp\Application();

oxphp_worker(function () use ($app) {
    $app->handle();
});
```

详细指南请参见[工作进程模式](../features/worker-mode.md)。

## 内部服务器

如果设置了 `INTERNAL_ADDR` 变量，OxPHP 会在指定端口启动一个独立的 HTTP 服务器。它提供三个端点：

| 端点 | 描述 |
|------|------|
| `GET /health` | JSON 格式的健康状态（运行时间、请求计数器、连接数、工作进程状态）。正常运行时返回 `200`，降级时返回 `503`。 |
| `GET /metrics` | Prometheus 格式的指标——请求计数器、响应时间、队列等待时间、工作进程统计、压缩节省量。 |
| `GET /config` | JSON 格式的当前活跃配置快照。TLS 文件路径已隐藏。 |

内部服务器不经过 PHP 工作进程池和有界队列——它直接从异步 HTTP 层响应，因此即使 PHP 池完全满载也能保持可用。这使得 `/health` 适用于 Kubernetes 的存活/就绪探针。

详细信息请参见[内部服务器](../features/internal-server.md)。

## 安全保障

OxPHP 提供多项保障，确保您的应用在生产环境中稳定运行：

- **请求隔离** — 如果某个 PHP 脚本崩溃或触发致命错误，只有该单个请求受到影响。服务器继续正常处理所有其他请求。崩溃的工作进程会自动替换为新的工作进程。
- **工作进程自动重建** — OxPHP 监控所有 PHP 工作进程的健康状态。如果工作进程意外终止，无需人工干预即可启动新的工作进程替代它。
- **背压保护** — 有界请求队列防止过载。当服务器达到容量上限时，新请求收到 529 响应并附带 `Retry-After` 头部，而不是无限排队并导致级联超时。
- **路径遍历保护** — 所有 URL 路径在访问文件系统前均经过清理。百分比编码的遍历尝试、`..` 段以及逃出文档根目录的路径均被阻止。
- **优雅关闭** — 收到 SIGTERM 或 SIGINT（Ctrl+C）时，OxPHP 停止接受新连接，等待进行中的请求完成（最长等待可配置的排空超时时间），然后退出。
