OxPHP выпускае структураваны JSON-запіс журнала для кожнага завершанага HTTP-запыту. Журналы запісваюцца ў stdout з выкарыстаннем неблакіруючага фонавага запісвальніка, таму ўвод-вывад журналаў ніколі не блакіруе канвеер апрацоўкі запытаў.

## Канфігурацыя

| Пераменная | Апісанне | Па змаўчанні |
|------------|----------|--------------|
| `ACCESS_LOG` | Узровень журнала доступу: `all`, `error` або пустое/не зададзена (выкл.) | *(выкл.)* |
| `LOG_LEVEL` | Мінімальны ўзровень лагіравання (trace, debug, info, warn, error) | `info` |

Журнал доступу па змаўчанні выключаны. Задайце `ACCESS_LOG` для кіравання дэталізацыяй:

- **`all`** — лагіраваць кожны завершаны запыт (метад, шлях, статус, час)
- **`error`** — лагіраваць толькі памылкі (HTTP-статус >= 400: 404, 403, 500 і г.д.)
- **пустое/не зададзена** — журнал доступу адключаны

```bash
# Лагіраваць усе запыты
ACCESS_LOG=all

# Лагіраваць толькі памылкі (4xx/5xx)
ACCESS_LOG=error

# Адключыць журнал доступу (па змаўчанні)
# ACCESS_LOG=
```

Пераменная асяроддзя `RUST_LOG` таксама падтрымліваецца і мае прыярытэт над `LOG_LEVEL`, калі зададзена. Гэта адпавядае стандартнай канвенцыі `tracing`/`env_filter`.

## Фармат журнала

Кожны запіс журнала доступу — гэта адзін радок JSON, запісаны ў stdout:

```json
{
  "timestamp": "2026-02-11T12:34:56.789Z",
  "level": "INFO",
  "fields": {
    "request_id": "67890abc00000042",
    "method": "GET",
    "path": "/api/users",
    "status": 200,
    "duration_us": 1234,
    "remote_addr": "10.0.0.1:54321",
    "message": "request completed"
  }
}
```

### Палі

| Поле | Тып | Апісанне |
|------|-----|----------|
| `request_id` | string | Унікальны ідэнтыфікатар запыту (гл. [Ідэнтыфікатары запытаў](/be/features/request-ids/)) |
| `method` | string | HTTP-метад (`GET`, `POST` і г.д.) |
| `path` | string | Шлях URI запыту |
| `status` | number | Код стану HTTP-адказу |
| `duration_us` | number | Агульны час апрацоўкі запыту ў мікрасекундах |
| `remote_addr` | string | IP-адрас і порт кліента |

## Як гэта працуе

Журнал доступу рэалізаваны як апрацоўшчык падзей, які слухае падзеі `RequestComplete` з прыярытэтам **100** (запускаецца апошнім сярод апрацоўшчыкаў з аднолькавым прыярытэтам). Апрацоўшчык выклікае `tracing::info!` з мэтай `access_log`.

Інфраструктура лагіравання выкарыстоўвае:

- **tracing** для выпуску структураваных падзей
- **tracing-subscriber** з JSON-фарматаваннем для вываду
- **tracing-appender** з неблакіруючым запісвальнікам для асінхроннага ўводу-вываду

Неблакіруючы запісвальнік запускае асобны фонавы паток, які буферызуе запісы журнала і скідвае іх у stdout. `WorkerGuard`, які вяртаецца пры ініцыялізацыі, павінен утрымлівацца да завяршэння працы, каб забяспечыць скідванне ўсіх буферызаваных запісаў.

## Мэты журналавання

OxPHP выкарыстоўвае розныя мэты tracing для розных тыпаў журналаў:

- `access_log` -- запісы журнала доступу для кожнага запыту
- Мэта па змаўчанні -- падзеі жыццёвага цыклу сервера, памылкі, папярэджанні

Вы можаце выкарыстоўваць `RUST_LOG` для незалежнага кіравання імі:

```bash
# Паказваць журналы доступу на ўзроўні info, прыглушыць іншыя паведамленні ўзроўню info
RUST_LOG=warn,access_log=info
```

## Інтэграцыя з агрэгатарамі журналаў

Паколькі журналы — гэта JSON-радкі ў stdout, яны непасрэдна інтэгруюцца з драйверамі журналаў кантэйнераў і інструментамі агрэгацыі:

- **Docker**: збіраюцца аўтаматычна праз драйвер журналаў кантэйнера
- **Kubernetes**: падхопліваюцца агентам журналаў вузла (Fluentd, Fluent Bit і інш.)
- **journald**: захопліваюцца пры працы як сэрвіс systemd з лагіраваннем у stdout

Бакавы кантэйнер або перадача журналаў на аснове файлаў не патрэбныя.
