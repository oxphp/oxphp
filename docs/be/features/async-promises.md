---

OxPHP прадастаўляе API на аснове промісаў, які дазваляе PHP-коду адпраўляць замыканні для выканання на выдзеленым пуле патокаў, асобным ад пула HTTP-воркераў. Гэта забяспечвае сапраўднае паралельнае вылічэнне без блакіроўкі патоку запыту.

## Канфігурацыя

| Зменная | Па змаўчанні | Апісанне |
|----------|---------|-------------|
| `ASYNC_WORKERS` | `0` (выключана) | Колькасць выдзеленых патокаў асінхронных воркераў. `0` адключае асінхронны пул |
| `ASYNC_QUEUE_CAPACITY` | `ASYNC_WORKERS * 64` | Памер абмежаванага канала для чаканых асінхронных задач. Задачы адхіляюцца, калі канал поўны |

Для ўключэння асінхроннага пула:

```bash
ASYNC_WORKERS=4
```

Усталюйце `0` (або пакіньце без значэння), каб цалкам адключыць падтрымку асінхроннасці. Калі адключана, выклік `oxphp_async()` выдае `E_WARNING` і вяртае `false`.

## PHP API

### `oxphp_async`

Адпраўляе замыканне для асінхроннага выканання на пуле асінхронных воркераў.

```php
oxphp_async(Closure $closure, mixed ...$args): int|false
```

**Параметры:**

| Імя | Тып | Апісанне |
|------|------|-------------|
| `$closure` | `Closure` | Замыканне для асінхроннага выканання |
| `...$args` | `mixed` | Аргументы, якія перадаюцца ў замыканне праз глыбокую копію |

**Вяртаемае значэнне:** Ідэнтыфікатар проміса (дадатнае цэлае) пры поспеху або `false`, калі асінхронны пул не сканфігураваны або чарга поўная.

**Прыклад:**

```php
<?php
$promise = oxphp_async(function(int $n): int {
    return $n * $n;
}, 42);

$result = oxphp_async_await($promise);
// 1764
```

### `oxphp_async_await`

Блакуе бягучы паток да завяршэння асінхроннай задачы і вяртае вынік.

```php
oxphp_async_await(int $promise_id, ?float $timeout = null): mixed
```

**Параметры:**

| Імя | Тып | Па змаўчанні | Апісанне |
|------|------|---------|-------------|
| `$promise_id` | `int` | *(абавязкова)* | Ідэнтыфікатар проміса, вернуты `oxphp_async()` |
| `$timeout` | `?float` | `null` | Тайм-аўт у секундах. `null` чакае бясконца |

**Вяртаемае значэнне:** Вяртаемае значэнне замыкання.

**Выключэнні:**

| Выключэнне | Калі |
|-----------|------|
| `OxPHP\AsyncException` | Замыканне выклікала выключэнне або выклікала `die()`/`exit()` |
| `OxPHP\AsyncTimeoutException` | Тайм-аўт скончыўся да завяршэння задачы |

### `oxphp_async_await_all`

Чакае некалькі промісаў і вяртае ўсе вынікі ў выглядзе масіву.

```php
oxphp_async_await_all(array $promise_ids, ?float $timeout = null): array
```

**Параметры:**

| Імя | Тып | Па змаўчанні | Апісанне |
|------|------|---------|-------------|
| `$promise_ids` | `array` | *(абавязкова)* | Масіў ідэнтыфікатараў промісаў |
| `$timeout` | `?float` | `null` | Тайм-аўт у секундах для кожнага проміса |

**Вяртаемае значэнне:** Асацыятыўны масіў, які супастаўляе ідэнтыфікатары промісаў з іх вынікамі.

**Выключэнні:** `OxPHP\AsyncException` або `OxPHP\AsyncTimeoutException`, калі любы проміс завяршаецца з памылкай або перавышае тайм-аўт.

### `oxphp_async_await_any`

Спаборніцтва некалькіх промісаў — вяртае першы завершаны, незалежна ад парадку ў масіве. Унутрана выкарыстоўвае `futures::select_all` для сапраўднай семантыкі канкурэнтнага спаборніцтва. Промісы, якія не перамаглі, застаюцца даступнымі для чакання паасобку праз `oxphp_async_await()`.

```php
oxphp_async_await_any(array $promise_ids, ?float $timeout = null): array
```

**Параметры:**

| Імя | Тып | Па змаўчанні | Апісанне |
|------|------|---------|-------------|
| `$promise_ids` | `array` | *(абавязкова)* | Масіў ідэнтыфікатараў промісаў |
| `$timeout` | `?float` | `null` | Агульны тайм-аўт у секундах для завяршэння любога проміса |

**Вяртаемае значэнне:** Асацыятыўны масіў з ключамі `id` (ідэнтыфікатар проміса-пераможцы) і `value` (яго вынік).

**Выключэнні:** `OxPHP\AsyncException`, калі першы завершаны проміс выклікаў выключэнне. `OxPHP\AsyncTimeoutException`, калі ніводны проміс не завяршыўся ў межах тайм-аўту.

**Заўвага:** Пры тайм-аўце ўсе ўказаныя промісы скасоўваюцца і не могуць быць чаканыя паасобку пасля гэтага.

## Семантыка перадачы даных

Замыканні выконваюцца на іншым патоку АС з уласным станам PHP ZTS і `zend_mm_heap`. Даныя не могуць быць разалоўлены па ўказальніку паміж патокамі — любы ўказальнік на радок або масіў, выдзелены на кучы аднаго патоку, становіцца нядзейсным на іншым патоку. OxPHP выкарыстоўвае **партатыўную бінарную серыялізацыю** для бяспечнай перадачы ўсіх даных праз межы патокаў.

### Як гэта працуе

Усе значэнні, якія перасякаюць межы патокаў (аргументы, зменныя `use`, вяртаемыя значэнні), серыялізуюцца ў плоскі байтавы буфер з дапамогай сістэмнага `malloc`. Буфер перадаецца ў мэтавы паток, які дэсерыялізуе яго з дапамогай `emalloc` на ўласнай кучы. Гэта гарантуе, што кожнае PHP-выдзяленне памяці належыць правільнаму `zend_mm_heap` для кожнага патоку.

### Захопленыя зменныя (праз `use`)

Зменныя, захопленыя клаўзулай `use` замыкання, **серыялізуюцца** на зыходным патоку і **дэсерыялізуюцца** як незалежныя копіі на патоку асінхроннага воркера. Зыходныя зменныя застаюцца нязменнымі і цалкам даступнымі падчас асінхроннага выканання.

```php
<?php
$config = ['db' => 'mysql', 'timeout' => 30];

$p = oxphp_async(function() use ($config): string {
    // $config — незалежная копія — чытанне і запіс працуюць нармальна
    return $config['db'];
});

// $config застаецца запісваемым тут — ён быў скапіраваны, а не замарожаны
$config['timeout'] = 60; // бяспечна
$result = oxphp_async_await($p);
```

### Аргументы

Аргументы, перададзеныя праз `...$args`, серыялізуюцца і дэсерыялізуюцца тым жа спосабам. Падтрымліваемыя тыпы:

| Тып | Перадача |
|------|----------|
| `null`, `bool`, `int`, `float` | Серыялізуецца як значэнне (1–9 байтаў) |
| `string` | Серыялізуецца з прэфіксам даўжыні + дадзеныя |
| `array` | Рэкурсіўная серыялізацыя (ключы + значэнні) |
| `resource` | **Адхіляецца** — выклікае `OxPHP\AsyncException` |
| `object` | **Адхіляецца** — выклікае `OxPHP\AsyncException` (аб'екты не могуць быць серыялізаваны паміж патокамі) |

### Вяртаемыя значэнні

Вяртаемае значэнне замыкання серыялізуецца на патоку асінхроннага воркера і дэсерыялізуецца на зыходным патоку тым жа механізмам. Падтрымліваюцца ўсе скалярныя тыпы, радкі і масівы (уключаючы ўкладзеныя).

## Апрацоўка выключэнняў

Выключэнні, выкліканыя ўнутры асінхроннага замыкання, перахопліваюцца і паўторна выклікаюцца як `OxPHP\AsyncException` пры выкліку `oxphp_async_await()`. Арыгінальны клас і паведамленне выключэння захоўваюцца ў паведамленні `AsyncException`:

```php
<?php
$p = oxphp_async(function(): never {
    throw new \DomainException('invalid value', 422);
});

try {
    oxphp_async_await($p);
} catch (\OxPHP\AsyncException $e) {
    echo $e->getMessage();
    // "Async task failed: [DomainException] invalid value"
}
```

### die() і exit()

Выклікі `die()` або `exit()` унутры асінхронных замыканняў перахопліваюцца `zend_try`/`zend_catch` і пераўтвараюцца ў `OxPHP\AsyncException`. Пул асінхронных воркераў працягвае працаваць — наступныя задачы выконваюцца нармальна:

```php
<?php
// Раўнд 1: die() — перахоплена як AsyncException
$p1 = oxphp_async(function(): never { die('fatal'); });
try { oxphp_async_await($p1); } catch (\OxPHP\AsyncException $e) { /* апрацавана */ }

// Раўнд 2: пул жывы, звычайная задача працуе
$p2 = oxphp_async(function(): int { return 42; });
$result = oxphp_async_await($p2); // 42
```

### Класы выключэнняў

| Клас | Бацькоўскі | Калі |
|-------|--------|------|
| `OxPHP\AsyncException` | `Exception` | Замыканне выклікала выключэнне або быў выкліканы `die()`/`exit()` |
| `OxPHP\AsyncTimeoutException` | `OxPHP\AsyncException` | Тайм-аўт скончыўся да завяршэння задачы |

## Вобласць бачнасці і час жыцця промісаў

Промісы захоўваюцца ў **лакальным для патоку сховішчы** на патоку PHP-воркера, які іх стварыў. Гэта мае тры наступствы:

1. **Прывязка да патоку.** Проміс можа быць чаканы толькі тым жа патокам воркера, які выклікаў `oxphp_async()`. Іншы паток воркера мае ўласную карту промісаў і не бачыць чужых ідэнтыфікатараў.

2. **Прывязка да запыту.** У канцы кожнага запыту (RSHUTDOWN) усе невыкарыстаныя промісы аўтаматычна ачышчаюцца. У рэжыме воркера тая ж ачыстка выконваецца паміж запытамі. Промісы не могуць перажыць межы запытаў.

3. **Ідэнтыфікатары лакальныя для патоку, а не глабальна ўнікальныя.** Лічыльнік промісаў манатонна нарастае ўнутры патоку і не скідваецца паміж запытамі. Два розныя патокі воркераў могуць мець проміс з ідэнтыфікатарам `0` — гэта незалежныя промісы ў асобных картах.

```
Worker Thread #1                    Worker Thread #2
┌─ Request A ─────────────┐        ┌─ Request C ──────────┐
│ PROMISE_MAP: {0, 1, 2}  │        │ PROMISE_MAP: {0, 1}  │
│ await_any([0, 1]) → OK  │        │ await(0) → OK        │
│ await(2) → OK           │        │ await(1) → OK        │
│ RSHUTDOWN: cleanup      │        │ RSHUTDOWN: cleanup    │
├─ Request B ─────────────┤        └──────────────────────┘
│ PROMISE_MAP: {3, 4}     │  ← counter continues from 3
│ (not awaited)           │
│ RSHUTDOWN: cancel + free│  ← promises 3, 4 cleaned up
└─────────────────────────┘
```

Для абмену асінхроннымі вынікамі паміж запытамі выкарыстоўвайце знешні механізм (Redis, сумесная памяць, база даных).

## Ачыстка RSHUTDOWN

Калі PHP-запыт завяршаецца без чакання ўсіх адпраўленых промісаў, хук RSHUTDOWN аўтаматычна ачышчае невыкарыстаныя промісы. Кожнаму нечаканаму промісу даецца 5-секундны тайм-аўт для завяршэння, пасля чаго ён скасоўваецца. Гэта прадухіляе ўцечкі рэсурсаў ад забытых промісаў.

```php
<?php
$p1 = oxphp_async(function(): int { return 1; });
$p2 = oxphp_async(function(): int { return 2; });

$result = oxphp_async_await($p1);
// $p2 ніколі не чакаецца — ачышчаецца аўтаматычна ў канцы запыту
```

## Архітэктура

Асінхронны пул — гэта **асобны** набор патокаў АС ад пула HTTP PHP-воркераў. Гэтае раздзяленне прадухіляе дэдлокі: калі ўсе HTTP-воркеры адправілі асінхронныя задачы і потым заблакіраваліся на `oxphp_async_await()`, агульны пул прывёў бы да дэдлоку.

```
HTTP Worker Thread              Async Worker Thread
─────────────────              ────────────────────
oxphp_async($fn)
  ├─ serialize use-vars
  ├─ serialize args
  ├─ create AsyncTask           recv(AsyncTask)
  ├─ send via channel ──────►     ├─ oxphp_async_reset()
  │                               ├─ deserialize use-vars
  │                               ├─ deserialize args
  │                               ├─ oxphp_execute_async_task()
  │                               ├─ serialize retval
oxphp_async_await($id)                  ├─ send AsyncResult
  ├─ block on oneshot ◄──────     └─ free local data
  ├─ deserialize result
  └─ return value
```

Усе даныя, якія перасякаюць межы патокаў, праходзяць праз партатыўную бінарную серыялізацыю: серыялізацыя з дапамогай сістэмнага `malloc` на зыходным патоку, перадача буфера, дэсерыялізацыя з дапамогай `emalloc` на мэтавым патоку. Гэта гарантуе, што кожнае PHP-выдзяленне памяці належыць правільнаму `zend_mm_heap` для кожнага патоку.

Кожны паток асінхроннага воркера:
1. Ініцыялізуе TSRM (Zend Thread Safety) — лакальнае для патоку сховішча
2. Выклікае `php_request_startup()` адзін раз пры запуску патоку
3. Цыклічна: атрымлівае задачу → скідвае стан → дэсерыялізуе даныя → выконвае замыканне → серыялізуе вынік → адпраўляе
4. Выклікае `php_request_shutdown()` пры выхадзе

## Памер і наладка

Асінхронныя воркеры — гэта выдзеленыя патокі АС з поўнай ініцыялізацыяй PHP ZTS. Яны канкуруюць за ядры CPU з HTTP-воркерамі і рантаймам Tokio. Правільны падбор памераў прадухіляе канкурэнцыю за CPU і забяспечвае, каб асінхронныя задачы не выцяснялі апрацоўку HTTP-запытаў.

### Бюджэт патокаў

Агульная колькасць патокаў ва ўсіх пулах павінна заставацца ў межах колькасці ядраў CPU:

```
Total threads = TOKIO_WORKERS + PHP_WORKERS + ASYNC_WORKERS ≤ CPU cores
```

Перавышэнне гэтага бюджэту выклікае накладныя выдаткі на пераключэнне кантэксту, якія пагаршаюць прапускную здольнасць для ўсіх пулаў.

| 8-ядровы сервер | TOKIO | PHP | ASYNC | Усяго | Ацэнка |
|---------------|-------|-----|-------|-------|------------|
| Кансерватыўны | 4 | 4 | 2 | 10 | добра — нязначнае перавышэнне дапушчальна |
| Агрэсіўны | 4 | 4 | 4 | 12 | прымальна, калі асінхронныя задачы I/O-bound |
| Перавышаны | 4 | 8 | 8 | 20 | дрэнна — дамінуюць накладныя выдаткі на пераключэнне кантэксту |

### ASYNC_WORKERS па тыпу нагрузкі

Аптымальная колькасць залежыць ад таго, ці з'яўляюцца асінхронныя задачы CPU-bound або I/O-bound:

| Нагрузка | Формула | Абгрунтаванне |
|----------|---------|-----------|
| **CPU-bound** (вылічэнні, апрацоўка даных) | `CPU_cores / 4` | Большая колькасць патокаў не дапаможа — яны канкуруюць за тыя ж ядры, што і HTTP-воркеры |
| **I/O-bound** (sleep, сеткавыя выклікі, файлавы I/O) | `PHP_WORKERS` | Патокі бо́льшую частку часу заблакіраваны на I/O, не спажываюць CPU |
| **Змешаная** (тыповая) | `PHP_WORKERS / 2` | Пачніце адсюль, карэктуйце на аснове метрык |

### ASYNC_QUEUE_CAPACITY па патрабаваннях да затрымкі

Кожная задача ў чарзе ўтрымлівае серыялізаваныя аргументы ў памяці. Глыбіня чаргі — гэта кампраміс паміж памяццю, затрымкай і ўстойлівасцю да пікаў:

| Сцэнар | Рэкамендаваная ёмістасць | Абгрунтаванне |
|----------|---------------------|-----------|
| **Вэб-запыты** (чуллівыя да затрымкі) | `ASYNC_WORKERS * 4..8` | Адхіліць рана і адступіць на рэзерв, а не ставіць у чаргу і чакаць |
| **Фонавыя/пакетныя** (чуллівыя да прапускной здольнасці) | `ASYNC_WORKERS * 64` (па змаўчанні) | Дапушчальна буферызаваць задачы для пазнейшай апрацоўкі |

### Пазбяганне зацішша

Калі HTTP-воркер выклікае `oxphp_async_await()`, ён блакуецца да завяршэння асінхроннай задачы. Калі ўсе HTTP-воркеры заблакуюцца адначасова, а асінхронныя воркеры не паспяваюць, прапускная здольнасць запытаў падае да нуля.

Абмежаванне:

```
ASYNC_WORKERS ≥ max concurrent oxphp_async_await() callers
```

На практыцы ацаніце, якая доля HTTP-запытаў выкарыстоўвае асінхроннасць:

| Выкарыстанне async | Правіла памеру |
|-------------|-------------|
| Кожны запыт адпраўляе async | `ASYNC_WORKERS ≥ PHP_WORKERS` |
| ~30% запытаў | `ASYNC_WORKERS ≥ PHP_WORKERS / 3` |
| Рэдка (1 з 10) | `ASYNC_WORKERS ≥ PHP_WORKERS / 4` |

### Накладныя выдаткі на памяць

Кожны паток асінхроннага воркера спажывае:
- Стэк патоку АС: 2–8 МБ (залежыць ад платформы)
- Куча PHP ZTS: ~2–10 МБ (залежыць ад пашырэнняў і наладаў INI)
- Прыблізна ўсяго: **4–18 МБ на воркер**

Задачы ў чарзе дадаюць памяць для серыялізаваных аргументаў (залежыць ад памеру карыснай нагрузкі, звычайна невялікая).

### Прыклады канфігурацый

**8-ядровы сервер, Laravel, ~30% запытаў выкарыстоўваюць async:**

```bash
TOKIO_WORKERS=0           # auto: 4 (CPU/2)
PHP_WORKERS=4
ASYNC_WORKERS=2           # CPU/4, дастаткова для 30% async нагрузкі
ASYNC_QUEUE_CAPACITY=16   # нізкая затрымка: 2 * 8
```

**16-ядровы сервер, пакетная апрацоўка, кожны запыт разгаліноўвае:**

```bash
TOKIO_WORKERS=0           # auto: 8 (CPU/2)
PHP_WORKERS=6
ASYNC_WORKERS=6           # адпавядае PHP-воркерам — усе запыты выкарыстоўваюць async
ASYNC_QUEUE_CAPACITY=384  # 6 * 64, высокая прапускная здольнасць
```

**4-ядровы кантэйнер, рэдкія фонавыя задачы:**

```bash
TOKIO_WORKERS=1           # аднапатоковы, зберагае ядры для PHP
PHP_WORKERS=2
ASYNC_WORKERS=1           # мінімальна — async рэдкі
ASYNC_QUEUE_CAPACITY=8    # 1 * 8
```

### Маніторынг

Пасля разгортвання выкарыстоўвайце гэтыя запыты Prometheus для праверкі памераў:

```promql
# Задачы адхіляюцца? → павялічце ASYNC_QUEUE_CAPACITY або ASYNC_WORKERS
rate(oxphp_async_tasks_rejected_total[5m]) > 0

# Адставанне задач расце? → павялічце ASYNC_WORKERS
oxphp_async_tasks_dispatched_total
  - oxphp_async_tasks_completed_total
  - oxphp_async_tasks_failed_total
  - oxphp_async_tasks_cancelled_total

# CPU перанасычаны? → паменшыце ASYNC_WORKERS
# Правярайце сістэмныя метрыкі: load average, выкарыстанне CPU, steal time
```

## Метрыкі

Калі асінхронны пул актыўны (хаця б адна задача адпраўлена), выводзяцца пяць лічыльнікаў Prometheus:

| Метрыка | Тып | Апісанне |
|--------|------|-------------|
| `oxphp_async_tasks_dispatched_total` | counter | Агульная колькасць задач, адпраўленых праз `oxphp_async()` |
| `oxphp_async_tasks_completed_total` | counter | Задачы, якія паспяхова вярнулі значэнне |
| `oxphp_async_tasks_failed_total` | counter | Задачы, якія выклікалі выключэнне або `die()`/`exit()` |
| `oxphp_async_tasks_cancelled_total` | counter | Задачы, скасаваныя (тайм-аўт або ачыстка RSHUTDOWN) |
| `oxphp_async_tasks_rejected_total` | counter | Задачы, адхіленыя з-за поўнай асінхроннай чаргі |

Гэтыя лічыльнікі адсутнічаюць у вывадзе Prometheus, калі ніводная асінхронная задача не была адпраўлена і ніводная не была адхілена.

## Асяроддзе асінхроннага воркера

Асінхронныя воркеры — гэта **ізаляваныя PHP-рухавікі**. Кожны паток асінхроннага воркера запускае `php_request_startup()` адзін раз пры запуску патоку і потым цыклічна выконвае замыканні. У адрозненне ад HTTP-воркераў, асінхронныя воркеры **не** выконваюць код загрузкі вашага прыкладання — ні `vendor/autoload.php`, ні ініцыялізацыю фрэймворка, ні сэрвісны кантэйнер.

### Што працуе

| Катэгорыя | Прыклады |
|----------|---------|
| Убудаваныя функцыі PHP | `array_map`, `json_encode`, `preg_match`, `hash`, `mb_*`, `date` |
| Убудаваныя пашырэнні | `PDO` (стварыце новае злучэнне ўнутры замыкання), `curl_*`, `file_get_contents` |
| Чыстыя вылічэнні | Матэматыка, апрацоўка радкоў, маніпуляцыі з масівамі, пераўтварэнне даных |
| Скалярныя даныя праз `use` | `string`, `int`, `float`, `bool`, `array` (глыбокая копія) |

```php
<?php
// ✅ Працуе: стварэнне новага PDO-злучэння ўнутры замыкання
$dsn = 'mysql:host=127.0.0.1;dbname=app';
$user = 'root';
$pass = 'secret';

$p = oxphp_async(function() use ($dsn, $user, $pass): array {
    $pdo = new PDO($dsn, $user, $pass);
    return $pdo->query('SELECT count(*) FROM users')->fetch();
});
```

### Што НЕ працуе

| Катэгорыя | Чаму |
|----------|-----|
| `DB::connection()`, `app('cache')`, фасады | Сэрвісны кантэйнер не ініцыялізаваны — яны залежаць ад загрузкі Laravel |
| Аўтазагрузчык Composer | `vendor/autoload.php` не выкананы — класы па-за ўбудаванымі пашырэннямі не вызначаны |
| Мадэлі Eloquent, сутнасці Doctrine | Патрабуюць аўтазагрузчык + загрузку фрэймворка |
| `$_SERVER`, `$_GET`, `$_POST` | Суперглабалы не запоўнены на асінхронных воркерах — у іх няма кантэксту HTTP-запыту |
| Статычны стан з HTTP-воркера | `static`-уласцівасці класаў, глабальныя зменныя — кожны паток мае ўласную ZTS-копію |
| Аб'екты праз `use` | Аб'екты не могуць быць серыялізаваны паміж патокамі — выклікае `AsyncException` пры адпраўцы |

```php
<?php
// ❌ Не працуе: аўтазагрузчык недаступны, клас не знойдзены
$p = oxphp_async(function(): void {
    $user = User::find(1);  // Fatal: Class "User" not found
});

// ❌ Не працуе: сэрвісны кантэйнер не ініцыялізаваны
$p = oxphp_async(function(): void {
    $db = app('db');  // Fatal: Function "app" not found
});

// ❌ Не працуе: аб'екты не могуць перасекчы мяжу патокаў
$pdo = new PDO($dsn, $user, $pass);
$p = oxphp_async(function() use ($pdo): array {
    // AsyncException: Cannot pass object values in use-vars
    return $pdo->query('SELECT 1')->fetch();
});
```

### Абыходны шлях: перадавайце параметры злучэння, а не злучэнні

Паколькі аб'екты не могуць перасякаць межы патокаў, перадавайце сырыя параметры злучэння і ствараце злучэнні ўнутры замыкання:

```php
<?php
$config = [
    'dsn'  => 'mysql:host=127.0.0.1;dbname=app',
    'user' => 'root',
    'pass' => getenv('DB_PASSWORD'),
];

$promises = [];
foreach ($chunks as $chunk) {
    $promises[] = oxphp_async(function() use ($config, $chunk): int {
        // Кожны асінхронны воркер стварае ўласнае злучэнне
        $pdo = new PDO($config['dsn'], $config['user'], $config['pass']);
        $pdo->beginTransaction();
        foreach ($chunk as $row) {
            $pdo->prepare('UPDATE t SET v=? WHERE id=?')->execute([$row['v'], $row['id']]);
        }
        $pdo->commit();
        return count($chunk);
    }, $chunk);
}

$results = oxphp_async_await_all($promises);
$total = array_sum($results);
```

## Шаблоны выкарыстання

### Паралельныя вылічэнні

```php
<?php
// Адпраўка некалькіх CPU-bound задач
$promises = [];
foreach ($chunks as $i => $chunk) {
    $promises[$i] = oxphp_async(function() use ($chunk): array {
        return array_map('process_record', $chunk);
    });
}

// Збор усіх вынікаў
$results = oxphp_async_await_all($promises);
```

### Фонавая праца пасля адказу

```php
<?php
echo json_encode(['status' => 'accepted']);
oxphp_finish_request();

// Адказ адпраўлены — цяпер выконваем фонавую працу паралельна
$p1 = oxphp_async(function() use ($data): void { send_email($data); });
$p2 = oxphp_async(function() use ($data): void { update_analytics($data); });
oxphp_async_await_all([$p1, $p2]);
```

### Апрацоўка вынікаў у парадку завяршэння

Выкарыстоўвайце `oxphp_async_await_any()` у цыкле для апрацоўкі промісаў па меры іх завяршэння — найхутчэйшыя першымі:

```php
<?php
$promises = [
    oxphp_async(fn() => call_api_a()),  // 500ms
    oxphp_async(fn() => call_api_b()),  // 100ms
    oxphp_async(fn() => call_api_c()),  // 300ms
];

while (!empty($promises)) {
    $winner = oxphp_async_await_any($promises);
    process_result($winner['id'], $winner['value']);

    // Выдаляем пераможцу, працягваем спаборніцтва астатніх
    $promises = array_values(
        array_filter($promises, fn($id) => $id !== $winner['id'])
    );
}
// Парадак апрацоўкі: api_b (100ms), api_c (300ms), api_a (500ms)
```

Кожная ітэрацыя бярэ прымачоў з унутранай карты промісаў, спаборнічае з дапамогай `select_all`, вяртае пераможцу і кладзе астатніх прымачоў назад. Ніводны проміс не губляецца і не ўцякае — кожны ачышчаецца роўна адзін раз, калі перамагае.

### Абарона тайм-аўтам

```php
<?php
$p = oxphp_async(function(): array {
    return fetch_from_slow_api();
});

try {
    $result = oxphp_async_await($p, 2.0); // 2-секундны тайм-аўт
} catch (\OxPHP\AsyncTimeoutException $e) {
    $result = cached_fallback();
}
```
