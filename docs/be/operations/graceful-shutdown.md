---
title: Плаўная спынка
description: Як OxPHP апрацоўвае сігналы спынкі і адводзіць злучэнні
---

OxPHP рэалізуе плаўную спынку, каб забяспечыць завяршэнне запытаў, якія знаходзяцца ў апрацоўцы, перад завяршэннем працэсу. Гэта важна для разгортванняў без прастояў, паслядоўных абнаўленняў і аркестрацыі кантэйнераў.

## Апрацоўка сігналаў

OxPHP слухае два сігналы спынкі:

| Сігнал | Крыніца | Паводзіны |
|--------|--------|----------|
| `SIGTERM` | Аркестратары кантэйнераў, `kill`, `docker stop` | Ініцыюе плаўную спынку |
| `SIGINT` | Тэрмінал Ctrl+C | Ініцыюе плаўную спынку |

Абодва сігналы запускаюць аднолькавую паслядоўнасць спынкі. Першы атрыманы сігнал пачынае працэс адводу. Серверу не патрэбны другі сігнал для прымусовага завяршэння.

## Паслядоўнасць спынкі

Пры атрыманні сігналу спынкі апрацоўшчык сігналу запускае задачу, якая выконвае паслядоўнасць спынкі адначасова з цыклам прыёму, які ўсё яшчэ працуе. Цыкл прыёму працягвае апрацоўваць новыя злучэнні, пакуль не заўважыць сцяг спынкі:

1. **Запуск задачы спынкі** --- запускаецца задача Tokio, якая выклікае `plugin_manager.shutdown_all()`, а затым `server.shutdown()`. Гэтыя два выклікі выконваюцца паслядоўна ўнутры задачы, але сама задача выконваецца адначасова з цыклам прыёму.

2. **Спынка плагінаў** --- унутры запушчанай задачы спачатку выклікаецца `PluginManager::shutdown_all()`, якая спыняе плагіны ў адваротным парадку прыярытэтаў ад ініцыялізацыі.

3. **Спыненне прыёму злучэнняў** --- таксама ўнутры запушчанай задачы `server.shutdown()` усталёўвае сцяг `shutdown` праз `AtomicBool`. Цыкл прыёму выходзіць на наступнай ітэрацыі пасля таго, як заўважыць гэты сцяг.

4. **Адвод злучэнняў у апрацоўцы** --- сервер чакае завяршэння ўсіх актыўных злучэнняў, правяраючы кожныя 100 мс.

5. **Прымяненне тайм-аўту адводу** --- калі злучэнні ўсё яшчэ актыўныя пасля `DRAIN_TIMEOUT_SECONDS`, сервер лагіруе папярэджанне і працягвае спынку. Астатнія злучэнні скідваюцца.

6. **Спыненне ўнутранага сервера** --- задача сервера стану/метрык адмяняецца.

7. **Спынка PHP-выканаўцы** --- пры знішчэнні `SapiExecutor` ён закрывае канал запытаў, далучае ўсе патокі воркераў і выклікае `php_module_shutdown()`.

8. **Выхад** --- працэс завяршаецца з кодам стану 0.

```
SIGTERM атрыманы
  └── запуск задачы спынкі (выконваецца адначасова з цыклам прыёму)
        ├── plugin_manager.shutdown_all() (адваротны парадак прыярытэтаў)
        └── server.shutdown() (усталёўвае AtomicBool; цыкл прыёму выходзіць пры наступнай праверцы)
цыкл прыёму выходзіць пасля заўважэння сцяга спынкі
  ├── цыкл адводу (чаканне актыўных злучэнняў, апытанне кожныя 100 мс)
  │   ├── усе адведзены → "All connections drained"
  │   └── тайм-аўт дасягнуты → "Drain timeout reached, forcing shutdown"
  ├── спыненне ўнутранага сервера
  ├── знішчэнне выканаўцы (закрыццё канала, далучэнне воркераў, спынка PHP)
  └── выхад
```

## Канфігурацыя

| Зменная | Па змаўчанні | Апісанне |
|----------|---------|-------------|
| `DRAIN_TIMEOUT_SECONDS` | `30` | Максімум секунд для чакання завяршэння злучэнняў у апрацоўцы |
| `MAX_CONNECTIONS` | `10000` | Максімальная колькасць адначасовых злучэнняў (кантралюецца семафорам Tokio) |

### Выбар тайм-аўту адводу

Усталюйце `DRAIN_TIMEOUT_SECONDS` з улікам вашага самага павольнага чаканага запыту:

- **API-серверы** з хуткімі адказамі: `10`--`15` секунд
- **Праграмы** з загрузкай файлаў або працяглымі запытамі: `30`--`60` секунд
- **Канчатковыя кропкі пакетнай апрацоўкі**: адпавядаюць вашай найбольш працяглай чаканай аперацыі

У Kubernetes усталюйце `DRAIN_TIMEOUT_SECONDS` менш за `terminationGracePeriodSeconds` пада, каб адвод завяршыўся да таго, як kubelet адправіць `SIGKILL`:

```yaml
spec:
  terminationGracePeriodSeconds: 45
  containers:
    - name: oxphp
      env:
        - name: DRAIN_TIMEOUT_SECONDS
          value: "30"
```

## Абмежаванне злучэнняў

OxPHP выкарыстоўвае `Semaphore` з Tokio для прымянення абмежавання `MAX_CONNECTIONS`. Кожнае прынятае злучэнне набывае дазвол. Калі ўсе дазволы заняты, новыя злучэнні чакаюць у чарзе TCP, пакуль дазвол не вызваліцца.

### ConnectionGuard

Актыўныя злучэнні адсочваюцца праз шаблон RAII-аховы. Калі злучэнне прынята, `Metrics::connection_opened()` павялічвае лічыльнік актыўных злучэнняў. Калі `ConnectionGuard` знішчаецца (апрацоўшчык злучэння завяршаецца або задача адмяняецца), `Metrics::connection_closed()` аўтаматычна памяншае яго.

```
Прыём TCP
  ├── набыццё дазволу семафора
  ├── connection_opened() (павелічэнне лічыльніка)
  ├── абслугоўванне HTTP-запытаў (можа быць некалькі праз keep-alive)
  └── знішчэнне ConnectionGuard → connection_closed() (памяншэнне лічыльніка)
      └── знішчэнне дазволу (вызваленне слота семафора)
```

Гэта гарантуе, што лічыльнік заўсёды дакладны, нават калі злучэнні скідваюцца з-за памылак або тайм-аўтаў.

## Спынка PHP-воркераў

Калі `SapiExecutor` знішчаецца:

1. Глабальны сцяг спынкі ўсталёўваецца, сігналізуючы ScaleManager (калі працуе) спыніцца.
2. Адпраўнік канала запытаў знішчаецца, што прыводзіць да закрыцця абмежаванага канала.
3. Для кожнага воркера ўсталёўваецца індывідуальны сцяг спынкі, і асноўны паток далучае кожны воркер.
4. Воркеры ў статычным рэжыме бачаць закрыты канал пры наступным `recv()` і выходзяць. Воркеры ў дынамічным рэжыме бачаць альбо закрыты канал, альбо сцяг спынкі пры наступным `recv_timeout()`.
5. Пасля далучэння ўсіх воркераў выклікаюцца `php_module_shutdown()`, `sapi_shutdown()` і `tsrm_shutdown()` для карэктнага завяршэння рухавіка PHP.

Гэта азначае, што PHP-скрыпты ў працэсе выканання завяршаюцца. Ніводзін запыт не перарываецца на сярэдзіне выканання.

## Docker

Docker адпраўляе `SIGTERM` пры выкананні `docker stop`. Тайм-аўт спынкі Docker па змаўчанні складае 10 секунд, пасля чаго Docker адпраўляе `SIGKILL`.

Каб даць OxPHP дастаткова часу для адводу, павялічце тайм-аўт спынкі Docker:

```bash
docker stop --time 45 oxphp
```

Або ўсталюйце ў `docker-compose.yml`:

```yaml
services:
  oxphp:
    stop_grace_period: 45s
    environment:
      DRAIN_TIMEOUT_SECONDS: "30"
```

## Kubernetes

Для паслядоўных абнаўленняў у Kubernetes паслядоўнасць спынкі наступная:

1. Kubernetes адпраўляе `SIGTERM` паду.
2. Пад выдаляецца са спісу канчатковых кропак сэрвісу (праверка гатоўнасці пачынае фейліцца).
3. OxPHP адводзіць злучэнні ў апрацоўцы.
4. Калі пад усё яшчэ працуе пасля `terminationGracePeriodSeconds`, Kubernetes адпраўляе `SIGKILL`.

### Хук перад спынкай

Калі ваш сэрвіс атрымлівае трафік ад знешніх балансіроўшчыкаў нагрузкі, якія павольна распаўсюджваюць змены канчатковых кропак, дадайце хук перад спынкай для затрымкі:

```yaml
lifecycle:
  preStop:
    exec:
      command: ["sleep", "5"]
```

Гэта дае балансіроўшчыку нагрузкі час выдаліць пад з яго спісу мэтаў перад тым, як OxPHP спыніць прымаць злучэнні.

## Маніторынг спынкі

Сервер лагіруе структураваныя JSON-паведамленні падчас паслядоўнасці спынкі:

```json
{"level":"INFO","message":"Received shutdown signal, draining connections"}
{"level":"INFO","message":"Draining in-flight connections","active_connections":3}
{"level":"INFO","message":"All connections drained"}
{"level":"INFO","message":"Server stopped"}
```

Калі тайм-аўт адводу дасягнуты да завяршэння ўсіх злучэнняў:

```json
{"level":"WARN","message":"Drain timeout reached, forcing shutdown","remaining_connections":1}
```

Вы можаце выкарыстоўваць гэтыя лог-паведамленні для наладкі алертаў, калі сервер рэгулярна дасягае тайм-аўту адводу, што можа паказваць на неабходнасць павелічэння `DRAIN_TIMEOUT_SECONDS` або расследавання працяглых запытаў.
