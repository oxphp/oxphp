# Штатное завершение работы

OxPHP обрабатывает сигналы `SIGTERM` и `SIGINT`, чтобы активные запросы завершились до выхода из процесса. Это необходимо для развёртывания без простоев и скользящих обновлений в системах оркестрации контейнеров.

## Обработка сигналов

OxPHP реагирует на два сигнала завершения:

| Сигнал | Источник | Поведение |
|-------|--------|---------|
| `SIGTERM` | Оркестраторы контейнеров, `docker stop`, `kill` | Инициирует штатное завершение работы |
| `SIGINT` | Ctrl+C в терминале | Инициирует штатное завершение работы |

Оба сигнала запускают одинаковую последовательность завершения. Достаточно отправить первый сигнал — сервер немедленно начинает дренирование.

## Последовательность завершения

При получении сигнала завершения OxPHP выполняет следующие шаги:

1. **Прекращение приёма новых соединений** — сервер перестаёт принимать новые TCP-соединения на основном порту и останавливает плагины. PHP-воркеры продолжают работу для обработки активных запросов.
2. **Дренирование активных запросов** — активным соединениям разрешается завершить обработку. Сервер проверяет готовность каждые 100 мс. Внутренний сервер health/metrics остаётся доступным на протяжении всего дренирования, поэтому проверки готовности продолжают работать.
3. **Применение тайм-аута дренирования** — если соединения остаются активными после истечения `DRAIN_TIMEOUT_SECONDS`, сервер записывает предупреждение и продолжает завершение. Оставшиеся соединения разрываются.
4. **Остановка асинхронного пула** — фоновый пул асинхронных задач останавливается.
5. **Остановка внутреннего сервера** — сервер health/metrics останавливается после завершения дренирования.
6. **Выход** — процесс завершается с кодом 0.

> **Примечание:** PHP-воркеры неявно завершают работу при закрытии очереди запросов. Воркер-потоки завершаются после обработки текущего запроса.

## Конфигурация

| Переменная | По умолчанию | Описание |
|-----------|-------------|---------|
| `DRAIN_TIMEOUT_SECONDS` | `30` | Максимальное время в секундах ожидания завершения активных соединений перед принудительным завершением |

Задайте `DRAIN_TIMEOUT_SECONDS` с учётом самого медленного ожидаемого запроса:

- **API-серверы** с быстрыми ответами: `10`–`15` секунд
- **Приложения** с загрузкой файлов или долгими запросами: `30`–`60` секунд
- **Режим Worker** с фоновой обработкой: соответствуйте продолжительности самой долгой ожидаемой операции

## Kubernetes

В Kubernetes последовательность завершения при скользящем обновлении:

1. Kubernetes отправляет `SIGTERM` поду.
2. Под удаляется из списка эндпоинтов Service.
3. OxPHP дренирует активные соединения в течение `DRAIN_TIMEOUT_SECONDS`.
4. Если под всё ещё работает после `terminationGracePeriodSeconds`, Kubernetes отправляет `SIGKILL`.

Задайте `DRAIN_TIMEOUT_SECONDS` меньше `terminationGracePeriodSeconds`, чтобы дренирование завершилось до принудительного завершения:

```yaml
apiVersion: apps/v1
kind: Deployment
spec:
  template:
    spec:
      terminationGracePeriodSeconds: 45
      containers:
        - name: oxphp
          image: ghcr.io/oxphp/oxphp:0.1.0
          env:
            - name: DRAIN_TIMEOUT_SECONDS
              value: "30"
```

### Хук Pre-Stop

Если ваш сервис получает трафик от внешних балансировщиков нагрузки, которые медленно распространяют изменения эндпоинтов, добавьте хук pre-stop для задержки последовательности завершения:

```yaml
lifecycle:
  preStop:
    exec:
      command: ["sleep", "5"]
```

Это даёт балансировщику нагрузки время исключить под из целевого списка до того, как OxPHP прекратит принимать соединения.

## Docker

Docker отправляет `SIGTERM` при выполнении `docker stop`. Тайм-аут остановки по умолчанию составляет 10 секунд, после чего Docker отправляет `SIGKILL`.

Чтобы дать OxPHP достаточно времени для дренирования, увеличьте тайм-аут остановки:

```bash
docker stop --time 45 my-oxphp-container
```

Или задайте это в Compose-файле:

```yaml
services:
  oxphp:
    image: ghcr.io/oxphp/oxphp:0.1.0
    stop_grace_period: 45s
    environment:
      DRAIN_TIMEOUT_SECONDS: "30"
```

## Сообщения лога

При штатном завершении OxPHP выводит структурированные сообщения лога, которые можно отслеживать:

**Успешное дренирование:**

```json
{"level":"INFO","message":"Received shutdown signal, draining connections"}
{"level":"INFO","message":"Draining in-flight connections","active_connections":3}
{"level":"INFO","message":"All connections drained"}
{"level":"INFO","message":"Server stopped"}
```

**Достигнут тайм-аут дренирования:**

```json
{"level":"INFO","message":"Received shutdown signal, draining connections"}
{"level":"WARN","message":"Drain timeout reached, forcing shutdown","remaining_connections":1}
{"level":"INFO","message":"Server stopped"}
```

Если предупреждение «Drain timeout reached» появляется регулярно, увеличьте `DRAIN_TIMEOUT_SECONDS` или изучите долго выполняющиеся запросы с помощью гистограммы `oxphp_request_duration_us`.
