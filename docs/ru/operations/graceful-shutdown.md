# Штатное завершение работы

OxPHP обрабатывает сигналы `SIGTERM` и `SIGINT`, чтобы активные запросы завершились до выхода из процесса. Это необходимо для развёртывания без простоев и скользящих обновлений в системах оркестрации контейнеров.

## Обработка сигналов

OxPHP реагирует на два сигнала завершения:

| Сигнал | Источник | Поведение |
|-------|--------|---------|
| `SIGTERM` | Оркестраторы контейнеров, `docker stop`, `kill` | Инициирует штатное завершение работы |
| `SIGINT` | Ctrl+C в терминале | Инициирует штатное завершение работы |

Оба сигнала запускают одинаковую последовательность завершения. Достаточно отправить первый сигнал — сервер немедленно начинает дренирование.

## Последовательность завершения

При получении сигнала завершения OxPHP выполняет следующие шаги:

1. **Прекращение приёма новых соединений** — сервер перестаёт принимать новые TCP-соединения на основном порту. PHP-воркеры продолжают работу для обработки активных запросов.
2. **Свёртывание живых соединений** — клиенты HTTP/2 получают кадр `GOAWAY`, простаивающие keep-alive-соединения HTTP/1.1 закрываются, так что клиенты переходят на здоровый инстанс, а не мультиплексируют новые запросы в умирающий. Открытые потоки корректно завершаются сразу — потоковым считается любой ответ, уже начавший отдавать chunked-вывод, конечные загрузки так же, как SSE, — см. [Server-Sent Events](../features/sse.md#поведение-при-остановке).
3. **Дренирование активных запросов** — обычные активные запросы спокойно завершаются с полными ответами. Сервер проверяет готовность каждые 100 мс. Внутренний сервер health/metrics остаётся доступным на протяжении всего дренирования, поэтому проверки готовности продолжают работать. Работа, которую запрос продолжает после `oxphp_finish_request()`, тоже считается активной, хотя его соединение уже закрыто.
4. **Применение дедлайна дренирования** — запросы, всё ещё работающие по истечении `DRAIN_TIMEOUT_SECONDS`, отменяются (их колбэки `register_shutdown_function()` всё равно выполняются) и получают ~2 секунды на размотку, после чего сервер продолжает завершение.
5. **Сброс плагинов** — записи access-лога и APM-спаны, накопленные за окно дренирования, сбрасываются.
6. **Остановка асинхронного пула** — фоновый пул асинхронных задач останавливается.
7. **Остановка внутреннего сервера** — сервер health/metrics останавливается после завершения дренирования.
8. **Выход** — процесс завершается с кодом 0.

> **Примечание:** воркер-потоки PHP не останавливаются в начале последовательности — сигнал на выход и join приходят в самом конце, когда дренирование уже завершено и процесс идёт на выход. Именно поэтому дренирование обязано учитывать работу, всё ещё исполняющуюся на воркере, даже когда живых клиентских соединений не осталось.

## Конфигурация

| Переменная | По умолчанию | Описание |
|-----------|-------------|---------|
| `DRAIN_TIMEOUT_SECONDS` | `25` | Максимальное время в секундах, которое активные запросы получают на завершение до отмены; процесс выходит в течение ~2 секунд после дедлайна. Значение по умолчанию оставляет запас на размотку после дедлайна и сброс телеметрии внутри стандартных 30 секунд terminationGracePeriodSeconds в Kubernetes |

Задайте `DRAIN_TIMEOUT_SECONDS` с учётом самого медленного ожидаемого запроса:

- **API-серверы** с быстрыми ответами: `10`–`15` секунд
- **Приложения** с загрузкой файлов или долгими запросами: `30`–`60` секунд
- **Режим Worker** с фоновой обработкой: соответствуйте продолжительности самой долгой ожидаемой операции

## Kubernetes

В Kubernetes последовательность завершения при скользящем обновлении:

1. Kubernetes отправляет `SIGTERM` поду.
2. Под удаляется из списка эндпоинтов Service.
3. OxPHP дренирует активные соединения в течение `DRAIN_TIMEOUT_SECONDS`, затем отменяет отставшие запросы и выходит в течение ещё ~2 секунд.
4. Если под всё ещё работает после `terminationGracePeriodSeconds`, Kubernetes отправляет `SIGKILL`.

Задайте `terminationGracePeriodSeconds` выше `DRAIN_TIMEOUT_SECONDS` + 2, чтобы дренирование — включая размотку после дедлайна и сброс телеметрии — завершилось до принудительного завершения:

```yaml
apiVersion: apps/v1
kind: Deployment
spec:
  template:
    spec:
      terminationGracePeriodSeconds: 45
      containers:
        - name: oxphp
          image: ghcr.io/oxphp/oxphp:0.10.0
          env:
            - name: DRAIN_TIMEOUT_SECONDS
              value: "30"
```

### Хук Pre-Stop

Если ваш сервис получает трафик от внешних балансировщиков нагрузки, которые медленно распространяют изменения эндпоинтов, добавьте хук pre-stop для задержки последовательности завершения:

```yaml
lifecycle:
  preStop:
    exec:
      command: ["sleep", "5"]
```

Это даёт балансировщику нагрузки время исключить под из целевого списка до того, как OxPHP прекратит принимать соединения.

## Docker

Docker отправляет `SIGTERM` при выполнении `docker stop`. Тайм-аут остановки по умолчанию составляет 10 секунд, после чего Docker отправляет `SIGKILL`.

Чтобы дать OxPHP достаточно времени для дренирования, увеличьте тайм-аут остановки:

```bash
docker stop --time 45 my-oxphp-container
```

Или задайте это в Compose-файле:

```yaml
services:
  oxphp:
    image: ghcr.io/oxphp/oxphp:0.10.0
    stop_grace_period: 45s
    environment:
      DRAIN_TIMEOUT_SECONDS: "30"
```

## Сообщения лога

При штатном завершении OxPHP выводит структурированные сообщения лога, которые можно отслеживать:

**Успешное дренирование:**

```json
{"level":"INFO","message":"Received shutdown signal, draining connections"}
{"level":"INFO","message":"Draining in-flight connections","active_connections":3,"in_flight_requests":4}
{"level":"INFO","message":"All connections drained"}
{"level":"INFO","message":"Server stopped"}
```

Счётчики пересекаются, а не делят множество: `active_connections` — живые клиентские соединения, `in_flight_requests` — запросы, всё ещё исполняющиеся на PHP-воркерах, и запрос с живым соединением попадает в оба. Запрос, завершивший ответ досрочно через `oxphp_finish_request()`, виден только в `in_flight_requests` — его соединение уже закрыто, пока фоновая работа продолжается.

**Достигнут тайм-аут дренирования:**

```json
{"level":"INFO","message":"Received shutdown signal, draining connections"}
{"level":"WARN","message":"Drain timeout reached, cancelling in-flight requests","remaining_connections":1,"in_flight_requests":1}
{"level":"INFO","message":"All connections drained"}
{"level":"INFO","message":"Server stopped"}
```

Если предупреждение «Drain timeout reached» появляется регулярно, увеличьте `DRAIN_TIMEOUT_SECONDS` или изучите долго выполняющиеся запросы с помощью гистограммы `oxphp_request_duration_us`.
