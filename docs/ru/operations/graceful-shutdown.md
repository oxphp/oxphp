title: Плавная остановка
description: Как OxPHP обрабатывает сигналы завершения и дренирует соединения
---

OxPHP реализует плавную остановку для обеспечения завершения текущих запросов до выхода процесса. Это необходимо для деплоев без простоя, поэтапных обновлений и оркестрации контейнеров.

## Обработка сигналов

OxPHP слушает два сигнала завершения:

| Сигнал | Источник | Поведение |
|--------|----------|-----------|
| `SIGTERM` | Оркестраторы контейнеров, `kill`, `docker stop` | Инициирует плавную остановку |
| `SIGINT` | Ctrl+C в терминале | Инициирует плавную остановку |

Оба сигнала запускают одну и ту же последовательность остановки. Первый полученный сигнал начинает процесс дренирования. Серверу не требуется второй сигнал для принудительного завершения.

## Последовательность остановки

При получении сигнала завершения обработчик сигнала порождает задачу, которая выполняет последовательность остановки конкурентно с продолжающим работу циклом приёма соединений. Цикл приёма продолжает обрабатывать новые соединения до тех пор, пока не обнаружит флаг завершения:

1. **Порождение задачи остановки** --- порождается задача Tokio, которая последовательно вызывает `plugin_manager.shutdown_all()`, а затем `server.shutdown()`. Эти два вызова выполняются последовательно внутри задачи, но сама задача работает конкурентно с циклом приёма.

2. **Остановка плагинов** --- внутри порождённой задачи сначала вызывается `PluginManager::shutdown_all()`, плагины останавливаются в обратном порядке приоритетов инициализации.

3. **Прекращение приёма соединений** --- также внутри порождённой задачи `server.shutdown()` устанавливает флаг `shutdown` через `AtomicBool`. Цикл приёма завершается на следующей итерации после обнаружения этого флага.

4. **Дренирование текущих соединений** --- сервер ожидает завершения всех активных соединений, проверяя каждые 100 мс.

5. **Применение таймаута дренирования** --- если соединения всё ещё активны по истечении `DRAIN_TIMEOUT_SECS`, сервер записывает предупреждение в лог и продолжает остановку. Оставшиеся соединения закрываются принудительно.

6. **Прерывание внутреннего сервера** --- задача сервера проверки состояния/метрик отменяется.

7. **Остановка PHP-исполнителя** --- при уничтожении `SapiExecutor` закрывается канал запросов, присоединяются все потоки воркеров и вызывается `php_module_shutdown()`.

8. **Выход** --- процесс завершается с кодом 0.

```
SIGTERM получен
  └── порождение задачи остановки (работает конкурентно с циклом приёма)
        ├── plugin_manager.shutdown_all() (обратный порядок приоритетов)
        └── server.shutdown() (устанавливает AtomicBool; цикл приёма завершается при следующей проверке)
цикл приёма завершается после обнаружения флага завершения
  ├── цикл дренирования (ожидание активных соединений, опрос 100 мс)
  │   ├── все дренированы → "All connections drained"
  │   └── таймаут достигнут → "Drain timeout reached, forcing shutdown"
  ├── прерывание внутреннего сервера
  ├── уничтожение исполнителя (закрытие канала, присоединение воркеров, остановка PHP)
  └── выход
```

## Конфигурация

| Переменная | По умолчанию | Описание |
|------------|--------------|----------|
| `DRAIN_TIMEOUT_SECS` | `30` | Максимальное время ожидания завершения текущих соединений в секундах |
| `MAX_CONNECTIONS` | `10000` | Максимальное количество одновременных соединений (ограничивается семафором Tokio) |

### Выбор таймаута дренирования

Установите `DRAIN_TIMEOUT_SECS` с учётом самого медленного ожидаемого запроса:

- **API-серверы** с быстрыми ответами: `10`--`15` секунд
- **Приложения** с загрузкой файлов или длительными запросами: `30`--`60` секунд
- **Эндпоинты пакетной обработки**: установите в соответствии с самой длительной ожидаемой операцией

В Kubernetes установите `DRAIN_TIMEOUT_SECS` меньше, чем `terminationGracePeriodSeconds` пода, чтобы дренирование завершилось до отправки `SIGKILL` kubelet-ом:

```yaml
spec:
  terminationGracePeriodSeconds: 45
  containers:
    - name: oxphp
      env:
        - name: DRAIN_TIMEOUT_SECS
          value: "30"
```

## Ограничение соединений

OxPHP использует `Semaphore` из Tokio для применения лимита `MAX_CONNECTIONS`. Каждое принятое соединение получает разрешение. Когда все разрешения заняты, новые соединения ожидают в TCP-очереди до освобождения разрешения.

### ConnectionGuard

Активные соединения отслеживаются через паттерн RAII-защиты. При принятии соединения `Metrics::connection_opened()` увеличивает счётчик активных соединений. При уничтожении `ConnectionGuard` (обработчик соединения возвращается или задача отменяется) `Metrics::connection_closed()` автоматически уменьшает его.

```
TCP accept
  ├── получение разрешения семафора
  ├── connection_opened() (увеличение счётчика)
  ├── обслуживание HTTP-запросов (может быть несколько через keep-alive)
  └── уничтожение ConnectionGuard → connection_closed() (уменьшение счётчика)
      └── освобождение разрешения (освобождение слота семафора)
```

Это гарантирует точность счётчика даже при разрыве соединений из-за ошибок или таймаутов.

## Остановка PHP-воркеров

При уничтожении `SapiExecutor`:

1. Устанавливается глобальный флаг завершения, сигнализируя ScaleManager (если запущен) остановиться.
2. Отправитель канала запросов уничтожается, что приводит к закрытию ограниченного канала.
3. Для каждого воркера устанавливается поточный флаг завершения, и основной поток присоединяет каждый воркер.
4. Воркеры в статическом режиме обнаруживают закрытый канал при следующем `recv()` и завершаются. Воркеры в динамическом режиме обнаруживают либо закрытый канал, либо флаг завершения при следующем `recv_timeout()`.
5. После присоединения всех воркеров вызываются `php_module_shutdown()`, `sapi_shutdown()` и `tsrm_shutdown()` для корректной остановки PHP-движка.

Это означает, что PHP-скрипты, находящиеся в процессе выполнения, завершаются. Ни один запрос не прерывается на середине выполнения.

## Docker

Docker отправляет `SIGTERM` при выполнении `docker stop`. Таймаут остановки Docker по умолчанию составляет 10 секунд, после чего Docker отправляет `SIGKILL`.

Чтобы предоставить OxPHP достаточно времени для дренирования, увеличьте таймаут остановки Docker:

```bash
docker stop --time 45 oxphp
```

Или установите его в `docker-compose.yml`:

```yaml
services:
  oxphp:
    stop_grace_period: 45s
    environment:
      DRAIN_TIMEOUT_SECS: "30"
```

## Kubernetes

Для поэтапных обновлений в Kubernetes последовательность остановки выглядит так:

1. Kubernetes отправляет `SIGTERM` поду.
2. Pod удаляется из списка эндпоинтов Service (readiness probe начинает отказывать).
3. OxPHP дренирует текущие соединения.
4. Если pod всё ещё работает по истечении `terminationGracePeriodSeconds`, Kubernetes отправляет `SIGKILL`.

### Pre-Stop Hook

Если ваш сервис получает трафик от внешних балансировщиков нагрузки, которые медленно распространяют изменения эндпоинтов, добавьте pre-stop hook для задержки остановки:

```yaml
lifecycle:
  preStop:
    exec:
      command: ["sleep", "5"]
```

Это даёт балансировщику нагрузки время удалить pod из своего списка целей до того, как OxPHP прекратит приём соединений.

## Мониторинг остановки

Сервер записывает структурированные JSON-сообщения во время последовательности остановки:

```json
{"level":"INFO","message":"Received shutdown signal, draining connections"}
{"level":"INFO","message":"Draining in-flight connections","active_connections":3}
{"level":"INFO","message":"All connections drained"}
{"level":"INFO","message":"Server stopped"}
```

Если таймаут дренирования достигнут до завершения всех соединений:

```json
{"level":"WARN","message":"Drain timeout reached, forcing shutdown","remaining_connections":1}
```

Вы можете использовать эти лог-сообщения для настройки алертов, если сервер регулярно достигает таймаута дренирования, что может указывать на необходимость увеличения `DRAIN_TIMEOUT_SECS` или исследования длительных запросов.
