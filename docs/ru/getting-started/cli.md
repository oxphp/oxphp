# Интерфейс командной строки

У бинарника `oxphp` три роли: **serve** — запуск HTTP-сервера, **run** — выполнение одного PHP-скрипта до завершения и **config** — служебные утилиты. Голый `oxphp` без аргументов — это неявный `serve`, поэтому `CMD ["oxphp"]` в опубликованном образе по-прежнему запускает сервер без изменений.

```
USAGE:
    oxphp [OPTIONS]
    oxphp <COMMAND> [OPTIONS]
    oxphp serve [--user=<name|uid[:gid]>]
    oxphp run [-d key=value]... [--user=<spec>] <script.php> [args]...
    oxphp [-d key=value]... [--user=<spec>] <script.php> [args]...

OPTIONS:
    -h, --help      Print this help and exit
    -v, --version   Print version information and exit

COMMANDS:
    serve           Start the HTTP server (default; same as bare 'oxphp')
    run             Execute a single PHP script under CLI semantics and exit
    config          Configuration utilities (see 'oxphp config --help')
```

Роль выбирается по ключевому слову. Точные токены `serve`, `run` и `config` выбирают подкоманду; **любой другой первый позиционный аргумент трактуется как путь к скрипту** — так что `oxphp ./bin/migrate.php` — это сокращение для `oxphp run ./bin/migrate.php`. Эвристики по расширению нет: PHP выполняется по содержимому файла, поэтому скрипт без расширения тоже запускается. Об отсутствующем файле сообщает файловая система, ровно как у `php`.

## `oxphp serve`

Запускает HTTP-сервер приложений — это роль по умолчанию. `oxphp` и `oxphp serve` эквивалентны. Конфигурация задаётся через [переменные окружения](../operations/configuration.md); сам `serve` принимает только `--user`.

```bash
oxphp                 # implicit serve
oxphp serve           # explicit
oxphp serve --user=www-data
```

`--user` привязывает листенеры от имени стартового пользователя (root, чтобы можно было занять порты ниже 1024), а затем безвозвратно сбрасывает привилегии до целевого пользователя до того, как будет обслужен хоть один запрос. Полный паттерн, грамматику `<spec>` и чек-лист прав доступа к файлам см. в разделе [Запуск без root на порту 80](docker.md#запуск-без-root-на-порту-80-serve---user).

## `oxphp run`

`oxphp run <script.php> [args…]` выполняет один PHP-файл до завершения и выходит с собственным кодом возврата скрипта. Он работает в главном потоке — нет ни листенера, ни пула воркеров, ни очереди запросов. `PHP_SAPI === 'cli'`, и `phpinfo()` печатает текст, а не HTML, как у штатного `php` CLI.

```bash
oxphp run migrate.php
oxphp run bin/console.php cache:clear
oxphp run -d memory_limit=512M import.php data.csv
```

Это та роль, которую стоит использовать для миграций, cron-задач, потребителей очередей и команд в духе `artisan`/`console` — в **том же образе**, что обслуживает ваше приложение, без второй установки PHP.

Под скриптом доступен весь движок OxPHP: [файберы](../features/fiber-multiplexing.md) (`oxphp_sleep()`) и [разделяемое состояние](../shared-state/shared-state.md) (`OxPHP\Shared\*`) работают из коробки. [Асинхронные промисы](../features/async-promises.md) (`oxphp_async()`) работают, когда `ASYNC_WORKERS` больше `0`; вызов по умолчанию не запускает async-пул, а значит и фоновую среду выполнения.

`$argv` и `$argc` заполнены (`$argv[0]` — путь к скрипту), а `STDIN` / `STDOUT` / `STDERR` определены, поэтому точки входа в стиле Composer и Symfony Console работают без изменений.

**Путь к скрипту — это разделитель.** Каждый токен после него передаётся в PHP дословно — включая токены с префиксом `--`, — поэтому явный `--` вводить никогда не нужно. Флаги, предназначенные самому `oxphp` (`-d`, `--user`), должны идти *перед* путём к скрипту; всё, что после него, принадлежит скрипту.

```bash
oxphp run console.php migrate --force --pretend
#            ▲ script  └──────────────┬──────────┘
#                        $argv[1..], passed to PHP verbatim (oxphp parses nothing here)
```

Так, `oxphp run console.php --force` отдаёт скрипту `--force` в `$argv`, тогда как `oxphp run --force console.php` — это ошибка: `--force` идёт перед путём к скрипту, где `oxphp` принимает только `-d` / `--user` / `--help`.

### Маркер конца опций `--`

`oxphp` поддерживает стандартный маркер конца опций `--`, и он важен ровно в одном месте: **перед путём к скрипту**, когда сам путь к скрипту начинается с дефиса. `--` останавливает разбор опций, поэтому следующий токен берётся как путь к скрипту, и `oxphp` его поглощает — в PHP он не передаётся.

```bash
oxphp run -- -odd-name.php      # runs the script "-odd-name.php"
oxphp -- -odd-name.php          # same, implicit form
oxphp run -odd-name.php         # error: parsed as options → "unexpected argument to 'run': -o"
```

После пути к скрипту опций, которые нужно было бы завершать, уже не остаётся, поэтому `--` там — это обычные данные, и он передаётся в PHP буквально, ровно как у `php`:

```bash
oxphp run app.php -- --raw      # $argv = ["app.php", "--", "--raw"]
```

### Shebang-скрипты

Ведущая строка `#!` пропускается перед компиляцией, поэтому исполняемый скрипт без расширения с shebang'ом `oxphp` запускается напрямую:

```php
#!/usr/bin/env oxphp
<?php
echo "hello from a shebang script\n";
```

```bash
chmod +x ./greet
./greet
```

### Переопределения ini через `-d`

`-d key[=value]` задаёт директиву `php.ini` для этого запуска. Флаг можно повторять, а голый `-d key` устанавливает значение `"1"`. Эти переопределения применяются до старта модулей, поэтому они выигрывают у `php.ini` для **любого** типа директив — включая директивы `PHP_INI_SYSTEM` / `PHP_INI_PERDIR` (`opcache.*`, `register_argc_argv`, …), которые рантаймовый `ini_set()` изменить не может.

```bash
oxphp run -d memory_limit=1G -d display_errors=1 report.php
```

### Ini по умолчанию для `run`

Роль `run` применяет CLI-ориентированные значения по умолчанию до ваших переопределений через `-d` и до `php.ini`:

| Директива | По умолчанию | Зачем |
|---|---|---|
| `max_execution_time` | `0` | Разовая задача (миграция, импортёр, демон) не должна убиваться `SIGALRM`. |
| `max_input_time` | `-1` | Для CLI нет дедлайна на разбор ввода. |
| `display_errors` | `stderr` | Ошибки идут в стандартный поток ошибок, а не в стандартный вывод. |
| `html_errors` | `0` | Ошибки в виде простого текста для терминала. |
| `output_buffering` | `0` | Вывод пишется по мере его формирования. |
| `implicit_flush` | `1` | Каждая запись немедленно сбрасывается. |
| `register_argc_argv` | `1` | Доступны `$argv` / `$argc`. |

[Суперглобальные переменные](../php/superglobals.md) для `run` всегда включены — разовому скрипту нужны `$argv`, `$_SERVER` и `$_ENV` — независимо от переключателя `SUPERGLOBALS_ENABLED`, который применяется к HTTP-серверу.

### Коды возврата

| Код | Значение |
|---|---|
| собственный код скрипта | `exit($code)` / `die($code)` либо `0` при чистом завершении. |
| `255` | Фатальная ошибка, непойманное исключение или ошибка парсинга. |
| `1` | Не удалось открыть путь к скрипту (`oxphp: Could not open input file: <path>`). |
| `2` | Некорректный аргумент `-d`. |

Случай с неоткрываемым файлом проверяется до старта движка, поэтому отсутствующий или нечитаемый скрипт падает сразу с сообщением в стиле `php`, а не раскручивает движок, чтобы упасть с ошибкой компиляции.

### `--user` на пути run

`oxphp run --user=<spec> <script.php>` сбрасывает привилегии ОС до выполнения скрипта, поэтому разовая задача, запущенная от root, может выполняться от непривилегированного пользователя. Грамматика `<spec>` и механика сброса идентичны [`serve --user`](docker.md#запуск-без-root-на-порту-80-serve---user); запуск от имени не-root с `--user` — это жёсткая ошибка.

## `oxphp config`

Служебные утилиты конфигурации. `--check` валидирует конфигурацию из переменных окружения и сообщает о проблемах, не запуская сервер.

```bash
oxphp config --check
```

```
config: OK
```

Проверка охватывает только корректность файловой системы — существование путей и тип файла/каталога (`DOCUMENT_ROOT`, `ENTRY_FILE`, `TLS_CERT`, `TLS_KEY`, `ERROR_PAGES_DIR`, …). PHP-рантайм, TLS-handshake и сетевой bind вне её охвата. При неудачной валидации она завершается с ненулевым кодом и печатает `config: INVALID` с одной строкой на каждую проблему, что делает её пригодной как пред-стартовый гейт в entrypoint или CI-задаче.

## `--help` и `--version`

```bash
oxphp --help            # full usage
oxphp config --help     # config subcommand usage
oxphp --version         # version and the feature flags compiled into this binary
```

`oxphp --version` сообщает включённые в сборке возможности (например, `php, plugin-apm, plugin-async`), что является самым быстрым способом подтвердить, собран ли образ с APM, async или другими опциональными плагинами.
