# Deny-лист выполнения PHP

`PHP_DENY_PATHS` запрещает прямое выполнение `.php`-файлов, попадающих под заданные glob-паттерны. Это закрывает повторяющийся класс уязвимостей в унаследованных PHP-приложениях: атакующий загружает PHP-файл в публичный каталог с правом записи (`/uploads`, `/cache`, временные каталоги ресайза изображений) и обращается к нему напрямую по URI, получая выполнение кода.

Проверка выполняется **до любого обращения к диску**, поэтому запрещённые пути возвращают одинаковый ответ независимо от наличия файла на диске — атакующий не может использовать deny-лист как existence oracle для перебора имён залитых файлов.

## Когда работает

Только в режиме direct-mapping. При заданной `ENTRY_FILE` (Framework, SPA или Worker) каждый запрос уже маршрутизируется через один доверенный entry-скрипт — произвольные `.php`-файлы в `DOCUMENT_ROOT` нельзя вызвать напрямую, поэтому deny-лист избыточен. Установка `PHP_DENY_PATHS` вместе с `ENTRY_FILE` приводит к startup-warning и отключению проверки.

| Режим маршрутизации | `PHP_DENY_PATHS` учитывается? |
|---|---|
| Traditional (без `ENTRY_FILE`) | Да |
| Framework (`ENTRY_FILE=index.php`) | Нет — warning, игнорируется |
| SPA (`ENTRY_FILE=index.html`) | Нет — warning, игнорируется |
| Worker (`WORKER_MODE_ENABLED=true`) | Нет — warning, игнорируется |

## Конфигурация

```bash
# Glob-паттерны через запятую
PHP_DENY_PATHS="/uploads/**,/cache/**,/tmp/**"

# Что возвращать при совпадении (по умолчанию: 404)
PHP_DENY_FALLBACK="403"
```

Запрос к `/uploads/shell.php` теперь вернёт 403 без обращения к диску. Запрос к `/uploads/image.png` обслуживается как обычно — deny-лист влияет только на выполнение `.php`, статика отдаётся без изменений.

## Синтаксис паттернов

Паттерны сопоставляются с санитизированным URI (путь запроса с уже разрешёнными `..`-сегментами и процентным кодированием) по синтаксису `globset`. Ведущий `/` в каждом паттерне опционален — `/uploads/**` и `uploads/**` эквивалентны.

| Паттерн | Совпадает | Не совпадает |
|---|---|---|
| `/uploads/**` | `/uploads/x.php`, `/uploads/a/b/c.php`, `/uploads/shell.php/extra` | `/uploads.php`, `/public/uploads/x.php` |
| `/files/*.php` | `/files/x.php` | `/files/sub/x.php` (один `*` не пересекает `/`) |
| `/admin/legacy.php` | `/admin/legacy.php` | `/admin/legacy.php/x` (PATH_INFO не покрыт — см. ниже) |
| `/admin/legacy.php{,/**}` | `/admin/legacy.php`, `/admin/legacy.php/x` | `/admin/other.php` |
| `/**/wp-config.php` | `/wp-config.php`, `/site/wp-config.php` | `/wp-config.txt` |

Несколько паттернов объединяются через OR — запрос попадает под deny-лист, если совпадает хотя бы с одним паттерном.

### Отдельные файлы vs директории

Работают оба варианта. `/uploads/**` блокирует целое поддерево; `/admin/legacy.php` — один конкретный скрипт. Чтобы закрыть и единичный entry-point, и PATH_INFO-вызовы (`/admin/legacy.php/foo`), используйте brace-форму: `/admin/legacy.php{,/**}`.

### Чувствительность к регистру

Сопоставление **регистрозависимое**. На регистронечувствительных файловых системах (macOS HFS+/APFS по умолчанию, NTFS на Windows по умолчанию, ext4 с `casefold`) запрос к `/uploads/Shell.PHP` обойдёт паттерн вида `/uploads/**/*.php`. Используйте широкий директорный паттерн `/uploads/**` (захватывает любые расширения), либо нормализуйте имена загружаемых файлов к нижнему регистру при записи.

## Режимы fallback

`PHP_DENY_FALLBACK` управляет тем, что возвращается при совпадении.

### HTTP-статус

Любое значение `400`–`599` (по умолчанию `404`). Сочетается с `ERROR_PAGES_DIR` для кастомного HTML-тела:

```bash
PHP_DENY_PATHS="/uploads/**"
PHP_DENY_FALLBACK="403"
ERROR_PAGES_DIR="/var/www/errors"  # отдаёт errors/403.html
```

### PHP-скрипт

URI-путь с ведущим `/` к fallback-скрипту внутри `DOCUMENT_ROOT`:

```bash
PHP_DENY_PATHS="/uploads/**"
PHP_DENY_FALLBACK="/_security/denied.php"
```

Скрипт валидируется при запуске — он должен существовать, канонический путь должен быть внутри `DOCUMENT_ROOT`, и сам скрипт не должен попадать под `PHP_DENY_PATHS` (защита от зацикливания; иначе старт прерывается). Скрипт получает два дополнительных ключа в `$_SERVER`, идентифицирующих исходный запрос:

| Ключ `$_SERVER` | Значение |
|---|---|
| `OXPHP_DENIED_PATH` | Исходный санитизированный URI, с ведущим `/` (тот же вид, что и `PATH_INFO`) |
| `OXPHP_DENIED_PATTERN` | Совпавший glob-паттерн |

`OXPHP_DENIED_PATTERN` хранится **без** ведущего `/` (нормализован как glob), а `OXPHP_DENIED_PATH` сохраняет `/` из URI запроса. Если сравниваете путь с паттерном, сначала сделайте `ltrim($_SERVER['OXPHP_DENIED_PATH'], '/')`, чтобы оба были в одном виде.

Пример honeypot:

```php
<?php
// /_security/denied.php — выполняется вместо любого заматченного .php-запроса.
error_log(sprintf(
    "PHP execution denied: path=%s pattern=%s ip=%s ua=%s",
    $_SERVER['OXPHP_DENIED_PATH'] ?? '',
    $_SERVER['OXPHP_DENIED_PATTERN'] ?? '',
    $_SERVER['REMOTE_ADDR'] ?? '',
    $_SERVER['HTTP_USER_AGENT'] ?? '-',
));

http_response_code(404);
echo "Not Found";
```

Так можно решать как отвечать на каждый конкретный запрос (404 атакующим, 403 авторизованным админам, редирект сканеров в sinkhole) вместо одного статичного статуса.

## Нет existence oracle

И статусный, и скриптовый fallback возвращаются без обращения к файловой системе. Запрос к `/uploads/never-uploaded.php` и запрос к `/uploads/actually-on-disk.php` дают идентичные ответы — нет ни различия по времени, ни различия в теле. Атакующий, сканирующий залитые шеллы, не может использовать deny-лист для перебора реальных имён файлов.

## Наблюдаемость

| Метрика | Описание |
|---|---|
| `oxphp_php_deny_total` | Счётчик, инкрементируется при каждом запрещённом запросе |

Каждое блокирование также пишет `tracing::info`-лог:

```
PHP execution denied by PHP_DENY_PATHS path=uploads/shell.php pattern=uploads/**
```

Access-логи фиксируют итоговый статус (значение `PHP_DENY_FALLBACK` или `http_response_code()` от fallback-скрипта) — на уровне access-лога запрещённые запросы не отличаются от обычных. Для атрибуции всплесков сверяйтесь с метрикой или структурированным логом.

## Производительность

Сопоставление — это lookup в `globset::GlobSet`, обычно один SIMD-проход по байтам URI. Совпадение также обходит кэш роутера (запрещённые URI приходят от спрея атакующего с фактически неограниченной кардинальностью; кэширование позволило бы вытеснить из LRU легитимные записи). И hit-, и miss-пути после прогрева не делают аллокаций.

## Ограничения

Честный список того, что эта фича *не* делает:

- **PATH_INFO bypass для литеральных файловых паттернов.** Паттерн `/admin/legacy.php` не совпадает с `/admin/legacy.php/extra`. Используйте `/admin/legacy.php{,/**}` чтобы покрыть оба случая, либо директорный паттерн.
- **Регистрозависимое сопоставление** (см. [Чувствительность к регистру](#чувствительность-к-регистру) выше).
- **Нет regex.** Только globs — якорные, с операторами `*`/`**`/`?`/`[abc]`/`{a,b}`. Вместо `(a|b)` используйте несколько паттернов через запятую.
- **Не влияет на `include` / `require` / `eval`.** Deny-лист управляет только *прямым* выполнением через URI. Уязвимый скрипт с `include $_GET['page']` всё равно может загрузить PHP из любого читаемого сервером места.

## Устаревший алиас

Старая переменная `PHP_DENY_DIRS` принимается как deprecated-алиас и выводит startup-warning:

```
WARN PHP_DENY_DIRS is deprecated, use PHP_DENY_PATHS instead — the alias will be removed in a future release
```

При наличии обеих `PHP_DENY_PATHS` имеет приоритет, а `PHP_DENY_DIRS` отмечается как игнорируемая. Значения не объединяются.
