# Режим воркера

Режим воркера запускает постоянные PHP-процессы, которые инициализируются один раз и обрабатывают множество запросов, устраняя накладные расходы на запуск для каждого запроса. Вместо сброса и восстановления состояния PHP при каждом запросе ваше приложение загружает автозагрузчик, конфигурацию и соединения с базой данных единожды и повторно использует их на протяжении всего времени жизни воркера.

## Как это работает

1. **Установите `WORKER_FILE`** в путь к вашему скрипту начальной загрузки. Это включает режим воркера для всех PHP-воркеров в пуле.
2. **PHP запускается и выполняет внешнюю область видимости один раз** — регистрация автозагрузчика, загрузка конфигурации, соединения с базой данных и любой другой инициализирующий код выполняются однократно.
3. **Вызовите `oxphp_worker(callback)`** для входа в цикл обработки запросов. OxPHP начинает диспетчеризацию входящих HTTP-запросов в ваш обратный вызов.
4. **Между запросами** суперглобальные переменные (`$_GET`, `$_POST`, `$_SERVER`, `$_COOKIE`, `$_FILES`, `php://input`), буферы вывода и заголовки ответов автоматически сбрасываются. Мягкий сброс очищает состояние запроса, сохраняя загруженные ресурсы во внешней области видимости.
5. **Внешняя область видимости сохраняется** — переменные, определённые до `oxphp_worker()`, статические свойства, соединения с базой данных и автозагрузчики остаются доступными для всех запросов, обрабатываемых этим воркером.

> **Примечание:** Установка `WORKER_FILE` также изменяет поведение маршрутизации. Все запросы, не соответствующие статическому файлу на диске, направляются воркеру вместо возврата 404. Подробности см. в разделе [Маршрутизация](routing.md).

## Конфигурация

| Переменная | По умолчанию | Описание |
|------------|--------------|----------|
| `WORKER_FILE` | *(не задана)* | Путь к PHP-скрипту воркера. Установка этой переменной включает режим воркера |
| `WORKER_MAX_REQUESTS` | `0` | Максимальное количество запросов, которые воркер обрабатывает до перезапуска. `0` = без ограничений |
| `WORKER_MAX_MEMORY_MIB` | `0` | Максимальный объём PHP-памяти на воркер в МиБ до перезапуска. `0` = без ограничений |

## Написание скрипта воркера

Скрипт воркера состоит из двух частей: внешней области видимости, выполняемой один раз при запуске, и обратного вызова, передаваемого в `oxphp_worker()`, который выполняется при каждом запросе.

```php
<?php
// Внешняя область видимости: выполняется один раз при запуске
require __DIR__ . '/../vendor/autoload.php';

$config = parse_ini_file(__DIR__ . '/../config/app.ini');
$db = new PDO($config['dsn'], $config['user'], $config['pass'], [
    PDO::ATTR_PERSISTENT => true,
]);

$app = new MyApp\Application($config, $db);

// Цикл запросов: выполняется для каждого запроса
oxphp_worker(function () use ($app) {
    $app->handle();
});

// Завершение: выполняется при выходе воркера
$app->terminate();
```

## Что сбрасывается между запросами

OxPHP выполняет мягкий сброс между запросами. Следующее состояние очищается автоматически:

- **Суперглобальные переменные** — `$_GET`, `$_POST`, `$_SERVER`, `$_COOKIE`, `$_FILES` и `php://input` заново заполняются данными нового запроса
- **Буферы вывода** — все буферы вывода сбрасываются и очищаются
- **Заголовки ответа** — код HTTP-статуса и заголовки сбрасываются до значений по умолчанию
- **Состояние ошибок** — последняя информация об ошибке (сообщение, файл, строка, тип) и статус соединения очищаются. Пользовательские обработчики ошибок (`set_error_handler()`), обработчики исключений (`set_exception_handler()`) и уровень `error_reporting()` сохраняются между запросами

## Что сохраняется

Следующее состояние выживает между запросами в пределах одного воркера:

- **Переменные во внешней области видимости** — всё, что определено до `oxphp_worker()` и захвачено через `use`
- **Статические свойства** — статические свойства классов сохраняют свои значения
- **Соединения с базой данных** — PDO, MySQLi и другие постоянные соединения остаются открытыми
- **Автозагрузчики** — зарегистрированные автозагрузчики (Composer, пользовательские) остаются активными
- **Загруженные классы и функции** — все ранее загруженные классы, интерфейсы, трейты и функции

## Перезапуск воркера

Воркеры автоматически перезапускаются (новый PHP-процесс) при выполнении любого из следующих условий:

- **Достигнуто максимальное число запросов** — воркер обработал `WORKER_MAX_REQUESTS` запросов
- **Превышена максимальная память** — использование PHP-памяти воркером превышает `WORKER_MAX_MEMORY_MIB` МиБ
- **Последовательные ошибки** — воркер сталкивается с 3 последовательными сбоями обработчика (фатальные ошибки, тайм-ауты или необработанные исключения). Обратите внимание, что вызовы `exit()`/`die()` не считаются сбоями

При перезапуске воркера PHP-процесс завершается и запускается новый, повторно выполняя внешнюю область видимости скрипта воркера. При перезапуске по причине max-requests и max-memory текущий запрос завершается нормально перед выходом воркера. При перезапуске по причине ошибок воркер завершается после неудачного запроса.

## Авто-перезагрузка кода в разработке

Worker Mode держит bootstrap-состояние (автозагрузчик, DI-контейнер, подключения к БД) в памяти, поэтому одного `opcache.validate_timestamps=1` недостаточно, чтобы подхватить изменения в коде, выполнявшемся во внешней области. В dev-цикле есть два варианта:

- **Пересоздавать воркер на каждый запрос.** Поставьте `WORKER_MAX_REQUESTS=1`, чтобы внешняя область видимости выполнялась заново на каждом запросе. Вы теряете выигрыш от worker-mode, но получаете FPM-подобную семантику перезагрузки — самый простой и надёжный вариант для активной разработки.
- **Держать воркер прогретым, обновлять только обработчики запросов.** Оставьте `WORKER_MAX_REQUESTS` большим, включите `opcache.validate_timestamps=1` и держите bootstrap минимальным. Код, загруженный внутри колбэка запроса, будет обновлён OPcache на следующем запросе; код, загруженный один раз во внешней области — нет. Полный список оговорок см. в разделе [OPcache и JIT → Настройки для разработки](../php/opcache.md#настройки-для-разработки).

## Устранение неполадок

### Запросы зависают и никогда не завершаются

Если `oxphp_worker()` никогда не вызывается в скрипте начальной загрузки, запросы не диспетчеризируются и каждый запрос ожидает бесконечно. Убедитесь, что ваш скрипт вызывает `oxphp_worker()` безусловно в нормальном пути выполнения кода.

### Утечка состояния между запросами

Переменные, определённые внутри обратного вызова `oxphp_worker()`, очищаются сборщиком мусора PHP, но статические свойства и глобалы, определённые во внешней области видимости, сохраняются. Если вы видите данные из одного запроса в другом, проверьте наличие статических свойств или глобальных переменных, накапливающих состояние между вызовами.

**Решение:** Явно сбрасывайте статическое состояние в начале каждого обратного вызова запроса или избегайте хранения состояния запроса в статических переменных.

### Воркер немедленно перезапускается (ограничение памяти)

Ограничение памяти воркера проверяется после каждого запроса на основе сообщаемого PHP использования памяти. Если фаза начальной загрузки выделяет большой объём памяти (например, загрузка большого кэша), начальный объём памяти может уже быть близок к лимиту.

**Решение:** Увеличьте `WORKER_MAX_MEMORY_MIB` или перенесите крупные выделения памяти на первый запрос.

### Воркер немедленно перезапускается (лимит ошибок)

Три последовательных сбоя обработчика вызывают перезапуск. Проверьте логи приложения на наличие исключений или фатальных ошибок, возникающих в обратном вызове запроса.

**Проверка:** Поищите ошибки в логе доступа или структурированном выводе логов:

```bash
docker logs <container> 2>&1 | grep '"level":"error"'
```

### Соединение с базой данных прерывается после простоя

Если сервер базы данных закрывает соединения в состоянии простоя, попытки переподключения при следующем запросе могут завершиться неудачей. Используйте пул соединений, обрабатывающий переподключение, или перехватывайте исключение и переподключайтесь вручную.

## Пример Docker

```yaml
services:
  app:
    image: ghcr.io/oxphp/oxphp:0.3.0
    ports:
      - "8080:80"
    volumes:
      - ./src:/var/www/html
    environment:
      - DOCUMENT_ROOT=/var/www/html/public
      - INDEX_FILE=index.php
      - WORKER_FILE=/var/www/html/worker.php
      - WORKER_MAX_REQUESTS=10000
      - WORKER_MAX_MEMORY_MIB=128
```

## Примеры PHP

### Определение режима воркера

Используйте `oxphp_is_worker()`, чтобы проверить, работает ли текущий процесс в режиме воркера. Это полезно для написания кода, работающего как в традиционном, так и в режиме воркера.

```php
<?php
if (oxphp_is_worker()) {
    // Повторно использовать постоянное соединение
    $redis = new Redis();
    $redis->pconnect('redis', 6379);
} else {
    // Традиционный режим: подключаться при каждом запросе
    $redis = new Redis();
    $redis->connect('redis', 6379);
}
```

### Скрипт воркера Symfony

```php
<?php
use App\Kernel;

require __DIR__ . '/../vendor/autoload.php';

$kernel = new Kernel('prod', false);
$kernel->boot();

oxphp_worker(function () use ($kernel) {
    $request = Symfony\Component\HttpFoundation\Request::createFromGlobals();
    $response = $kernel->handle($request);
    $response->send();
    $kernel->terminate($request, $response);
});

$kernel->shutdown();
```

## Лучшие практики

- **Устанавливайте оба параметра `WORKER_MAX_REQUESTS` и `WORKER_MAX_MEMORY_MIB`** для предотвращения неограниченного роста ресурсов. Начните со значений около `10000` запросов и `128` МиБ.
- **Избегайте хранения состояния запроса в статических свойствах или глобалах.** Поскольку они сохраняются между запросами, остаточное состояние одного запроса может проникнуть в другой.
- **Сначала тестируйте с `WORKER_MAX_REQUESTS=1`**, затем увеличивайте. Это проверяет, что ваше приложение корректно обрабатывает мягкий сброс, прежде чем переходить к долгоживущим воркерам.
- **Обрабатывайте тайм-ауты простоя базы данных.** Если драйвер базы данных отключается после периода простоя, перехватывайте исключение и переподключайтесь, или используйте пул соединений, обрабатывающий переподключение автоматически.
- **Минимизируйте внешнюю область видимости.** Инициализируйте только то, что действительно должно сохраняться — автозагрузчики, конфигурацию и общие сервисы. Откладывайте настройку, специфичную для запроса, в обратный вызов.
