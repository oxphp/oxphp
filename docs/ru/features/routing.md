OxPHP поддерживает три режима маршрутизации, управляемых одной переменной окружения. Каждый режим определяет, как входящие URL-пути отображаются на файлы на диске.

## Режимы маршрутизации

Переменная окружения `INDEX_FILE` выбирает режим маршрутизации:

| Режим | Значение `INDEX_FILE` | Сценарий использования |
|-------|----------------------|----------------------|
| Традиционный | *(не задано)* | Классический PHP-хостинг, WordPress с пофайловой маршрутизацией |
| Фреймворк | `index.php` | Laravel, Symfony или любой фреймворк с единой точкой входа |
| SPA | `index.html` | React, Vue, Angular с клиентской маршрутизацией |

### Традиционный режим

Когда `INDEX_FILE` не задана, OxPHP напрямую отображает URL на файлы на диске.

- `/style.css` отдаёт `DOCUMENT_ROOT/style.css`
- `/about.php` выполняет `DOCUMENT_ROOT/about.php`
- `/` разрешается в `index.php`, если он существует, иначе в `index.html`
- `/subdir/` пробует `subdir/index.php`, затем `subdir/index.html`
- Отсутствующие файлы возвращают 404

```bash
# INDEX_FILE не задана -- традиционный режим по умолчанию
DOCUMENT_ROOT=/var/www/html
```

### Режим фреймворка

Когда `INDEX_FILE=index.php`, все запросы, не совпадающие с существующим статическим файлом, направляются к единой точке входа (front controller).

- `/style.css` отдаёт статический файл напрямую
- `/api/users` выполняет `index.php` (файл не существует на диске)
- `/about.php` возвращает 404 (прямой доступ к `.php` заблокирован)
- `/index.php` возвращает 404 (прямой доступ к индексному файлу заблокирован)

```bash
INDEX_FILE=index.php
DOCUMENT_ROOT=/var/www/html
```

Блокировка прямого доступа к `.php` предотвращает утечку URL и обеспечивает прохождение всех PHP-запросов через маршрутизатор фреймворка.

### Режим SPA

Когда `INDEX_FILE=index.html`, несуществующие пути перенаправляются на HTML-точку входа. PHP-файлы по-прежнему выполняются в обычном режиме.

- `/style.css` отдаёт статический файл
- `/app/dashboard` отдаёт `index.html` (клиентский маршрутизатор обрабатывает путь)
- `/api.php` выполняет PHP-скрипт
- `/index.html` возвращает 404 (прямой доступ к индексному файлу заблокирован)

```bash
INDEX_FILE=index.html
DOCUMENT_ROOT=/var/www/html
```

## Разрешение корневого пути

Запросы к `/` используют предвычисленные пути, чтобы избежать аллокаций при каждом запросе. Сервер сначала проверяет наличие `index.php`, затем `index.html`. Если ни одного из них нет, возвращается 404.

Пути к подкаталогам с завершающим слешем (например, `/blog/`) следуют той же логике разрешения индексного файла: сначала `index.php`, затем `index.html`.

## Санитизация пути

Каждый входящий URI-путь проходит через конвейер санитизации перед обращением к файловой системе:

1. **Процентное декодирование** -- `%2e%2e` декодируется в `..` до того, как санитизация его перехватит
2. **Фильтрация сегментов** -- `..`, `.` и пустые сегменты удаляются
3. **Проверка символических ссылок** -- разрешённые пути проверяются относительно каноничного корня документов

Запрос вида `/%2e%2e/etc/passwd` декодируется в `/../etc/passwd`, санитизируется в `etc/passwd`, а затем проверяется на выход за границу корня документов.

## Защита от выхода через символические ссылки

При запуске OxPHP канонизирует путь к корню документов. Каждый разрешённый путь к файлу канонизируется и проверяется на принадлежность к корню документов. Это блокирует символические ссылки, указывающие за пределы обслуживаемой директории.

Результаты канонизации кешируются, чтобы избежать повторных системных вызовов `realpath(3)`. Кеш использует ту же LRU-стратегию вытеснения, что и кеш метаданных.

Если корень документов не может быть канонизирован при запуске (например, директория ещё не существует), защита через символические ссылки отключается, и записывается предупреждение.

### Защита от TOCTOU

Сервер статических файлов повторно канонизирует путь в момент отдачи, непосредственно перед чтением с диска. Это предотвращает атаки типа time-of-check-to-time-of-use, когда символическая ссылка подменяется между разрешением маршрута и чтением файла.
