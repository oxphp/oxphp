# Маршрутизация

OxPHP направляет входящие HTTP-запросы в одном из четырёх режимов, управляемых единственной переменной окружения. Выбранный режим определяет, как URL-пути сопоставляются с файлами на диске.

## Как это работает

Когда поступает запрос, OxPHP обрабатывает URL-путь через конвейер безопасности перед его разрешением в файл:

1. **Декодирование процентных последовательностей** — закодированные символы, такие как `%2e%2e`, декодируются в буквальные значения
2. **Фильтрация сегментов** — сегменты обхода пути (`..`), сегменты текущего каталога (`.`) и пустые сегменты удаляются
3. **Маршрутизация по режиму** — очищенный путь сопоставляется с файловой системой согласно активному режиму маршрутизации
4. **Проверка символических ссылок** — разрешённый путь в файловой системе проверяется на соответствие границе корневого каталога документов для предотвращения выхода через символические ссылки

## Конфигурация

| Переменная | По умолчанию | Описание |
|------------|--------------|----------|
| `DOCUMENT_ROOT` | `/var/www/html/public` | Корневой каталог для обслуживания файлов и PHP-скриптов |
| `INDEX_FILE` | *(не задана)* | Определяет режим маршрутизации. Не задана = традиционный, `index.php` = фреймворк, `index.html` = SPA |
| `SPLIT_PATH_INFO_ENABLED` | `false` | Разбивает URI вида `/script.php/path` на скрипт + `PATH_INFO` |

## Традиционный режим

Традиционный режим активен, когда `INDEX_FILE` не задана. URL-адреса напрямую сопоставляются с файлами на диске — аналогично классическому PHP-хостингу с Apache или nginx.

- `/about.php` выполняет `DOCUMENT_ROOT/about.php`
- `/style.css` отдаёт `DOCUMENT_ROOT/style.css`
- `/` разрешается в `index.php`, если он существует, иначе в `index.html`
- `/blog/` пробует `blog/index.php`, затем `blog/index.html`
- Любой путь, не соответствующий файлу, возвращает 404

Этот режим хорошо подходит для WordPress, устаревших PHP-приложений или любых проектов, где каждый URL соответствует конкретному файлу.

## Режим фреймворка

Режим фреймворка активен при `INDEX_FILE=index.php`. Все запросы, не соответствующие существующему статическому файлу, направляются к фронт-контроллеру — именно так ожидают Laravel, Symfony и другие PHP-фреймворки.

- `/style.css` отдаёт статический файл напрямую (если он существует на диске)
- `/api/users` выполняет `index.php` (путь не существует как файл)
- `/about.php` возвращает 404 (прямой доступ к `.php` заблокирован)
- `/index.php` возвращает 404 (прямой доступ к фронт-контроллеру заблокирован)

Блокировка прямого доступа к `.php` предотвращает утечки URL и обеспечивает прохождение всех PHP-запросов через маршрутизатор фреймворка.

## Режим SPA

Режим SPA активен при `INDEX_FILE=index.html`. Запросы, не соответствующие существующему файлу, перенаправляются к HTML-точке входа, позволяя клиентским маршрутизаторам (React Router, Vue Router и т.д.) обрабатывать путь.

- `/style.css` отдаёт статический файл
- `/app/dashboard` отдаёт `index.html` (путь обрабатывается клиентским маршрутизатором)
- `/api.php` выполняет PHP-скрипт, если он существует на диске
- `/index.html` возвращает 404 (прямой доступ к индексному файлу заблокирован)

## Режим воркера

Маршрутизация в режиме воркера активируется автоматически при установке `WORKER_FILE`. Все входящие запросы, не соответствующие статическому файлу на диске, отправляются постоянному PHP-воркеру вместо возврата 404.

- `/style.css` отдаёт статический файл напрямую
- `/api/users` отправляется воркеру (файл по этому пути не существует)
- `/` отправляется воркеру, если не существует `index.php` или `index.html`

Режим воркера совместим с `INDEX_FILE`. Установка одновременно `WORKER_FILE` и `INDEX_FILE=index.php` объединяет маршрутизацию режима воркера с обработкой статических файлов режима фреймворка — статические файлы отдаются напрямую, всё остальное направляется воркеру.

Подробности конфигурации см. в разделе [Режим воркера](worker-mode.md).

## Разбиение PATH_INFO

Некоторые устаревшие PHP-приложения используют `PATH_INFO` для маршрутизации — добавляя дополнительные сегменты пути после имени `.php`-скрипта (например, `/api.php/users/42`). По умолчанию OxPHP обрабатывает весь URI как единый путь в файловой системе, поэтому такие запросы возвращают 404.

Установите `SPLIT_PATH_INFO_ENABLED=true` для активации разбиения путей:

```bash
SPLIT_PATH_INFO_ENABLED=true
```

При включении OxPHP сканирует URI слева направо в поисках первого сегмента `.php`, который соответствует существующему файлу на диске. Всё, что следует после него, становится `PATH_INFO`:

```
/app.php/user/42
├── Скрипт: DOCUMENT_ROOT/app.php
└── PATH_INFO: /user/42
```

Это корректно заполняет `$_SERVER` для CGI-маршрутизации:

| Переменная | Значение |
|---|---|
| `SCRIPT_NAME` | `/app.php` |
| `SCRIPT_FILENAME` | `/var/www/html/public/app.php` |
| `PATH_INFO` | `/user/42` |
| `PHP_SELF` | `/app.php/user/42` |

Если ни один файл `.php` не найден по пути, маршрутизация продолжается по обычной цепочке разрешения (запасной воркер, запасной `INDEX_FILE` или 404).

> **Когда использовать:** Drupal, MediaWiki, устаревшие REST API на основе `$_SERVER['PATH_INFO']` или любое приложение, ранее настроенное с nginx `fastcgi_split_path_info`.

## Безопасность путей

OxPHP применяет несколько уровней защиты для предотвращения атак обхода каталогов и выхода через символические ссылки:

- **Декодирование процентных последовательностей** выполняется до очистки, поэтому закодированные попытки обхода, такие как `/%2e%2e/etc/passwd`, перехватываются
- **Фильтрация сегментов** удаляет `..`, `.` и пустые сегменты из разрешённого пути
- **Проверка символических ссылок** канонизирует каждый разрешённый путь и проверяет, что он остаётся в пределах корневого каталога документов. Символические ссылки, указывающие за пределы обслуживаемого каталога, блокируются
- **Блокировка dot-путей** блокирует любой сегмент пути, начинающийся с `.` (например, `/.git/config`, `/.env`), за исключением `/.well-known/*`. См. [Блокировка dot-путей](../security/dot-path-blocking.md)

> **Примечание:** Если корневой каталог документов не существует при запуске, сервер завершает работу с фатальной ошибкой. Защита от выхода через символические ссылки требует допустимого, разрешаемого пути к корневому каталогу документов.

## Устранение неполадок

### Все запросы возвращают 404

Убедитесь, что `DOCUMENT_ROOT` указывает на правильный каталог и этот каталог существует на диске. OxPHP завершает работу при запуске, если корневой каталог документов не может быть разрешён, поэтому работающий сервер означает, что каталог существовал при запуске — однако монтирование тома или неверный путь всё равно приведут к тому, что каждый запрос не найдёт файл.

**Проверка:** Подтвердите путь к корневому каталогу документов внутри контейнера:

```bash
docker exec <container> ls /var/www/html/public
```

**Решение:** Исправьте `DOCUMENT_ROOT` или убедитесь, что ваш том монтирует правильный путь.

### Режим фреймворка возвращает 404 для PHP-маршрутов

Прямой доступ к `.php` намеренно заблокирован в режиме фреймворка. Если ваше приложение ссылается непосредственно на файлы `.php`, переключитесь на традиционный режим (`INDEX_FILE` не задана) или обновите ссылки для использования чистых URL.

### URL со специальными символами возвращают 404

OxPHP декодирует URL перед маршрутизацией. Запросы к путям, таким как `/café/menu`, работают корректно. Если путь по-прежнему возвращает 404, убедитесь, что файл существует на диске с декодированным именем.

### Символическая ссылка внутри корневого каталога документов возвращает 404

Символические ссылки, указывающие за пределы корневого каталога документов, блокируются намеренно. Переместите целевое содержимое внутрь корневого каталога документов или примонтируйте его как каталог по правильному пути.

## Пример Docker

```yaml
services:
  app:
    image: ghcr.io/oxphp/oxphp:0.2.0
    ports:
      - "8080:80"
    volumes:
      - ./src:/var/www/html
    environment:
      - DOCUMENT_ROOT=/var/www/html/public
      - INDEX_FILE=index.php
```
