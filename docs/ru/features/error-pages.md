# Пользовательские страницы ошибок

OxPHP обслуживает брендированные HTML-страницы ошибок для ответов 4xx и 5xx. Страницы ошибок загружаются с диска один раз при запуске и обслуживаются из памяти, поэтому при обработке запросов операции ввода-вывода не выполняются.

## Как это работает

1. При запуске OxPHP читает директорию, указанную в `ERROR_PAGES_DIR`, и загружает в память все допустимые файлы `{status}.html`.
2. Файлы должны быть названы числовым кодом HTTP-статуса в диапазоне 400–599 (например, `404.html`, `503.html`). Файлы с нечисловыми именами, кодами статуса вне этого диапазона (включая `200.html`) или с расширениями, отличными от `.html`, молча игнорируются.
3. Когда OxPHP генерирует ответ 4xx или 5xx, он проверяет наличие предзагруженной страницы ошибки. При её наличии тело ответа заменяется пользовательским HTML, а `Content-Type` устанавливается в `text/html; charset=utf-8`.
4. Если директория не существует или не может быть прочитана при запуске, OxPHP регистрирует ошибку и завершает работу. Если отдельный файл не может быть прочитан, OxPHP также регистрирует ошибку и завершает работу. Убедитесь, что директория и все `.html`-файлы доступны для чтения перед запуском.

## Конфигурация

| Переменная | По умолчанию | Описание |
|------------|-------------|----------|
| `ERROR_PAGES_DIR` | *(не задана)* | Директория, содержащая HTML-файлы пользовательских страниц ошибок. Файлы должны называться `{status}.html` для кодов статуса 400–599. Если не задана, ответы об ошибках используют текстовые тела |

## Примеры страниц

Минимальная страница 404:

```html
<!DOCTYPE html>
<html lang="en">
<head>
  <meta charset="utf-8">
  <title>404 - Page Not Found</title>
  <style>
    body { font-family: system-ui, sans-serif; text-align: center; padding: 4rem 1rem; color: #333; }
    h1 { font-size: 2rem; margin-bottom: 0.5rem; }
    p { color: #666; }
  </style>
</head>
<body>
  <h1>Page Not Found</h1>
  <p>The page you requested does not exist.</p>
</body>
</html>
```

Страница обслуживания 503 с автообновлением:

```html
<!DOCTYPE html>
<html lang="en">
<head>
  <meta charset="utf-8">
  <meta http-equiv="refresh" content="30">
  <title>503 - Service Unavailable</title>
  <style>
    body { font-family: system-ui, sans-serif; text-align: center; padding: 4rem 1rem; color: #333; }
    h1 { font-size: 2rem; margin-bottom: 0.5rem; }
    p { color: #666; }
  </style>
</head>
<body>
  <h1>Service Unavailable</h1>
  <p>We are performing maintenance. This page will refresh automatically.</p>
</body>
</html>
```

## Устранение неполадок

### Пользовательские страницы ошибок не отображаются

Убедитесь, что переменная `ERROR_PAGES_DIR` задана, а файлы названы правильно.

**Проверьте:** Подтвердите активный путь к директории и что OxPHP вывел строки "Loaded custom error page" при запуске:

```bash
docker logs my-app 2>&1 | grep "error page"
```

**Исправление:** Убедитесь, что путь к директории верен, файлы названы `{status}.html`, а контейнер имеет доступ на чтение директории.

### Сервер завершает работу при запуске с ошибкой файла

OxPHP останавливается, если директория `ERROR_PAGES_DIR` не существует или файл не может быть прочитан. Проверьте правильность монтирования тома в Docker:

```bash
docker run --rm -v ./errors:/var/www/errors:ro \
  -e ERROR_PAGES_DIR=/var/www/errors \
  ghcr.io/oxphp/oxphp:0.3.0
```

### Ответ 429 всё равно показывает стандартное тело

Некоторые ответы, генерируемые до запуска конвейера ответов — например, отказы от ограничителя частоты — не обрабатываются обработчиком страниц ошибок. Ответ `429 Too Many Requests` от ограничителя частоты использует стандартное тело независимо от наличия файла `429.html`.

## Пример Docker

```yaml
services:
  app:
    image: ghcr.io/oxphp/oxphp:0.3.0
    ports:
      - "8080:8080"
    volumes:
      - ./src:/var/www/html:ro
      - ./errors:/var/www/errors:ro
    environment:
      ERROR_PAGES_DIR: "/var/www/errors"
      INDEX_FILE: "index.php"
```

Структура директорий:

```text
project/
  src/
    public/
      index.php
  errors/
    403.html
    404.html
    500.html
    502.html
    503.html
```

## Лучшие практики

- Делайте страницы ошибок самодостаточными со встроенным CSS. Не ссылайтесь на внешние таблицы стилей или скрипты — эти вторичные запросы сами могут завершиться неудачей.
- Добавляйте тег `<meta http-equiv="refresh" content="30">` на страницу `503.html`, чтобы пользователи автоматически повторяли попытку после завершения обслуживания.
- Держите страницы ошибок небольшими. Каждая загруженная страница хранится в памяти на всё время работы серверного процесса.

## Примечания

Пользовательские страницы ошибок применяются к ответам, проходящим через обычный конвейер обработки запросов. Ответ `429 Too Many Requests` от ограничителя частоты генерируется до запуска обработчика страниц ошибок и использует стандартное текстовое тело.
