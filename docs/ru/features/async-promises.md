OxPHP предоставляет API на основе промисов, позволяющий PHP-коду отправлять замыкания для выполнения в выделенном пуле потоков, отдельном от пула HTTP-воркеров. Это обеспечивает настоящее параллельное вычисление без блокировки потока запроса.

## Конфигурация

| Переменная | По умолчанию | Описание |
|------------|--------------|----------|
| `ASYNC_WORKERS` | `0` (отключено) | Количество выделенных потоков асинхронных воркеров. `0` отключает асинхронный пул |
| `ASYNC_QUEUE_CAPACITY` | `ASYNC_WORKERS * 64` | Размер ограниченного канала для ожидающих асинхронных задач. Задачи отклоняются при заполнении |

Для включения асинхронного пула:

```bash
ASYNC_WORKERS=4
```

Установите `0` (или оставьте не заданным) для полного отключения асинхронной поддержки. При отключённом пуле вызов `oxphp_async()` генерирует `E_WARNING` и возвращает `false`.

## PHP API

### `oxphp_async`

Отправляет замыкание для асинхронного выполнения в пуле асинхронных воркеров.

```php
oxphp_async(Closure $closure, mixed ...$args): int|false
```

**Параметры:**

| Имя | Тип | Описание |
|-----|-----|----------|
| `$closure` | `Closure` | Замыкание для асинхронного выполнения |
| `...$args` | `mixed` | Аргументы, передаваемые замыканию через глубокое копирование |

**Возвращаемое значение:** Идентификатор промиса (положительное целое число) при успехе или `false`, если асинхронный пул не настроен или очередь заполнена.

**Пример:**

```php
<?php
$promise = oxphp_async(function(int $n): int {
    return $n * $n;
}, 42);

$result = oxphp_async_await($promise);
// 1764
```

### `oxphp_async_await`

Блокирует текущий поток до завершения асинхронной задачи и возвращает результат.

```php
oxphp_async_await(int $promise_id, ?float $timeout = null): mixed
```

**Параметры:**

| Имя | Тип | По умолчанию | Описание |
|-----|-----|--------------|----------|
| `$promise_id` | `int` | *(обязательный)* | Идентификатор промиса, возвращённый `oxphp_async()` |
| `$timeout` | `?float` | `null` | Таймаут в секундах. `null` ожидает бесконечно |

**Возвращаемое значение:** Возвращаемое значение замыкания.

**Исключения:**

| Исключение | Когда |
|------------|-------|
| `OxPHP\AsyncException` | Замыкание выбросило исключение или вызвало `die()`/`exit()` |
| `OxPHP\AsyncTimeoutException` | Таймаут истёк до завершения задачи |

### `oxphp_async_await_all`

Ожидает несколько промисов и возвращает все результаты в виде массива.

```php
oxphp_async_await_all(array $promise_ids, ?float $timeout = null): array
```

**Параметры:**

| Имя | Тип | По умолчанию | Описание |
|-----|-----|--------------|----------|
| `$promise_ids` | `array` | *(обязательный)* | Массив идентификаторов промисов |
| `$timeout` | `?float` | `null` | Таймаут в секундах для каждого промиса |

**Возвращаемое значение:** Ассоциативный массив, сопоставляющий идентификаторы промисов с их результатами.

**Исключения:** `OxPHP\AsyncException` или `OxPHP\AsyncTimeoutException`, если какой-либо промис завершился с ошибкой или по таймауту.

### `oxphp_async_await_any`

Устраивает гонку нескольких промисов и возвращает первый завершившийся, независимо от порядка в массиве. Внутренне использует `futures::select_all` для настоящей конкурентной семантики гонки. Непобедившие промисы остаются доступными для индивидуального ожидания через `oxphp_async_await()`.

```php
oxphp_async_await_any(array $promise_ids, ?float $timeout = null): array
```

**Параметры:**

| Имя | Тип | По умолчанию | Описание |
|-----|-----|--------------|----------|
| `$promise_ids` | `array` | *(обязательный)* | Массив идентификаторов промисов |
| `$timeout` | `?float` | `null` | Общий таймаут в секундах для завершения любого промиса |

**Возвращаемое значение:** Ассоциативный массив с ключами `id` (идентификатор победившего промиса) и `value` (его результат).

**Исключения:** `OxPHP\AsyncException`, если первый завершившийся промис выбросил исключение. `OxPHP\AsyncTimeoutException`, если ни один промис не завершился в пределах таймаута.

**Примечание:** При таймауте все указанные промисы отменяются и не могут быть ожидаемы индивидуально в дальнейшем.

## Семантика передачи данных

Замыкания выполняются в другом потоке ОС с собственным состоянием PHP ZTS и `zend_mm_heap`. Данные не могут быть разделены через указатели между потоками --- любой указатель на строку или массив, выделенный в куче одного потока, становится недействительным в другом потоке. OxPHP использует **портативную бинарную сериализацию** для безопасной передачи всех данных через границы потоков.

### Как это работает

Все значения, пересекающие границы потоков (аргументы, `use`-переменные, возвращаемые значения), сериализуются в плоский байтовый буфер с использованием системного `malloc`. Буфер передаётся в целевой поток, который десериализует его с использованием `emalloc` в своей собственной куче. Это гарантирует, что каждое PHP-выделение принадлежит корректной потоко-локальной `zend_mm_heap`.

### Захваченные переменные (через `use`)

Переменные, захваченные конструкцией `use` замыкания, **сериализуются** в исходном потоке и **десериализуются** как независимые копии в потоке асинхронного воркера. Исходные переменные остаются неизменными и полностью доступными во время асинхронного выполнения.

```php
<?php
$config = ['db' => 'mysql', 'timeout' => 30];

$p = oxphp_async(function() use ($config): string {
    // $config — независимая копия; чтение и запись работают нормально
    return $config['db'];
});

// $config остаётся доступной для записи — она была скопирована, а не заморожена
$config['timeout'] = 60; // безопасно
$result = oxphp_async_await($p);
```

### Аргументы

Аргументы, переданные через `...$args`, сериализуются и десериализуются тем же способом. Поддерживаемые типы:

| Тип | Передача |
|-----|----------|
| `null`, `bool`, `int`, `float` | Сериализуется как значение (1-9 байт) |
| `string` | Сериализуется с префиксом длины + данные |
| `array` | Рекурсивная сериализация (ключи + значения) |
| `resource` | **Отклоняется** --- выбрасывает `OxPHP\AsyncException` |
| `object` | **Отклоняется** --- выбрасывает `OxPHP\AsyncException` (объекты невозможно сериализовать между потоками) |

### Возвращаемые значения

Возвращаемое значение замыкания сериализуется в потоке асинхронного воркера и десериализуется в исходном потоке тем же механизмом. Поддерживаются все скалярные типы, строки и массивы (включая вложенные).

## Обработка исключений

Исключения, выброшенные внутри асинхронного замыкания, перехватываются и повторно выбрасываются как `OxPHP\AsyncException` при вызове `oxphp_async_await()`. Класс и сообщение исходного исключения сохраняются в сообщении `AsyncException`:

```php
<?php
$p = oxphp_async(function(): never {
    throw new \DomainException('invalid value', 422);
});

try {
    oxphp_async_await($p);
} catch (\OxPHP\AsyncException $e) {
    echo $e->getMessage();
    // "Async task failed: [DomainException] invalid value"
}
```

### die() и exit()

Вызовы `die()` или `exit()` внутри асинхронных замыканий перехватываются через `zend_try`/`zend_catch` и преобразуются в `OxPHP\AsyncException`. Пул асинхронных воркеров выживает --- последующие задачи выполняются нормально:

```php
<?php
// Раунд 1: die() — перехвачен как AsyncException
$p1 = oxphp_async(function(): never { die('fatal'); });
try { oxphp_async_await($p1); } catch (\OxPHP\AsyncException $e) { /* обработано */ }

// Раунд 2: пул жив, обычная задача работает
$p2 = oxphp_async(function(): int { return 42; });
$result = oxphp_async_await($p2); // 42
```

### Классы исключений

| Класс | Родитель | Когда |
|-------|----------|-------|
| `OxPHP\AsyncException` | `Exception` | Замыкание выбросило исключение или был вызван `die()`/`exit()` |
| `OxPHP\AsyncTimeoutException` | `OxPHP\AsyncException` | Таймаут истёк до завершения задачи |

## Область видимости и время жизни промисов

Промисы хранятся в **потоко-локальном хранилище** PHP-воркера, который их создал. Это имеет три следствия:

1. **Привязка к потоку.** Промис может быть ожидаем только тем же потоком воркера, который вызвал `oxphp_async()`. Другой поток воркера имеет собственную карту промисов и не видит чужие идентификаторы промисов.

2. **Привязка к запросу.** В конце каждого запроса (RSHUTDOWN) все невостребованные промисы автоматически очищаются. В режиме воркера та же очистка выполняется между запросами. Промисы не могут пережить границы запросов.

3. **Идентификаторы уникальны в пределах потока, но не глобально.** Счётчик промисов монотонно увеличивается в пределах потока и не сбрасывается между запросами. Два разных потока воркеров могут оба иметь промис с идентификатором `0` --- это независимые промисы в отдельных картах.

```
Worker Thread #1                    Worker Thread #2
┌─ Request A ─────────────┐        ┌─ Request C ──────────┐
│ PROMISE_MAP: {0, 1, 2}  │        │ PROMISE_MAP: {0, 1}  │
│ await_any([0, 1]) → OK  │        │ await(0) → OK        │
│ await(2) → OK           │        │ await(1) → OK        │
│ RSHUTDOWN: cleanup      │        │ RSHUTDOWN: cleanup    │
├─ Request B ─────────────┤        └──────────────────────┘
│ PROMISE_MAP: {3, 4}     │  ← counter continues from 3
│ (not awaited)           │
│ RSHUTDOWN: cancel + free│  ← promises 3, 4 cleaned up
└─────────────────────────┘
```

Для обмена результатами асинхронного выполнения между запросами используйте внешний механизм (Redis, разделяемая память, база данных).

## Очистка при RSHUTDOWN

Если PHP-запрос завершается без ожидания всех отправленных промисов, хук RSHUTDOWN автоматически очищает невостребованные промисы. Каждому неожидаемому промису даётся 5-секундный таймаут для завершения, после чего он отменяется. Это предотвращает утечку ресурсов от забытых промисов.

```php
<?php
$p1 = oxphp_async(function(): int { return 1; });
$p2 = oxphp_async(function(): int { return 2; });

$result = oxphp_async_await($p1);
// $p2 никогда не ожидается — автоматически очищается при завершении запроса
```

## Архитектура

Асинхронный пул представляет собой **отдельный** набор потоков ОС от пула HTTP PHP-воркеров. Такое разделение предотвращает дедлоки: если бы все HTTP-воркеры отправили асинхронные задачи и затем заблокировались на `oxphp_async_await()`, общий пул зашёл бы в тупик.

> **Файбер-совместимое поведение:** В режиме воркера при активном планировщике файберов `oxphp_async_await()` приостанавливает текущий файбер запроса вместо блокировки потока воркера. Это позволяет обрабатывать другие запросы во время ожидания асинхронных результатов. Подробнее см. [Мультиплексирование запросов на файберах](fiber-multiplexing.md).

```
HTTP Worker Thread              Async Worker Thread
─────────────────              ────────────────────
oxphp_async($fn)
  ├─ serialize use-vars
  ├─ serialize args
  ├─ create AsyncTask           recv(AsyncTask)
  ├─ send via channel ──────►     ├─ oxphp_async_reset()
  │                               ├─ deserialize use-vars
  │                               ├─ deserialize args
  │                               ├─ oxphp_execute_async_task()
  │                               ├─ serialize retval
oxphp_async_await($id)                  ├─ send AsyncResult
  ├─ block on oneshot ◄──────     └─ free local data
  ├─ deserialize result
  └─ return value
```

Все данные, пересекающие границы потоков, проходят через портативную бинарную сериализацию: сериализация с использованием системного `malloc` в исходном потоке, передача буфера, десериализация с использованием `emalloc` в целевом потоке. Это гарантирует, что каждое PHP-выделение принадлежит корректной потоко-локальной `zend_mm_heap`.

Каждый поток асинхронного воркера:
1. Инициализирует TSRM (Zend Thread Safety) потоко-локальное хранилище
2. Вызывает `php_request_startup()` один раз при запуске потока
3. Цикл: получение задачи -> сброс состояния -> десериализация данных -> выполнение замыкания -> сериализация результата -> отправка
4. Вызывает `php_request_shutdown()` при завершении

## Подбор параметров и тюнинг

Асинхронные воркеры --- это выделенные потоки ОС с полной инициализацией PHP ZTS. Они конкурируют за ядра CPU с HTTP-воркерами и средой выполнения Tokio. Правильный подбор параметров предотвращает конкуренцию за CPU и гарантирует, что асинхронные задачи не лишают ресурсов обработку HTTP-запросов.

### Бюджет потоков

Общее количество потоков по всем пулам должно оставаться в пределах количества ядер CPU:

```
Total threads = TOKIO_WORKERS + PHP_WORKERS + ASYNC_WORKERS ≤ CPU cores
```

Превышение этого бюджета вызывает накладные расходы на переключение контекста, снижающие пропускную способность всех пулов.

| Сервер с 8 ядрами | TOKIO | PHP | ASYNC | Всего | Оценка |
|-------------------|-------|-----|-------|-------|--------|
| Консервативный | 4 | 4 | 2 | 10 | хорошо --- небольшая переподписка допустима |
| Агрессивный | 4 | 4 | 4 | 12 | приемлемо, если асинхронные задачи I/O-ёмкие |
| Перегруженный | 4 | 8 | 8 | 20 | плохо --- накладные расходы на переключение контекста доминируют |

### ASYNC_WORKERS по типу нагрузки

Оптимальное количество зависит от того, являются ли асинхронные задачи CPU-ёмкими или I/O-ёмкими:

| Нагрузка | Формула | Обоснование |
|----------|---------|-------------|
| **CPU-ёмкая** (вычисления, обработка данных) | `CPU_cores / 4` | Больше потоков не поможет --- они конкурируют за те же ядра, что и HTTP-воркеры |
| **I/O-ёмкая** (sleep, сетевые вызовы, файловый I/O) | `PHP_WORKERS` | Потоки большую часть времени заблокированы на I/O, не потребляя CPU |
| **Смешанная** (типичная) | `PHP_WORKERS / 2` | Начните с этого значения, корректируйте по метрикам |

### ASYNC_QUEUE_CAPACITY по требованиям к задержке

Каждая задача в очереди содержит сериализованные аргументы в памяти. Глубина очереди --- это баланс между памятью и задержкой, с одной стороны, и устойчивостью к всплескам --- с другой:

| Сценарий | Рекомендуемая ёмкость | Обоснование |
|----------|----------------------|-------------|
| **Веб-запросы** (чувствительные к задержке) | `ASYNC_WORKERS * 4..8` | Лучше отклонить рано и использовать запасной вариант, чем ставить в очередь и ждать |
| **Фоновые/пакетные** (чувствительные к пропускной способности) | `ASYNC_WORKERS * 64` (по умолчанию) | Допустимо буферизовать задачи для последующей обработки |

### Предотвращение зависаний

Когда HTTP-воркер вызывает `oxphp_async_await()`, он блокируется до завершения асинхронной задачи. Если все HTTP-воркеры заблокируются одновременно, а асинхронные воркеры не справляются, пропускная способность запросов падает до нуля.

Ограничение:

```
ASYNC_WORKERS ≥ max concurrent oxphp_async_await() callers
```

На практике оцените, какая доля HTTP-запросов использует асинхронность:

| Использование async | Правило подбора |
|--------------------|-----------------|
| Каждый запрос отправляет async | `ASYNC_WORKERS ≥ PHP_WORKERS` |
| ~30% запросов | `ASYNC_WORKERS ≥ PHP_WORKERS / 3` |
| Редко (1 из 10) | `ASYNC_WORKERS ≥ PHP_WORKERS / 4` |

### Потребление памяти

Каждый поток асинхронного воркера потребляет:
- Стек потока ОС: 2-8 МБ (зависит от платформы)
- PHP ZTS куча: ~2-10 МБ (зависит от расширений и INI-настроек)
- Приблизительный итог: **4-18 МБ на воркер**

Задачи в очереди добавляют память для сериализованных аргументов (зависит от размера полезной нагрузки, обычно небольшой).

### Примеры конфигураций

**Сервер с 8 ядрами, Laravel, ~30% запросов используют async:**

```bash
TOKIO_WORKERS=0           # auto: 4 (CPU/2)
PHP_WORKERS=4
ASYNC_WORKERS=2           # CPU/4, достаточно для 30% асинхронной нагрузки
ASYNC_QUEUE_CAPACITY=16   # низкая задержка: 2 * 8
```

**Сервер с 16 ядрами, пакетная обработка, каждый запрос разветвляется:**

```bash
TOKIO_WORKERS=0           # auto: 8 (CPU/2)
PHP_WORKERS=6
ASYNC_WORKERS=6           # соответствует PHP-воркерам — все запросы используют async
ASYNC_QUEUE_CAPACITY=384  # 6 * 64, высокая пропускная способность
```

**Контейнер с 4 ядрами, периодические фоновые задачи:**

```bash
TOKIO_WORKERS=1           # однопоточный, экономим ядра для PHP
PHP_WORKERS=2
ASYNC_WORKERS=1           # минимум — async используется редко
ASYNC_QUEUE_CAPACITY=8    # 1 * 8
```

### Мониторинг

После деплоя используйте следующие PromQL-запросы для проверки подбора параметров:

```promql
# Задачи отклоняются? → увеличьте ASYNC_QUEUE_CAPACITY или ASYNC_WORKERS
rate(oxphp_async_tasks_rejected_total[5m]) > 0

# Очередь задач растёт? → увеличьте ASYNC_WORKERS
oxphp_async_tasks_dispatched_total
  - oxphp_async_tasks_completed_total
  - oxphp_async_tasks_failed_total
  - oxphp_async_tasks_cancelled_total

# CPU перегружен? → уменьшите ASYNC_WORKERS
# Проверьте системные метрики: load average, утилизация CPU, steal time
```

## Метрики

При активном асинхронном пуле (отправлена хотя бы одна задача) генерируются пять счётчиков Prometheus:

| Метрика | Тип | Описание |
|---------|-----|----------|
| `oxphp_async_tasks_dispatched_total` | counter | Общее количество задач, отправленных через `oxphp_async()` |
| `oxphp_async_tasks_completed_total` | counter | Задачи, успешно вернувшие значение |
| `oxphp_async_tasks_failed_total` | counter | Задачи, выбросившие исключение или вызвавшие `die()`/`exit()` |
| `oxphp_async_tasks_cancelled_total` | counter | Задачи, отменённые (таймаут или очистка при RSHUTDOWN) |
| `oxphp_async_tasks_rejected_total` | counter | Задачи, отклонённые из-за заполненности асинхронной очереди |

Эти счётчики не включаются в вывод Prometheus, когда ни одна асинхронная задача не была отправлена и ни одна не была отклонена.

## Окружение асинхронного воркера

Асинхронные воркеры --- это **изолированные PHP-движки**. Каждый поток асинхронного воркера выполняет `php_request_startup()` один раз при запуске потока и затем в цикле выполняет замыкания. В отличие от HTTP-воркеров, асинхронные воркеры **не** выполняют код начальной загрузки вашего приложения --- ни `vendor/autoload.php`, ни инициализацию фреймворка, ни сервис-контейнер.

### Что работает

| Категория | Примеры |
|-----------|---------|
| Встроенные функции PHP | `array_map`, `json_encode`, `preg_match`, `hash`, `mb_*`, `date` |
| Встроенные расширения | `PDO` (создание нового соединения внутри замыкания), `curl_*`, `file_get_contents` |
| Чистые вычисления | Математика, обработка строк, манипуляции с массивами, преобразование данных |
| Скалярные данные через `use` | `string`, `int`, `float`, `bool`, `array` (глубокое копирование) |

```php
<?php
// Работает: создание нового PDO-соединения внутри замыкания
$dsn = 'mysql:host=127.0.0.1;dbname=app';
$user = 'root';
$pass = 'secret';

$p = oxphp_async(function() use ($dsn, $user, $pass): array {
    $pdo = new PDO($dsn, $user, $pass);
    return $pdo->query('SELECT count(*) FROM users')->fetch();
});
```

### Что НЕ работает

| Категория | Почему |
|-----------|--------|
| `DB::connection()`, `app('cache')`, фасады | Сервис-контейнер не инициализирован --- они зависят от начальной загрузки Laravel |
| Автозагрузчик Composer | `vendor/autoload.php` не выполнен --- классы вне встроенных расширений не определены |
| Модели Eloquent, сущности Doctrine | Требуют автозагрузчик + начальную загрузку фреймворка |
| `$_SERVER`, `$_GET`, `$_POST` | Суперглобальные переменные не заполняются в асинхронных воркерах --- у них нет контекста HTTP-запроса |
| Статическое состояние из HTTP-воркера | Статические свойства классов, глобальные переменные --- каждый поток имеет собственную ZTS-копию |
| Объекты через `use` | Объекты невозможно сериализовать между потоками --- выбрасывается `AsyncException` при отправке |

```php
<?php
// Не работает: автозагрузчик недоступен, класс не найден
$p = oxphp_async(function(): void {
    $user = User::find(1);  // Fatal: Class "User" not found
});

// Не работает: сервис-контейнер не инициализирован
$p = oxphp_async(function(): void {
    $db = app('db');  // Fatal: Function "app" not found
});

// Не работает: объекты не могут пересечь границу потока
$pdo = new PDO($dsn, $user, $pass);
$p = oxphp_async(function() use ($pdo): array {
    // AsyncException: Cannot pass object values in use-vars
    return $pdo->query('SELECT 1')->fetch();
});
```

### Обходной путь: передавайте параметры подключения, а не соединения

Поскольку объекты не могут пересекать границы потоков, передавайте необработанные параметры подключения и создавайте соединения внутри замыкания:

```php
<?php
$config = [
    'dsn'  => 'mysql:host=127.0.0.1;dbname=app',
    'user' => 'root',
    'pass' => getenv('DB_PASSWORD'),
];

$promises = [];
foreach ($chunks as $chunk) {
    $promises[] = oxphp_async(function() use ($config, $chunk): int {
        // Каждый асинхронный воркер создаёт собственное соединение
        $pdo = new PDO($config['dsn'], $config['user'], $config['pass']);
        $pdo->beginTransaction();
        foreach ($chunk as $row) {
            $pdo->prepare('UPDATE t SET v=? WHERE id=?')->execute([$row['v'], $row['id']]);
        }
        $pdo->commit();
        return count($chunk);
    }, $chunk);
}

$results = oxphp_async_await_all($promises);
$total = array_sum($results);
```

## Паттерны использования

### Параллельные вычисления

```php
<?php
// Отправка нескольких CPU-ёмких задач
$promises = [];
foreach ($chunks as $i => $chunk) {
    $promises[$i] = oxphp_async(function() use ($chunk): array {
        return array_map('process_record', $chunk);
    });
}

// Сбор всех результатов
$results = oxphp_async_await_all($promises);
```

### Фоновая работа после ответа

```php
<?php
echo json_encode(['status' => 'accepted']);
oxphp_finish_request();

// Ответ отправлен — теперь выполняем фоновую работу параллельно
$p1 = oxphp_async(function() use ($data): void { send_email($data); });
$p2 = oxphp_async(function() use ($data): void { update_analytics($data); });
oxphp_async_await_all([$p1, $p2]);
```

### Обработка результатов в порядке завершения

Используйте `oxphp_async_await_any()` в цикле для обработки промисов по мере их завершения --- самый быстрый первым:

```php
<?php
$promises = [
    oxphp_async(fn() => call_api_a()),  // 500ms
    oxphp_async(fn() => call_api_b()),  // 100ms
    oxphp_async(fn() => call_api_c()),  // 300ms
];

while (!empty($promises)) {
    $winner = oxphp_async_await_any($promises);
    process_result($winner['id'], $winner['value']);

    // Удаляем победителя, продолжаем гонку остальных
    $promises = array_values(
        array_filter($promises, fn($id) => $id !== $winner['id'])
    );
}
// Порядок обработки: api_b (100ms), api_c (300ms), api_a (500ms)
```

Каждая итерация извлекает приёмники из внутренней карты промисов, устраивает гонку с помощью `select_all`, возвращает победителя и помещает оставшиеся приёмники обратно. Ни один промис не теряется и не утекает --- каждый очищается ровно один раз, когда побеждает.

### Защита таймаутом

```php
<?php
$p = oxphp_async(function(): array {
    return fetch_from_slow_api();
});

try {
    $result = oxphp_async_await($p, 2.0); // таймаут 2 секунды
} catch (\OxPHP\AsyncTimeoutException $e) {
    $result = cached_fallback();
}
```
