# Тайм-ауты

OxPHP применяет два независимых тайм-аута, защищающих от медленных клиентов и зависших запросов. Тайм-аут заголовков охраняет фазу подключения на уровне сервера. Время выполнения PHP ограничивается собственной ini-директивой `max_execution_time` (и функцией `set_time_limit()`), точно так же, как на любом другом SAPI.

## Как это работает

Каждый запрос проходит через следующие фазы:

1. **Соединение принято** — запускается тайм-аут заголовков. OxPHP ожидает, пока клиент отправит полный набор HTTP-заголовков.
2. **Заголовки получены** — тайм-аут заголовков заканчивается. Запрос отправляется PHP-воркеру.
3. **PHP обрабатывает запрос** — код приложения выполняется под управлением `max_execution_time` (на основе SIGALRM). При превышении лимита запрос отменяется и срабатывает унифицированная фатальная ошибка `Request cancelled (timeout)`.
4. **Ответ отправлен** — на keep-alive-соединениях цикл повторяется с шага 1.

```text
TCP connect (+ TLS handshake если включён)
  |
  +-- [HEADER_TIMEOUT_SECONDS] --> заголовки получены
                                   |
                                   +-- [max_execution_time] --> ответ отправлен
                                                                    |
                                                                    +-- следующий запрос (keep-alive)
```

На keep-alive-соединениях оба тайм-аута применяются независимо к каждому запросу в соединении.

> **Примечание:** При включённом TLS тайм-аут заголовков запускается после завершения TLS-рукопожатия, а не в момент принятия TCP-соединения.

Тайм-аут заголовков защищает от атак типа slowloris, при которых клиент отправляет заголовки по одному байту, удерживая соединения открытыми неограниченно долго.

Тайминг выполнения PHP полностью делегирован PHP. При превышении `max_execution_time` унифицированный путь отмены OxPHP:

- Устанавливает `connection_status() & PHP_CONNECTION_TIMEOUT`, чтобы userland-код мог определить причину.
- Запускает все обработчики `register_shutdown_function()`, как и PHP-FPM.
- Возвращает HTTP `504 Gateway Timeout` с сообщением `Request cancelled (timeout)`, записанным в журнал ошибок.

### Коды статусов при отмене запроса

OxPHP отменяет запрос по нескольким различным причинам. Каждая отображается в HTTP-статус, отражающий реальную причину, а не обобщённый `500`:

| Причина | Статус | Примечания |
|---------|--------|------------|
| Превышен `max_execution_time` / `set_time_limit()` | `504 Gateway Timeout` | Серверное превышение времени выполнения. |
| Запрос прерван при graceful-остановке сервера | `503 Service Unavailable` | Добавляется заголовок `Retry-After: 5`, чтобы клиенты повторили попытку на восстановившемся или новом инстансе. |
| Клиент закрыл соединение посреди обработки | `499` | nginx-style «Client Closed Request». Соединение уже разорвано, поэтому статус появляется только в access-логе и метриках — клиенту никогда не отправляется. Выводит клиент-инициированные обрывы из категории `5xx`, чтобы они не попадали в алёрты по серверным ошибкам. |
| Воркер признан зависшим супервизором | `500 Internal Server Error` | Обобщённая ошибка сервера — точная причина (deadlock, блокирующий syscall и т. п.) неизвестна. |
| Userland-инициированная отмена | `500 Internal Server Error` | Userland мог сам выставить статус через `http_response_code()` до триггера отмены — этот явный статус сохраняется. |

Если в `ERROR_PAGES_DIR` лежит только `500.html`, добавьте `504.html`, `503.html` и (опционально) `499.html`, чтобы оформление страниц было одинаковым для всех причин отмены.

## Конфигурация

| Переменная | По умолчанию | Описание |
|------------|-------------|----------|
| `HEADER_TIMEOUT_SECONDS` | `5` | Максимальное количество секунд для получения заголовков запроса после принятия соединения. Защищает от атак slowloris. Значение `0` **не** обрабатывается особым образом — оно передаётся в hyper как нулевой тайм-аут, который срабатывает мгновенно. Чтобы отключить тайм-аут, не задавайте переменную, а не устанавливайте её в `0` |

Время выполнения PHP настраивается через `php.ini`, а не переменные окружения OxPHP:

```ini
; php.ini
max_execution_time = 30
```

Или для каждого скрипта во время выполнения:

```php
set_time_limit(60);  // 60 секунд от текущего момента
set_time_limit(0);   // отключить для этого запроса
```

## Рекомендуемые значения

| Сценарий | Тайм-аут заголовков | `max_execution_time` |
|----------|---------------------|----------------------|
| API-сервер | 5с | 30с |
| Обычный веб-сервер | 5с | 60с |
| Загрузка файлов | 10с | 300с |
| SSE / long-polling | 5с | 0 (отключён, для каждого скрипта) |

Корректируйте эти значения исходя из характеристик вашего приложения. Для SSE-эндпоинтов вызывайте `set_time_limit(0)` в начале стримингового скрипта вместо глобального отключения `max_execution_time`.

## Устранение неполадок

### Клиенты неожиданно получают 504 с сообщением `Request cancelled (timeout)`

Лимит времени выполнения PHP сработал до завершения скрипта.

**Исправление:** Увеличьте `max_execution_time` для затронутого скрипта или вызовите `set_time_limit($seconds)` во время выполнения:

```php
// в начале медленного скрипта
set_time_limit(300);
```

Для SSE- или стриминговых эндпоинтов, где соединения должны оставаться открытыми неограниченно долго, отключите таймер для этого скрипта:

```php
set_time_limit(0);
```

### Соединения разрываются до получения заголовков

Тайм-аут заголовков слишком короткий для клиентов с высокой задержкой или за медленными балансировщиками нагрузки.

**Исправление:** Увеличьте тайм-аут заголовков:

```bash
HEADER_TIMEOUT_SECONDS=15
```

### OPcache вызывает тайм-аут первого запроса после изменения скрипта

Перекомпиляция OPcache увеличивает задержку при первом запросе после изменения файла. Это чаще встречается в среде разработки с большим количеством файлов. Увеличьте `max_execution_time` или отключите его в процессе разработки.

## Пример Docker

```yaml
services:
  app:
    image: ghcr.io/oxphp/oxphp:0.8.0
    ports:
      - "8080:8080"
    environment:
      HEADER_TIMEOUT_SECONDS: "5"
    volumes:
      - ./app:/var/www/html:ro
      - ./php.ini:/usr/local/etc/php/conf.d/zz-app.ini:ro
```

С `php.ini`, содержащим:

```ini
max_execution_time = 30
```

## Лучшие практики

- **Никогда не устанавливайте `max_execution_time = 0` глобально в продакшене**, если у вас нет SSE- или long-polling-эндпоинтов, требующих бессрочных соединений. Предпочитайте `set_time_limit(0)` для каждого скрипта.
- **Используйте короткие лимиты для API-серверов.** API имеют предсказуемое время отклика. `max_execution_time` в 30 секунд быстро обнаруживает зависшие запросы, не влияя на обычный трафик.
- **Сочетайте с ограничением частоты запросов.** Тайм-ауты защищают отдельные запросы; ограничение частоты защищает от высокого объёма запросов. Вместе они обеспечивают комплексную защиту от медленных и быстрых атак.
