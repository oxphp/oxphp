# Журнал доступа

OxPHP записывает структурированные JSON-логи доступа для каждого HTTP-запроса в stdout. Ведение журнала выполняется асинхронно и никогда не блокирует обработку запросов.

## Как это работает

1. Если переменная `ACCESS_LOG` установлена, OxPHP записывает одну строку JSON в stdout после завершения каждого запроса.
2. Записи в журнал буферизируются в фоновом потоке записи и никогда не блокируют конвейер обработки запросов.
3. `ACCESS_LOG=all` логирует каждый запрос. `ACCESS_LOG=error` логирует только ответы со статусом 400 и выше.
4. Каждая строка лога включает поле `request_id`, которое позволяет сопоставить записи журнала доступа с логами вашего приложения.
5. Когда включено распространение трассировки W3C Trace Context, записи журнала также содержат поля `trace_id` и `span_id`.

## Конфигурация

| Переменная | По умолчанию | Описание |
|------------|-------------|----------|
| `ACCESS_LOG` | *(не задана)* | Режим журнала доступа. `all` — логировать каждый запрос; `error` — только ответы 4xx и 5xx. Оставьте пустым или не задавайте для отключения |

> **Примечание:** Допустимые значения — только `all` и `error`. При указании нераспознанного значения выводится предупреждение и ведение журнала доступа отключается.

## Формат записей

Каждая запись журнала доступа — одна строка JSON, записываемая в stdout:

```json
{
  "timestamp": "2026-02-11T12:34:56.789012Z",
  "level": "INFO",
  "fields": {
    "request_id": "67890abc12341a2b0042",
    "method": "GET",
    "path": "/api/users",
    "status": 200,
    "duration_us": 1234,
    "remote_addr": "10.0.0.1:54321",
    "message": "request completed"
  }
}
```

При активном W3C Trace Context поля `trace_id` и `span_id` добавляются рядом со стандартными полями:

```json
{
  "timestamp": "2026-02-11T12:34:56.789012Z",
  "level": "INFO",
  "fields": {
    "request_id": "67890abc12341a2b0042",
    "trace_id": "4bf92f3577b34da6a3ce929d0e0e4736",
    "span_id": "00f067aa0ba902b7",
    "method": "POST",
    "path": "/api/orders",
    "status": 201,
    "duration_us": 8421,
    "remote_addr": "10.0.0.1:54322",
    "message": "request completed"
  }
}
```

## Поля

| Поле | Тип | Описание |
|------|-----|----------|
| `request_id` | строка | Уникальный идентификатор запроса. См. [Идентификаторы запросов](request-ids.md) |
| `method` | строка | HTTP-метод (`GET`, `POST` и т.д.) |
| `path` | строка | Путь URI запроса |
| `status` | число | Код статуса HTTP-ответа |
| `duration_us` | число | Общее время обработки запроса в микросекундах |
| `remote_addr` | строка | IP-адрес и порт клиента. Когда `TRUSTED_PROXIES` настроен, показывает реальный IP клиента, извлечённый из заголовков пересылки, а не IP прокси |
| `trace_id` | строка | W3C trace ID (присутствует только при `TRACE_CONTEXT=true`) |
| `span_id` | строка | W3C span ID (присутствует только при `TRACE_CONTEXT=true`) |

## Тонкая фильтрация

OxPHP использует внутреннюю цель логирования `access_log` для записей журнала доступа. Используйте переменную `RUST_LOG` для независимой фильтрации журналов доступа от остального вывода логов:

```bash
# Подавить общие информационные сообщения, сохранить журналы доступа
RUST_LOG=warn,access_log=info
```

> **Примечание:** Цель `access_log` используется для фильтрации на уровне `RUST_LOG`, но не включается в JSON-вывод. Для идентификации записей журнала доступа в downstream-системах используйте поле `"message": "request completed"` и набор характерных полей (`method`, `path`, `status`, `duration_us`).

## Устранение неполадок

### Записи журнала доступа не появляются

Журнал доступа отключён, если переменная `ACCESS_LOG` не задана или пуста.

**Исправление:** Установите переменную в значение `all` или `error`:

```bash
ACCESS_LOG=all
```

### Журнал доступа в режиме `error`, но успешные запросы отсутствуют

`ACCESS_LOG=error` логирует только ответы со статусом 400 и выше. Это ожидаемое поведение — проверьте значение и переключитесь на `all`, если нужно логировать все запросы.

**Проверьте:** Подтвердите активную настройку:

```bash
curl -s http://localhost:9090/config | jq '.access_log'
```

### Записи журнала не содержат `trace_id` и `span_id`

Поля контекста трассировки присутствуют только при включённом распространении W3C Trace Context.

**Исправление:** Включите с помощью:

```bash
TRACE_CONTEXT=true
```

И убедитесь, что вышестоящий клиент или балансировщик нагрузки отправляет заголовок `traceparent` в запросах.

## Пример Docker

```yaml
services:
  app:
    image: ghcr.io/oxphp/oxphp:0.5.0
    ports:
      - "80:80"
      - "9090:9090"
    volumes:
      - ./src:/var/www/html:ro
    environment:
      ACCESS_LOG: "all"
      ENTRY_FILE: "index.php"
      INTERNAL_ADDR: "0.0.0.0:9090"
```

## Лучшие практики

- Используйте `ACCESS_LOG=error` в продакшене для снижения объёма логов, при этом сохраняя фиксацию всех неудачных запросов. Успешные запросы не логируются, но ошибки при статусе 400 и выше всегда фиксируются.
- Включайте идентификатор запроса в логи приложения через `oxphp_request_id()`, чтобы сопоставлять записи PHP-уровня с записями журнала доступа.
- Используйте структурированный агрегатор логов — например, Elasticsearch, Loki или Datadog — для эффективного запроса и фильтрации строк JSON-логов.

## Интеграция

Поскольку логи представляют собой строки JSON в stdout, они напрямую интегрируются с драйверами логов контейнеров и инструментами агрегации:

- **Docker** — собираются автоматически через драйвер логов контейнера (json-file, fluentd и другие)
- **Kubernetes** — подхватываются агентом логов узла (Fluentd, Fluent Bit, Filebeat и другие)
- **systemd** — захватываются при запуске в виде systemd-службы с логированием в stdout через journald

Дополнительные sidecar-контейнеры или доставка логов через файлы не требуются.
