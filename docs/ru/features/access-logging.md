title: Журнал доступа

OxPHP создаёт структурированную JSON-запись для каждого завершённого HTTP-запроса. Журналы записываются в stdout с использованием неблокирующего фонового писателя, поэтому ввод-вывод журналирования никогда не блокирует конвейер обработки запросов.

## Настройка

| Переменная | Описание | По умолчанию |
|------------|----------|--------------|
| `ACCESS_LOG` | Включить журналирование каждого запроса | `true` |
| `LOG_LEVEL` | Минимальный уровень логирования (trace, debug, info, warn, error) | `info` |

Журналирование доступа включено по умолчанию. Когда `ACCESS_LOG` установлено в `false`, `0` или `off`, `AccessLogHandler` не регистрируется в диспетчере событий и записи журнала доступа для отдельных запросов не создаются.

```bash
# Отключить журналирование доступа
ACCESS_LOG=false

LOG_LEVEL=info
```

Переменная окружения `RUST_LOG` также поддерживается и имеет приоритет над `LOG_LEVEL`, если задана. Это соответствует стандартному соглашению `tracing`/`env_filter`.

## Формат журнала

Каждая запись журнала доступа — это одна JSON-строка, записываемая в stdout:

```json
{
  "timestamp": "2026-02-11T12:34:56.789Z",
  "level": "INFO",
  "fields": {
    "request_id": "67890abc00000042",
    "method": "GET",
    "path": "/api/users",
    "status": 200,
    "duration_us": 1234,
    "remote_addr": "10.0.0.1:54321",
    "message": "request completed"
  }
}
```

### Поля

| Поле | Тип | Описание |
|------|-----|----------|
| `request_id` | string | Уникальный идентификатор запроса (см. [Идентификаторы запросов](/ru/features/request-ids/)) |
| `method` | string | HTTP-метод (`GET`, `POST` и т.д.) |
| `path` | string | Путь URI запроса |
| `status` | number | Код состояния HTTP-ответа |
| `duration_us` | number | Общее время обработки запроса в микросекундах |
| `remote_addr` | string | IP-адрес и порт клиента |

## Как это работает

Журнал доступа реализован как обработчик событий, слушающий события `RequestComplete` с приоритетом **100** (выполняется последним среди обработчиков с тем же приоритетом). Обработчик вызывает `tracing::info!` с целью `access_log`.

Инфраструктура логирования использует:

- **tracing** для структурированной генерации событий
- **tracing-subscriber** с JSON-форматированием для вывода
- **tracing-appender** с неблокирующим писателем для асинхронного ввода-вывода

Неблокирующий писатель запускает выделенный фоновый поток, который буферизует записи журнала и сбрасывает их в stdout. `WorkerGuard`, возвращаемый при инициализации, должен удерживаться до завершения работы, чтобы все буферизованные записи были сброшены.

## Цели журналирования

OxPHP использует разные цели tracing для разных типов журналов:

- `access_log` — записи журнала доступа для каждого запроса
- Цель по умолчанию — события жизненного цикла сервера, ошибки, предупреждения

Вы можете использовать `RUST_LOG` для независимого управления ими:

```bash
# Показывать журналы доступа на уровне info, подавить остальные info-сообщения
RUST_LOG=warn,access_log=info
```

## Интеграция с агрегаторами журналов

Поскольку журналы представляют собой JSON-строки в stdout, они напрямую интегрируются с драйверами логирования контейнеров и инструментами агрегации:

- **Docker**: собираются автоматически через драйвер логирования контейнера
- **Kubernetes**: подхватываются агентом логирования узла (Fluentd, Fluent Bit и др.)
- **journald**: захватываются при работе в качестве systemd-сервиса с логированием в stdout

Не требуется ни sidecar-контейнер, ни файловая пересылка журналов.
