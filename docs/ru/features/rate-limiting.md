# Ограничение частоты запросов

OxPHP включает встроенный ограничитель частоты запросов по IP, не требующий внешних зависимостей или инфраструктуры. При включении он отслеживает количество запросов от каждого клиентского IP и возвращает ответ `429 Too Many Requests`, когда клиент превышает настроенный порог.

## Как это работает

Ограничитель частоты использует счётчик фиксированного окна с ключом по клиентскому IP-адресу. Каждый IP получает собственный независимый счётчик и окно.

1. Когда поступает запрос, OxPHP ищет клиентский IP в своём внутреннем трекере.
2. Если запись не найдена или текущее окно истекло, начинается новое окно с нулевым счётчиком.
3. Счётчик увеличивается для каждого запроса.
4. Если счётчик превышает `RATE_LIMIT`, сервер немедленно возвращает ответ `429` с заголовками ограничения частоты. Запрос отклоняется до маршрутизации или выполнения PHP.

Запросы, превысившие лимит, по-прежнему отображаются в логах доступа и метриках.

## Конфигурация

| Переменная | По умолчанию | Описание |
|------------|--------------|----------|
| `RATE_LIMIT` | `0` | Максимальное количество запросов от одного IP в пределах окна. `0` полностью отключает ограничение частоты без каких-либо накладных расходов |
| `RATE_WINDOW_SECONDS` | `60` | Продолжительность окна ограничения частоты в секундах |

```bash
# Разрешить 100 запросов с одного IP в течение 60-секундного окна
RATE_LIMIT=100
RATE_WINDOW_SECONDS=60
```

## Заголовки ответа

Отклонённые запросы возвращают ответ `429 Too Many Requests` со следующими заголовками:

| Заголовок | Описание |
|-----------|----------|
| `Retry-After` | Секунды до сброса текущего окна |
| `x-ratelimit-limit` | Максимальное количество запросов, разрешённых за окно |
| `x-ratelimit-remaining` | Оставшееся количество запросов в текущем окне (`0` при превышении лимита) |
| `x-ratelimit-reset` | Секунды до сброса текущего окна |
| `x-request-id` | Идентификатор запроса для сопоставления этого ответа с логами доступа |

Пример ответа `429`:

```http
HTTP/1.1 429 Too Many Requests
Retry-After: 45
x-ratelimit-limit: 100
x-ratelimit-remaining: 0
x-ratelimit-reset: 45
x-request-id: 67e2a1f412341a2b0042

429 Too Many Requests
```

## Устранение неполадок

> **За обратным прокси?** Установите `TRUSTED_PROXIES`, чтобы rate limiting использовал реальный IP клиента вместо IP прокси. См. [Доверенные прокси](../security/trusted-proxies.md).

### Легитимные пользователи превышают лимит запросов

Ваш порог может быть слишком низким для реальных паттернов трафика. Проверьте количество ответов 429 в ваших метриках и соответствующим образом скорректируйте `RATE_LIMIT` или `RATE_WINDOW_SECONDS`.

**Проверка** количества запросов с превышением лимита:

```bash
curl http://localhost:9090/metrics | grep rate_limited
```

**Решение:** Увеличьте `RATE_LIMIT` или расширьте `RATE_WINDOW_SECONDS`, чтобы предоставить клиентам больше запасного пространства.

### Пользователи за корпоративным NAT используют общий счётчик IP

OxPHP ограничивает частоту по исходному IP. Все пользователи за общим NAT или прокси используют один счётчик. Если это создаёт проблемы, рассмотрите возможность отключения встроенного ограничителя OxPHP (`RATE_LIMIT=0`) и применения ограничения частоты на более высоком уровне (например, на балансировщике нагрузки или API-шлюзе), где у вас есть доступ к идентификаторам пользователей.

### Ограничение частоты не работает между несколькими экземплярами

Ограничитель частоты OxPHP хранится в памяти и является per-экземплярным. Если вы запускаете несколько экземпляров OxPHP за балансировщиком нагрузки, каждый отслеживает собственные независимые счётчики. Клиент может отправить `RATE_LIMIT` запросов на каждый экземпляр, не вызвав 429. Для скоординированного ограничения частоты между экземплярами используйте внешний ограничитель на уровне балансировщика нагрузки или API-шлюза.

### Память растёт при атаках с ротацией IP

OxPHP отслеживает до 100 000 уникальных IP-адресов. При достижении этого лимита перед добавлением новых записей выполняется очистка устаревших. Если вы наблюдаете рост памяти из-за злоумышленника, быстро меняющего IP, автоматическая очистка ограничивает воздействие до фиксированного объёма памяти.

## Пример Docker

```yaml
services:
  app:
    image: ghcr.io/oxphp/oxphp:0.2.0
    ports:
      - "8080:80"
    environment:
      RATE_LIMIT: "100"
      RATE_WINDOW_SECONDS: "60"
    volumes:
      - ./app:/var/www/html:ro
```

## Лучшие практики

- **Начинайте с консервативных значений.** Установите более низкий лимит (например, 60 запросов в минуту) и увеличивайте его на основе наблюдаемых паттернов трафика. Ослабить ограничения проще, чем восстановиться после перегруженного сервера.
- **Используйте общий ограничитель частоты для развёртывания с несколькими экземплярами.** Ограничитель частоты OxPHP является per-экземплярным. Для скоординированного ограничения между экземплярами применяйте ограничение частоты на уровне балансировщика нагрузки или API-шлюза.
- **Отслеживайте количество ответов 429.** Следите за долей запросов с превышением лимита в ваших метриках для обнаружения неправильно настроенных порогов или неожиданных всплесков трафика.

## Примечания

- **Алгоритм фиксированного окна.** Ограничитель использует счётчик фиксированного окна, а не скользящее окно. Клиент может отправить до `2x` от настроенного лимита в виде всплеска на границе между двумя окнами.
- **Только по IP.** Ограничение частоты привязано к исходному IP-адресу. Настраиваемые ключи, такие как API-ключ или идентификатор пользователя, не поддерживаются.
- **Состояние в памяти.** Счётчики ограничения частоты не разделяются между несколькими экземплярами OxPHP.
- **Автоматическая очистка.** Устаревшие записи очищаются, когда трекер превышает 100 000 IP, удаляя все записи с истёкшими окнами.
