title: Совместимость с OPcache

OPcache работает с OxPHP без дополнительной настройки. PHP-скрипты компилируются один раз и кэшируются в разделяемой памяти, повторно используясь всеми потоками воркеров в течение всего времени жизни серверного процесса.

## Как это работает

OxPHP использует пользовательский SAPI, который идентифицирует себя для PHP как `cli-server`. OPcache распознаёт это имя SAPI, но по умолчанию не активируется для cli-server SAPI. Поставляемый в комплекте `oxphp.ini` включает `opcache.enable_cli = 1`, что и обеспечивает активацию OPcache для этого SAPI. Без этой настройки OPcache не будет активироваться независимо от остальной конфигурации.

Поскольку OxPHP использует PHP ZTS (Zend Thread Safety), все потоки воркеров разделяют один и тот же сегмент разделяемой памяти OPcache. Скрипт, скомпилированный одним воркером, немедленно становится доступным всем остальным воркерам. Это обеспечивает поведение «компиляция один раз --- выполнение многократно» OPcache с конкурентностью нескольких потоков воркеров.

## Требование времени запроса

Функция `file_update_protection` OPcache предотвращает кэширование файлов, которые были изменены совсем недавно (по умолчанию в течение последних 2 секунд). Во время инициализации каждого запроса OPcache сравнивает время модификации файла с текущим временем запроса.

SAPI OxPHP предоставляет callback `get_request_time`, который возвращает текущую Unix-метку времени. Этот callback вызывается PHP во время `php_request_startup()`, что означает, что время запроса **должно** быть доступно до этого момента.

### Что происходит без времени запроса

Если время запроса возвращает `0` (нулевую эпоху), проверка защиты файлов OPcache сравнивает `mtime` каждого файла с 1 января 1970 года. Поскольку все файлы были изменены после этой даты, OPcache считает их «слишком новыми» и отказывается кэшировать. Результат --- **0% попаданий в кэш** --- каждый запрос перекомпилирует каждый скрипт.

OxPHP избегает этого, реализуя callback SAPI `get_request_time`, который возвращает `SystemTime::now()` как Unix-метку времени с точностью до микросекунд.

## Проверка статуса OPcache

Создайте диагностический скрипт для подтверждения того, что OPcache активен:

```php
<?php
// www/opcache_check.php
if (!function_exists('opcache_get_status')) {
    echo "OPcache extension is not loaded\n";
    exit(1);
}

$status = opcache_get_status();

echo "OPcache enabled: " . ($status['opcache_enabled'] ? 'yes' : 'no') . "\n";
echo "Cached scripts:  " . $status['opcache_statistics']['num_cached_scripts'] . "\n";
echo "Cache hits:      " . $status['opcache_statistics']['hits'] . "\n";
echo "Cache misses:    " . $status['opcache_statistics']['misses'] . "\n";
echo "Hit rate:        " . round($status['opcache_statistics']['opcache_hit_rate'], 1) . "%\n";
echo "Memory used:     " . round($status['memory_usage']['used_memory'] / 1048576, 1) . " MB\n";
echo "Memory free:     " . round($status['memory_usage']['free_memory'] / 1048576, 1) . " MB\n";
```

Протестируйте его:

```bash
curl http://localhost:8080/opcache_check.php
# Первый запрос: промах (скрипт компилируется и кэшируется)
curl http://localhost:8080/opcache_check.php
# Второй запрос: попадание (скрипт обслуживается из кэша)
```

Исправно работающий OPcache показывает процент попаданий, стремящийся к 100% после начального периода прогрева.

## JIT-компиляция

JIT-компилятор OPcache поддерживается при использовании PHP 8.0+. Включите его в вашем `php.ini`:

```ini
opcache.enable=1
opcache.jit=tracing
opcache.jit_buffer_size=64M
```

JIT даёт наибольшую пользу для CPU-интенсивного PHP-кода (математика, циклы, обработка строк). Для приложений с интенсивным вводом-выводом (запросы к базе данных, вызовы API) улучшение минимально.

## Рекомендуемые настройки

Эти настройки соответствуют поставляемому `oxphp.ini` и оптимизированы для продакшен-деплоев в контейнерах, где PHP-файлы не изменяются во время выполнения:

```ini
[opcache]
opcache.enable=1
opcache.enable_cli=1
opcache.memory_consumption=128
opcache.max_accelerated_files=10000
opcache.validate_timestamps=0
opcache.revalidate_freq=0
opcache.file_update_protection=0
opcache.save_comments=1
opcache.jit=tracing
opcache.jit_buffer_size=64M
```

| Настройка | Описание |
|-----------|----------|
| `enable_cli` | Обязательно для активации OPcache с cli-server SAPI, используемым OxPHP. |
| `memory_consumption` | Объём разделяемой памяти в МБ для скомпилированных скриптов. Увеличьте, если `opcache_get_status()` показывает мало свободной памяти. |
| `max_accelerated_files` | Максимальное количество кэшированных скриптов. Установите выше общего количества `.php`-файлов. |
| `validate_timestamps` | При значении `0` OPcache никогда не проверяет файловую систему на наличие изменений после кэширования скрипта. Для применения изменений кода необходимо перезапустить контейнер (или вызвать `opcache_reset()`). |
| `revalidate_freq` | Интервал в секундах между проверками модификации файлов. Применяется только при `validate_timestamps=1`. |
| `file_update_protection` | Секунды после модификации файла до его кэширования. Установите `0` в продакшене, чтобы избежать окна защиты. |
| `save_comments` | Сохранять doc-комментарии в кэшированных скриптах. Требуется фреймворками, использующими маршрутизацию на основе аннотаций (например, Symfony, Laravel). |

Это продакшен-оптимизированные настройки, предполагающие неизменность PHP-файлов в течение всего срока жизни контейнера. Для разработки можно использовать `validate_timestamps=1` и `revalidate_freq=2`, чтобы изменения кода вступали в силу без перезапуска сервера.

## ZTS и разделяемая память

OxPHP запускает PHP в режиме ZTS, где каждый поток воркера имеет собственный контекст выполнения, но все потоки разделяют один и тот же сегмент разделяемой памяти OPcache. Это означает:

- Скрипт, скомпилированный воркером 0, немедленно доступен воркерам 1, 2, 3 и т.д.
- Внутренние блокировки OPcache обеспечивают безопасную конкурентную компиляцию.
- Потребление памяти не масштабируется с количеством воркеров --- одна копия каждого скомпилированного скрипта обслуживает все потоки.

Это более эффективно по памяти, чем PHP-FPM, где каждый процесс поддерживает собственный сегмент OPcache (если только вы не используете `opcache.file_cache` с `file_cache_only=1` для разделяемого хранилища).
