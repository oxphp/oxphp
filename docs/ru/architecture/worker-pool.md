OxPHP выполняет PHP-скрипты в пуле выделенных потоков ОС, изолированных от асинхронной среды выполнения ввода-вывода. На этой странице рассматриваются трейт `ScriptExecutor`, архитектура ограниченного канала, поведение обратного давления и автоматическое масштабирование воркеров.

## Трейт ScriptExecutor

Все бэкенды выполнения PHP реализуют трейт `ScriptExecutor`, определённый в `src/executor/mod.rs`:

```rust
pub trait ScriptExecutor: Send + Sync {
    fn execute(&self, request: ScriptRequest) -> ExecuteResult;

    fn shutdown(&self);

    fn is_healthy(&self) -> bool {
        true
    }

    fn start_scale_manager(&self) {}
}
```

| Метод | Назначение |
|---|---|
| `execute()` | Принимает запрос и возвращает `ExecuteResult` (немедленный или отложенный ответ) |
| `shutdown()` | Сигнализирует исполнителю о прекращении приёма работы |
| `is_healthy()` | Проверка состояния для внутренней точки `/health` |
| `start_scale_manager()` | Запускает фоновую задачу масштабирования (no-op в stub; статический режим порождает монитор здоровья) |

Трейт возвращает `ExecuteResult`, а не сырой `Future` или `oneshot::Receiver`. Это позволяет исполнителю немедленно вернуть ответ с ошибкой (например, 503 при заполненной очереди) без привлечения потока воркера, при этом поддерживая отложенный случай, когда задача Tokio ожидает `oneshot::Receiver` для ответа.

```rust
pub enum ExecuteResult {
    Immediate(ScriptResponse),
    Deferred(tokio::sync::oneshot::Receiver<ScriptResponse>),
}
```

## Типы данных

Запросы и ответы определены в `src/types.rs`:

```rust
pub struct ScriptRequest {
    pub request_id: String,
    pub script_path: PathBuf,
    pub method: Method,
    pub uri: Uri,
    pub query_string: String,
    pub headers: HeaderMap,
    pub body: Bytes,
    pub remote_addr: SocketAddr,
    pub document_root: Arc<PathBuf>,
}

pub struct ScriptResponse {
    pub status: u16,
    pub headers: Vec<(HeaderName, HeaderValue)>,
    pub body: Bytes,
    pub execution_time_us: u64,
}
```

`document_root` обёрнут в `Arc<PathBuf>` для эффективного разделения между запросами. `headers` в ответе используют `Vec` (не `HeaderMap`), поскольку воркер PHP предварительно разбирает строки заголовков в типизированные пары `HeaderName`/`HeaderValue` в потоке воркера, избегая затрат на разбор в среде выполнения Tokio.

## SapiExecutor

Продакшен-исполнитель (`src/executor/sapi.rs`, за feature-гейтом `--features php`) управляет пулом потоков воркеров PHP ZTS, подключённых через ограниченный `crossbeam_channel`. Он поддерживает два режима работы: **статический** (фиксированный размер пула) и **динамический** (автоматическое масштабирование в пределах min/max).

### Архитектура

```
                         ┌──────────────────────┐
                         │   crossbeam_channel  │
Tokio tasks ──try_send──▶│   bounded(CAPACITY)  │──recv──▶ php-worker-0
             (non-block) │                      │──recv──▶ php-worker-1
                         │                      │──recv──▶ php-worker-N
                         └──────────────────────┘
                                                          ▲
                         ┌──────────────────────┐         │
                         │   ScaleManager       │─────────┘
                         │   (tokio task,       │  spawn/retire workers
                         │    dynamic mode only)│  based on idle count
                         └──────────────────────┘

Each worker:
  ┌──────────────────────────────────────────────────┐
  │  recv(WorkerRequest)                             │
  │    ├── sapi::clear_buffers()                     │
  │    ├── sapi::set_request_data(request)           │
  │    ├── php_request_startup()                     │
  │    ├── zend_stream_init_filename(file_handle)    │
  │    ├── php_execute_script(file_handle)           │
  │    ├── zend_destroy_file_handle(file_handle)     │
  │    ├── php_request_shutdown()                    │
  │    ├── sapi::take_response() → (output, headers) │
  │    └── tx.send(ScriptResponse)                   │
  └──────────────────────────────────────────────────┘
```

### Режимы воркеров

Переменная окружения `PHP_WORKERS` управляет режимом пула воркеров:

| Формат | Режим | Пример | Поведение |
|--------|-------|--------|-----------|
| `N` | Статический | `PHP_WORKERS=8` | Фиксированный пул из 8 воркеров |
| `0` или не задано | Статический | `PHP_WORKERS=0` | Фиксированный пул из CPU count / 2 воркеров (мин. 1) |
| `MIN:MAX` | Динамический | `PHP_WORKERS=2:16` | Начинает с MIN, масштабируется до MAX под нагрузкой |
| `MIN:0` | Динамический | `PHP_WORKERS=2:0` | MIN задан явно, MAX определяется автоматически (CPU count * 2) |
| `0:0` | Динамический | `PHP_WORKERS=0:0` | MIN автоматически (CPU/4, минимум 1), MAX автоматически (CPU * 2) |

В **статическом режиме** размер пула не меняется после запуска. Воркеры используют блокирующий `recv()` с нулевым потреблением CPU в состоянии простоя.

В **динамическом режиме** фоновая задача ScaleManager периодически проверяет утилизацию воркеров и порождает или выводит воркеры из работы. Воркеры используют `recv_timeout(200ms)` для периодической проверки флага остановки.

### Последовательность запуска

Конструктор `SapiExecutor::new(metrics)` выполняет инициализацию PHP в главном потоке до создания каких-либо потоков воркеров:

1. **Запуск TSRM**: `php_tsrm_startup()` инициализирует Zend Thread Safety. Это должно произойти в главном потоке до установки обработчиков сигналов асинхронной среды выполнения.
2. **Регистрация SAPI**: `sapi_startup()` регистрирует пользовательский SAPI-модуль `oxphp`.
3. **Запуск движка PHP**: `php_module_startup()` инициализирует движок PHP, загружает расширения и разбирает `php.ini`. Это запускает MINIT для всех расширений, включая расширение OxPHP, которое регистрирует функции плагинов в Zend.
4. **Обработчик ошибок**: `sapi::install_error_cb()` заменяет стандартный обработчик ошибок на структурированное JSON-логирование.
5. **Разбор режима воркеров**: `parse_php_workers()` считывает `PHP_WORKERS` и возвращает `WorkerMode::Static(n)` или `WorkerMode::Dynamic { min, max }`.
6. **Создание канала**: `crossbeam_channel::bounded(queue_capacity)` создаёт ограниченную очередь работы. Ёмкость по умолчанию — `worker_count * 128` (используется min для динамического режима).
7. **Порождение воркеров**: Начальные воркеры порождаются — полное количество для статического режима или `min` для динамического. Каждый обёрнут в структуру `ManagedWorker`.
8. **Инициализация метрик**: Устанавливаются `metrics.set_workers_min/max/current` для отражения начального состояния пула.

### ManagedWorker

Каждый воркер отслеживается структурой `ManagedWorker`:

```rust
struct ManagedWorker {
    id: usize,                       // Уникальный ID (для отладочного отображения)
    handle: JoinHandle<()>,          // Дескриптор потока ОС
    shutdown: Arc<AtomicBool>,       // Флаг остановки для конкретного воркера
    last_active: Arc<AtomicU64>,     // Epoch в мс последнего запроса (только динамический режим)
}
```

Флаг `shutdown` позволяет выводить отдельные воркеры из работы без закрытия общего канала. Временная метка `last_active` используется ScaleManager для определения простаивающих воркеров при масштабировании вниз.

### Жизненный цикл потока воркера

Каждый поток воркера:

1. Инициализирует потоколокальное хранилище TSRM через `ts_resource_ex()`
2. Входит в цикл приёма (зависит от режима):
   - **Статический режим**: Блокирующий `while let Ok(wr) = request_rx.recv()` — нулевое потребление CPU при простое
   - **Динамический режим**: `recv_timeout(200ms)` с периодической проверкой флага `shutdown` и обновлением `last_active`
3. Для каждого запроса:
   - Очищает буферы вывода через `sapi::clear_buffers()`
   - Устанавливает данные запроса (состояние SAPI, суперглобальные переменные) через `sapi::set_request_data()`
   - Создаёт `RequestDataGuard` (RAII — очищает данные SAPI при drop, даже при панике)
   - Вызывает `php_request_startup()` (запускает RINIT для всех расширений)
   - Открывает файл скрипта через `zend_stream_init_filename()`
   - Выполняет через `php_execute_script()`
   - Уничтожает дескриптор файла через `zend_destroy_file_handle()`
   - Вызывает `php_request_shutdown()` (запускает RSHUTDOWN)
   - Собирает ответ: буфер вывода, заголовки, код статуса через `sapi::take_response()`
   - Разбирает строки заголовков в типизированные пары `HeaderName`/`HeaderValue` в потоке воркера
   - Отправляет ответ через oneshot-канал
4. Условия выхода:
   - **Статический режим**: Отправитель канала удалён (остановка), `recv()` возвращает `Err`
   - **Динамический режим**: Флаг `shutdown` установлен ScaleManager или канал отключён

### ScaleManager (динамический режим)

В **статическом режиме** `start_scale_manager()` порождает задачу монитора здоровья воркеров, а не no-op. Монитор здоровья периодически проверяет наличие упавших воркеров (воркеров, чей поток ОС неожиданно завершился) и пересоздаёт их для поддержания заданного целевого количества. Это предотвращает постоянное уменьшение ёмкости пула из-за аварийного завершения воркера.

Когда настроен `PHP_WORKERS=MIN:MAX`, `start_scale_manager()` вместо этого порождает задачу автоматического масштабирования ScaleManager. ScaleManager работает в среде выполнения Tokio и проверяет утилизацию воркеров каждые 500 мс:

**Масштабирование вверх** (все условия должны быть выполнены):
- Обнаружено ноль простаивающих воркеров (простаивающий = last_active > 200 мс назад)
- Текущее количество воркеров ниже MAX
- Прошло не менее 500 мс с последнего масштабирования вверх

**Масштабирование вниз** (все условия должны быть выполнены):
- Текущее количество воркеров выше MIN
- Воркер простаивает дольше `PHP_WORKERS_IDLE_SEC` (по умолчанию 30 с)
- Прошло не менее 5 секунд с последнего масштабирования вниз

ScaleManager снимает блокировку Mutex перед порождением новых потоков ОС, чтобы не блокировать среду выполнения Tokio. Выведенные из работы воркеры присоединяются в фоновом потоке.

### Конфигурация

| Переменная | По умолчанию | Описание |
|---|---|---|
| `PHP_WORKERS` | `0` (CPU count / 2, мин. 1, статический) | Режим пула воркеров. `N` для статического, `MIN:MAX` для динамического |
| `PHP_WORKERS_IDLE_SEC` | `30` | Тайм-аут простоя до вывода динамического воркера из работы |
| `QUEUE_CAPACITY` | `PHP_WORKERS * 128` | Ёмкость ограниченного канала (используется начальное количество для динамического режима) |

## Режим воркера (Persistent PHP)

Режим воркера --- это альтернативная модель выполнения, в которой PHP-процессы остаются живыми между запросами, избегая накладных расходов на `php_request_startup()` / `php_request_shutdown()` при каждом запросе. Этот режим включается установкой переменной окружения `WORKER_FILE`.

### Как это работает

Вместо стандартного жизненного цикла на каждый запрос (startup -> execute -> shutdown), режим воркера выполняет один PHP-скрипт, который вызывает `oxphp_worker()` с callback-обработчиком. Обработчик вызывается для каждого запроса, а между запросами **мягкий сброс** очищает состояние текущего запроса без уничтожения PHP-кучи:

```
Жизненный цикл потока воркера:

  php_request_startup()           <- выполняется ОДИН РАЗ
  require worker.php              <- начальная загрузка: autoload, подключение к БД, конфигурация
  oxphp_worker(function() {       <- вход в цикл воркера
      +-----------------------------+
      | ожидание запроса             | <- блокировка на crossbeam-канале
      | мягкий сброс                | <- обновление суперглобалов, очистка вывода
      | вызов handler()             | <- выполнение пользовательского кода
      | отправка ответа             | <- ответ на HTTP-уровень
      | проверка лимитов            | <- max_requests, max_memory
      +-----------------------------+
      | цикл назад ^                |
  })
  php_request_shutdown()          <- выполняется ОДИН РАЗ (при выходе)
```

Мягкий сброс между запросами:
- Заполняет `$_GET`, `$_POST`, `$_SERVER`, `$_COOKIE`, `$_FILES` данными нового запроса
- Очищает и сбрасывает буферы вывода
- Сбрасывает заголовки и код статуса HTTP-ответа
- Вызывает и очищает обработчики `register_shutdown_function()`

### Рециклирование

Воркеры рециклируются (завершаются и пересоздаются) на основе настраиваемых лимитов:

| Причина выхода | Триггер | Метка метрики |
|---|---|---|
| `max_requests` | Достигнут `WORKER_MAX_REQUESTS` | `reason="max_requests"` |
| `max_memory` | Превышен `WORKER_MAX_MEMORY` (МиБ) | `reason="max_memory"` |
| `error` | Неперехваченное исключение или фатальная ошибка в обработчике | `reason="error"` |
| `shutdown` | Плавная остановка сервера | *(не считается рециклированием)* |

Когда воркер завершается не по причине остановки, монитор здоровья (статический режим) или ScaleManager (динамический режим) автоматически пересоздаёт его. Новый воркер повторно выполняет весь скрипт воркера, включая начальную загрузку.

### Метрики

Режим воркера предоставляет выделенные метрики Prometheus для мониторинга состояния персистентных воркеров:

- **`oxphp_worker_requests_handled_total`** --- общее количество обработанных запросов всеми воркерами
- **`oxphp_worker_recycles_total`** / **`oxphp_worker_recycles_by_reason_total`** --- количество рециклирований, глобально и по причине
- **`oxphp_worker_memory_bytes{worker="N"}`** --- текущее использование PHP-кучи для каждого воркера
- **`oxphp_worker_uptime_seconds{worker="N"}`** --- время с момента создания каждого воркера
- **`oxphp_worker_request_duration_us`** --- гистограмма времени выполнения PHP-обработчика (без времени ожидания в очереди)

Полный справочник и примеры PromQL-запросов см. в разделе [Метрики](../operations/metrics.md#режим-воркера).

### Конфигурация

| Переменная | По умолчанию | Описание |
|---|---|---|
| `WORKER_FILE` | *(нет)* | Путь к PHP-скрипту воркера (относительно `DOCUMENT_ROOT`). Включает режим воркера при установке |
| `WORKER_MAX_REQUESTS` | `0` | Максимальное количество запросов до рециклирования. `0` = без лимита |
| `WORKER_MAX_MEMORY` | `0` | Максимальная память (МиБ) до рециклирования. `0` = без лимита |

### Интеграция с маршрутизацией

Когда `WORKER_FILE` установлен, маршрутизация изменяется: запросы к нестатическим файлам, не совпадающие с файлами на диске, направляются в скрипт воркера вместо возврата 404. Статические файлы (CSS, JS, изображения) по-прежнему обслуживаются напрямую с диска. Это аналогично директиве `try_files` в nginx.

## Ограниченная очередь и обратное давление

Канал между Tokio и воркерами PHP использует `crossbeam_channel::bounded(QUEUE_CAPACITY)`. Исполнитель вызывает `try_send()` (неблокирующий) для постановки запросов в очередь:

```rust
if let Err(e) = self.request_tx.as_ref().unwrap().try_send(worker_request) {
    let (status, body) = match e {
        TrySendError::Full(_) => (503, "Service Unavailable: queue full"),
        TrySendError::Disconnected(_) => (500, "PHP worker pool unavailable"),
    };
    return ExecuteResult::Immediate(ScriptResponse {
        status,
        headers: vec![],
        body: Bytes::from_static(body.as_bytes()),
        execution_time_us: 0,
    });
}
```

| Условие | Поведение |
|---|---|
| В очереди есть место | Запрос ставится в очередь, задача Tokio ожидает oneshot-ответ |
| Очередь заполнена | Немедленно возвращается 503 Service Unavailable с заголовком `Retry-After: 1` |
| Воркеры отключены | 500 Internal Server Error (пул воркеров недоступен) |

Эта архитектура обеспечивает обратное давление: когда воркеры PHP не справляются, новые запросы отклоняются немедленно, а не ставятся в очередь бесконечно. Заголовок `Retry-After: 1` сигнализирует клиентам о необходимости повторить запрос после короткой задержки.

### Метрики

Обработчик соединений отслеживает состояние очереди через структуру `Metrics`:

| Метод | Когда |
|---|---|
| `metrics.request_queued()` | Непосредственно перед `executor.execute()` |
| `metrics.request_dequeued()` | Когда приходит ответ по oneshot-каналу |
| `metrics.request_dropped()` | Когда oneshot-канал сломан (воркер упал) |

Эти данные предоставляются как gauge/counter-метрики Prometheus: `oxphp_pending_requests`, `oxphp_busy_workers`, `oxphp_dropped_requests_total`.

## StubExecutor

`StubExecutor` (`src/executor/stub.rs`) — это бэкенд с нулевыми накладными расходами для тестирования и бенчмаркинга. Он синхронно возвращает фиксированный ответ 200 OK без создания каких-либо потоков:

```rust
impl ScriptExecutor for StubExecutor {
    fn execute(&self, _request: ScriptRequest) -> ExecuteResult {
        ExecuteResult::Immediate(ScriptResponse {
            status: 200,
            headers: vec![(
                HeaderName::from_static("content-type"),
                HeaderValue::from_static("text/plain"),
            )],
            body: Bytes::from_static(b"OK"),
            execution_time_us: 0,
        })
    }
}
```

Используйте stub-исполнитель, установив `EXECUTOR=stub`. Он активируется автоматически, когда бинарный файл скомпилирован без `--features php`.

## Выбор исполнителя

Фабрика `create_executor()` в `src/executor/mod.rs` выбирает бэкенд на основе переменной окружения `EXECUTOR` и feature-флагов времени компиляции:

| `EXECUTOR` | `--features php` | Результат |
|---|---|---|
| `sapi` (по умолчанию) | да | `SapiExecutor` (пул воркеров PHP) |
| `sapi` (по умолчанию) | нет | `StubExecutor` (запасной вариант с предупреждением) |
| `stub` | любой | `StubExecutor` (режим бенчмарка) |

## Остановка

`SapiExecutor` реализует `Drop` для корректной остановки:

1. **Глобальный флаг остановки**: `global_shutdown.store(true)` — останавливает ScaleManager (если запущен)
2. **Удаление отправителя канала**: Воркеры получают `Err` от `recv()` (статический) или обнаруживают отключение (динамический) и выходят из циклов
3. **Остановка каждого воркера**: Устанавливает флаг `shutdown` для каждого воркера, гарантируя выход динамических воркеров из циклов с тайм-аутом
4. **Присоединение всех потоков воркеров**: Блокируется до завершения текущего запроса каждым воркером
5. **Очистка PHP**: `php_module_shutdown()`, `sapi_shutdown()`, `tsrm_shutdown()` последовательно

Это гарантирует, что ни один PHP-запрос не будет прерван посередине выполнения при остановке.
