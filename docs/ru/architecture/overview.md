# Обзор архитектуры

OxPHP — это HTTP-сервер в виде единого бинарного файла, заменяющий традиционную связку nginx + PHP-FPM. Он выполняет разбор HTTP, терминацию TLS, маршрутизацию, выполнение PHP, сжатие и наблюдаемость в рамках одного процесса без внешних зависимостей во время выполнения.

## Как работает OxPHP

OxPHP объединяет два уровня среды выполнения в одном процессе:

1. **Асинхронный HTTP-уровень** — событийно-ориентированный сетевой уровень принимает TCP-соединения, выполняет TLS-рукопожатия, разбирает HTTP-запросы и отправляет ответы. Он обрабатывает тысячи одновременных соединений с использованием неблокирующего ввода-вывода — один медленный клиент никогда не заблокирует другого.
2. **Пул PHP-воркеров** — пул выделенных PHP-воркеров выполняет ваши PHP-скрипты. В стандартном режиме каждый воркер обрабатывает один запрос за раз. В [режиме Worker](../features/worker-mode.md) с включённым [мультиплексированием файберов](../features/fiber-multiplexing.md) один воркер может обслуживать несколько конкурентных запросов — когда скрипт вызывает `oxphp_sleep()` или `oxphp_async_await()`, файбер уступает поток, и воркер переключается на следующий запрос.
3. **Асинхронный пул** — отдельные OS-потоки для задач, отправленных через `oxphp_async()`. Этот пул изолирован от пула воркеров, чтобы тяжёлые фоновые вычисления не блокировали обработку HTTP-запросов.

Эти два уровня взаимодействуют через ограниченную очередь. Когда поступает HTTP-запрос, требующий выполнения PHP, асинхронный уровень помещает его в очередь. Свободный PHP-воркер забирает его, выполняет скрипт и возвращает ответ асинхронному уровню для доставки клиенту.

Такое разделение означает, что сетевой ввод-вывод — принятие соединений, чтение заголовков, сжатие ответов, обслуживание статических файлов — никогда не конкурирует с выполнением PHP за ресурсы. Каждый уровень масштабируется независимо.

## Пул воркеров

Пул PHP-воркеров определяет, сколько PHP-скриптов может выполняться одновременно. OxPHP поддерживает два режима пула.

### Статический пул

Фиксированное число воркеров запускается при старте и остаётся работающим на протяжении всего времени жизни сервера. Это режим по умолчанию.

```bash
PHP_WORKERS=8    # ровно 8 воркеров
PHP_WORKERS=0    # авто-определение (по умолчанию): половина доступных ядер CPU, минимум 1
```

### Динамический пул

Воркеры масштабируются вверх и вниз в зависимости от нагрузки. Укажите минимальное и максимальное количество через двоеточие:

```bash
PHP_WORKERS=2:16    # стартует с 2, масштабируется до 16 при нагрузке
```

Когда все текущие воркеры заняты, OxPHP запускает новые воркеры вплоть до максимума. Когда воркер простаивает дольше, чем `PHP_WORKERS_IDLE_SECONDS` (по умолчанию: 30 секунд), он завершается, уменьшая количество до минимума.

### Очередь и противодавление

Между асинхронным HTTP-уровнем и пулом воркеров расположена ограниченная очередь. Её ёмкость по умолчанию равна начальному числу воркеров, умноженному на 128, и может быть переопределена через `QUEUE_CAPACITY`. Для статического пула начальное число равно настроенному числу воркеров. Для динамического пула (`MIN:MAX`) начальное число равно минимуму.

Когда очередь заполнена — то есть все воркеры заняты, а очередь достигла ёмкости — OxPHP немедленно возвращает клиенту ответ `529 Site is Overloaded` с заголовком `Retry-After`. Код 529 (нестандартный, используется Cloudflare и другими) явно отличает перегрузку от ошибок приложения (500) и обслуживания (503), что упрощает настройку алертов и балансировщиков.

## Поток запросов

Каждый запрос проходит через одинаковый конвейер, независимо от того, обслуживает ли он статический файл или выполняет PHP:

```text
Клиент
  │
  ▼
TLS-терминация (если настроена)
  │
  ▼
Разбор HTTP + назначение Request ID
  │
  ▼
Проверка ограничения частоты запросов
  │
  ▼
Разрешение маршрута
  │
  ├── Статический файл ──► Кэш файлов / чтение с диска
  │                               │
  │                               ▼
  │                         Сжатие + заголовки ответа
  │                               │
  │                               ▼
  │                         Ответ клиенту
  │
  └── PHP-запрос ──► Ограниченная очередь (529 если полна)
                            │
                            ▼
                       PHP-воркер выполняет скрипт
                            │
                       ┌────┼─────────────────┐
                       ▼    ▼                 ▼
                    Обычный  SSE-стриминг   Ранний ответ
                    ответ    (chunked)      (finish_request)
                       │       │                │
                       ▼       ▼                ▼
                    Сжатие  Чанки ──► клиент  Ответ клиенту
                       │                      + фоновая работа
                       ▼
                    Ответ клиенту
```

1. **TLS-терминация** — если настроены `TLS_CERT` и `TLS_KEY`, OxPHP выполняет TLS напрямую. Отдельный обратный прокси не нужен.
2. **Разбор HTTP и Request ID** — запрос разбирается, и генерируется уникальный идентификатор запроса (либо сохраняется входящий заголовок `X-Request-ID`).
3. **Ограничение частоты запросов** — если задан `RATE_LIMIT`, IP клиента проверяется по счётчику запросов на уровне IP. Запросы, превышающие лимит, немедленно получают ответ `429 Too Many Requests`.
4. **Разрешение маршрута** — URL сопоставляется с настроенным режимом маршрутизации (традиционный, framework, SPA или worker). Результатом является статический файл, PHP-скрипт или 404.
5. **Статические файлы** — обслуживаются напрямую из кэша в памяти (для часто запрашиваемых файлов) или передаются с диска потоком. OxPHP автоматически добавляет заголовки `ETag`, `Last-Modified` и `Cache-Control`.
6. **Выполнение PHP** — запрос помещается в ограниченную очередь и забирается свободным воркером. Если очередь полна, клиент немедленно получает 529.
7. **Сжатие** — текстовые ответы сжимаются с помощью Brotli перед отправкой, когда клиент передаёт `Accept-Encoding: br` (настраивается через `COMPRESSION_LEVEL`).
8. **SSE-стриминг** — если скрипт устанавливает `Content-Type: text/event-stream` или вызывает `oxphp_stream_flush()`, OxPHP переключается на потоковую передачу: каждый вызов `flush()` отправляет чанк клиенту немедленно, без буферизации всего ответа. В режиме Worker SSE кооперативно работает с [мультиплексированием файберов](../features/fiber-multiplexing.md).
9. **Ранний ответ** — вызов `oxphp_finish_request()` немедленно отправляет HTTP-ответ клиенту. Скрипт продолжает выполнение в фоне — для записи логов, обновления кэша, отправки уведомлений — не удерживая соединение.
10. **Доставка ответа** — готовый ответ отправляется обратно по соединению, и если включено [логирование доступа](../features/access-logging.md), срабатывает запись в лог.

## Режим Worker и стандартный режим

OxPHP поддерживает две модели выполнения PHP:

**Стандартный режим** (по умолчанию) создаёт свежую среду PHP для каждого запроса. Автозагрузчики, конфигурация и соединения с базой данных инициализируются при каждом запросе и уничтожаются после него. Эта модель совместима со всеми PHP-приложениями без дополнительной настройки.

**Режим Worker** сохраняет PHP-процессы живыми между запросами. Ваше приложение инициализируется один раз — загружает автозагрузчик, конфигурацию и устанавливает соединения с базой данных — а затем входит в цикл обработки запросов. Между запросами OxPHP автоматически сбрасывает суперглобальные переменные, буферы вывода и заголовки ответа, сохраняя инициализированное состояние.

Режим Worker устраняет накладные расходы на инициализацию при каждом запросе, что может значительно снизить время ответа для приложений на базе фреймворков (Laravel, Symfony и т.д.), где инициализация обходится дорого.

Для включения режима Worker задайте `WORKER_FILE`, указав на PHP-скрипт, вызывающий `oxphp_worker()`:

```php
<?php
require __DIR__ . '/../vendor/autoload.php';
$app = new MyApp\Application();

oxphp_worker(function () use ($app) {
    $app->handle();
});
```

Подробное руководство см. в разделе [Режим Worker](../features/worker-mode.md).

## Внутренний сервер

Если задана переменная `INTERNAL_ADDR`, OxPHP запускает отдельный HTTP-сервер на указанном порту. Он обслуживает три эндпоинта:

| Эндпоинт | Описание |
|----------|----------|
| `GET /health` | Статус работоспособности в JSON (аптайм, счётчики запросов, соединения, состояние воркеров). Возвращает `200` при нормальной работе, `503` при деградации. |
| `GET /metrics` | Метрики в формате Prometheus — счётчики запросов, время ответа, ожидание в очереди, статистика воркеров, экономия сжатия. |
| `GET /config` | Снимок активной конфигурации в JSON. Пути к TLS-файлам скрыты. |

Внутренний сервер не проходит через пул PHP-воркеров и ограниченную очередь — он отвечает напрямую из асинхронного HTTP-уровня, поэтому остаётся доступным даже при полной загрузке PHP-пула. Это делает `/health` пригодным для Kubernetes liveness/readiness проб.

Подробнее — в разделе [Внутренний сервер](../features/internal-server.md).

## Безопасность

OxPHP предоставляет ряд гарантий для надёжной работы вашего приложения в продакшене:

- **Изоляция запросов** — если PHP-скрипт аварийно завершается или вызывает фатальную ошибку, затрагивается только этот единственный запрос. Сервер продолжает обрабатывать все остальные запросы в штатном режиме. Аварийно завершившийся воркер автоматически заменяется новым.
- **Автоматический перезапуск воркеров** — OxPHP отслеживает работоспособность всех PHP-воркеров. Если воркер неожиданно завершается, вместо него запускается новый без ручного вмешательства.
- **Защита от перегрузки** — ограниченная очередь запросов предотвращает перегрузку. Когда сервер работает на пределе мощности, новые запросы получают ответ 529 с заголовком `Retry-After`, а не ставятся в очередь бесконечно, вызывая каскадные тайм-ауты.
- **Защита от обхода пути** — все URL-пути обеззараживаются до обращения к файловой системе. Закодированные в процентах попытки обхода, сегменты `..` и пути, выходящие за пределы корня документа, блокируются.
- **Штатное завершение работы** — при получении SIGTERM OxPHP прекращает принимать новые соединения и ожидает завершения активных запросов (вплоть до настраиваемого тайм-аута дренирования) перед выходом.
