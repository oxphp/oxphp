OxPHP — это HTTP-сервер в виде единого бинарного файла, заменяющий традиционный стек nginx + PHP-FPM. Он объединяет асинхронную среду выполнения ввода-вывода (Rust/Tokio) с многопоточным пулом воркеров PHP (ZTS) в одном процессе.

## Принципы проектирования

- **Единый бинарный файл**: Нет внешнего менеджера процессов, нет сайдкаров. Один бинарный файл обрабатывает TCP, TLS, разбор HTTP, маршрутизацию, выполнение PHP и наблюдаемость.
- **Асинхронный ввод-вывод, синхронный PHP**: Сетевой ввод-вывод мультиплексируется в асинхронной среде выполнения. PHP-скрипты выполняются в выделенных потоках ОС. Обе половины взаимодействуют через каналы.
- **Минимум копирования**: Данные запроса проходят через конвейер без лишних клонирований. `Bytes`, `Arc` и `std::mem::take` позволяют избежать аллокаций на горячем пути.

## Модель среды выполнения

```
                    ┌─────────────────────────────────────────────────┐
                    │      Tokio Runtime (single- or multi-thread)    │
                    │                                                 │
                    │  ┌──────────┐  ┌───────────┐  ┌───────────┐     │
  TCP connections──▶│  │ accept   │  │ service   │  │ service   │     │
                    │  │ loop     │  │ task      │  │ task      │     │
                    │  └──────────┘  └─────┬─────┘  └─────┬─────┘     │
                    │                      │              │           │
                    └──────────────────────┼──────────────┼───────────┘
                         ScriptRequest     │              │
                  (sync_channel + oneshot) │  ┌───────────┘
                                           │  │
                                           ▼  ▼
                    ┌──────────────────────┼──┼───────────────────────┐
                    │                                                 │
                    │  ┌────────────┐  ┌────────────┐  ┌────────────┐ │
                    │  │php-worker-0│  │php-worker-1│  │php-worker-N│ │
                    │  │            │  │            │  │            │ │
                    │  └────────────┘  └────────────┘  └────────────┘ │
                    │              PHP Worker Pool (OS threads)       │
                    └─────────────────────────────────────────────────┘
```

**Среда выполнения Tokio** настраивается через `TOKIO_WORKERS`. При значении `0` (по умолчанию) используется `Builder::new_current_thread()` для однопоточной асинхронной среды. При значении `N` используется `Builder::new_multi_thread()` с N рабочими потоками для повышенной пропускной способности. Она обрабатывает всю асинхронную работу: приём TCP-соединений, TLS-рукопожатия, разбор HTTP, маршрутизацию, сжатие и диспетчеризацию событий. Каждое соединение — это легковесная задача Tokio. Процесс использует mimalloc в качестве глобального аллокатора для снижения задержки аллокаций при конкурентном доступе потоков.

**Пул воркеров PHP** — это набор выделенных потоков ОС. Каждый поток владеет экземпляром интерпретатора PHP ZTS (Zend Thread Safety). Воркеры получают структуры `ScriptRequest` через ограниченный `crossbeam_channel` и возвращают `ScriptResponse` через канал `tokio::sync::oneshot`.

### Почему PHP не работает в многопоточном режиме внутри Tokio?

C-среда выполнения PHP не является безопасной для асинхронного использования. Такие функции, как `php_request_startup()` и `php_execute_script()`, блокируют вызывающий поток и изменяют глобальное состояние, не являющееся потокобезопасным. Запуск их в рабочем потоке Tokio приведёт к голоданию асинхронной среды выполнения. Выделенные потоки ОС изолируют блокирующее поведение PHP от цикла асинхронного ввода-вывода.

### Основные компоненты

| Компонент | Расположение | Назначение |
|---|---|---|
| **Config** | `src/config/` | Считывает всю конфигурацию из переменных окружения при запуске |
| **Server** | `src/server/mod.rs` | Управляет циклом приёма соединений, построителем hyper-util, флагом остановки |
| **RouteConfig** | `src/server/routing.rs` | Разрешает URI-пути в `Serve`, `Execute` или `NotFound` |
| **FileCache** | `src/server/response/static_file.rs` | LRU-кэш для метаданных файлов и поиска канонических путей |
| **ScriptExecutor** | `src/executor/mod.rs` | Трейт для бэкендов выполнения PHP (`SapiExecutor`, `StubExecutor`) |
| **Metrics** | `src/metrics.rs` | Безблокировочные атомарные счётчики (формат экспозиции Prometheus) |
| **EventDispatcher** | `src/events/dispatcher.rs` | Типизированная синхронная диспетчеризация событий с упорядочиванием по приоритету |
| **PluginManager** | `src/plugin/mod.rs` | Управление жизненным циклом плагинов с топологической сортировкой |
| **RateLimiter** | `src/server/rate_limit.rs` | Ограничение частоты запросов по IP-адресу с использованием скользящего окна и `DashMap` |
| **Compression** | `src/server/compression.rs` | Сжатие Brotli для текстовых ответов |

## Каналы связи

Асинхронная и синхронная половины OxPHP взаимодействуют через два типа каналов:

| Канал | Направление | Тип | Назначение |
|---|---|---|---|
| `crossbeam_channel::bounded` | Tokio → воркер PHP | `ScriptRequest` | Ограниченная очередь с обратным давлением (503 при заполнении) |
| `tokio::sync::oneshot` | Воркер PHP → Tokio | `ScriptResponse` | Один ответ на запрос |

Этот паттерн позволяет среде выполнения Tokio отправлять работу воркерам PHP без блокировки и асинхронно ожидать ответы. Подробности см. в разделе [Пул воркеров](./worker-pool.md).

## Последовательность запуска

1. **Конфигурация**: `Config::from_env()` считывает все переменные окружения
2. **Метрики**: `Metrics::new()` инициализирует безблокировочные атомарные счётчики (создаются до исполнителя, чтобы метрики воркеров могли записываться при запуске)
3. **Менеджер плагинов**: `PluginManager::new()` создаёт менеджер, плагины добавляются, затем `init_all()` регистрирует обработчики событий плагинов в диспетчере и заполняет реестр функций плагинов в мосте
4. **PHP-функции плагинов**: Функции плагинов передаются в `sapi::register_plugin_functions()`, чтобы реестр моста был заполнен до запуска движка PHP
5. **Исполнитель**: `create_executor(metrics)` инициализирует TSRM, регистрирует модуль SAPI, запускает `php_module_startup()` (что инициирует MINIT — регистрацию функций плагинов в Zend), разбирает режим `PHP_WORKERS` и порождает начальные потоки воркеров PHP
6. **Среда выполнения Tokio**: Настраивается через `TOKIO_WORKERS` — `0` создаёт однопоточную среду, `N` создаёт многопоточную среду с N потоками
7. **Менеджер масштабирования**: `executor.start_scale_manager()` порождает задачу масштабирования воркеров (no-op в статическом режиме). В статическом режиме фоновый монитор здоровья обнаруживает и пересоздаёт упавшие воркеры
8. **Ограничение частоты запросов**: Опционально, с фоновой задачей очистки
9. **TLS**: Опционально, загружает сертификат и ключ через `rustls`
10. **Диспетчер событий**: Встроенные обработчики зарегистрированы, затем `freeze()` сортирует по приоритету
11. **TCP-слушатель**: Привязывается к настроенному адресу
12. **Внутренний сервер**: Опциональные `/health`, `/metrics`, `/config` на отдельном порту
13. **Готовность плагинов**: `plugin_manager.on_ready_all()` уведомляет плагины о том, что сервер слушает
14. **Цикл приёма**: Порождает задачу Tokio на каждое соединение, ограниченную `Semaphore(max_connections)`

## Последовательность остановки

1. SIGTERM или Ctrl+C активирует `shutdown_signal()`
2. `plugin_manager.shutdown_all()` уведомляет плагины, затем `server.shutdown()` устанавливает атомарный флаг остановки и вызывает `executor.shutdown()`
3. Цикл приёма прерывается при `is_shutdown()`
4. Фаза дренажа: ожидание до `drain_timeout_secs` (по умолчанию 30) для завершения текущих соединений
5. Задача внутреннего сервера прерывается
6. `SapiExecutor::drop()` закрывает отправитель канала, дожидается завершения всех потоков воркеров, затем вызывает `php_module_shutdown()`, `sapi_shutdown()` и `tsrm_shutdown()`
